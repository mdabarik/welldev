Transaction Isolation — ৪টি level

দুইটা terminal, দুইটা psql session (transaction-A.sql আর transaction-B.sql)। একই সময়ে একই row ছুঁলে কে কী দেখে — প্রতিটা level-এ ধাপে ধাপে। সব output PostgreSQL 18-এ চালিয়ে নেওয়া।

একটাই table — দুইটা bank account। প্রতিটা level শুরুর আগে Reset চালাও, যাতে সবসময় Rahim = 1000, Karim = 500 থেকে শুরু হয়।

terminal
createdb bank          # একবার
psql -d bank           # Terminal 1 → Session A
psql -d bank           # Terminal 2 → Session B

পুরো file \i দিয়ে একবারে চালাবে না। [2.4]-এর মতো নম্বর ধরে A আর B-তে পালা করে একেকটা লাইন চালাও।

transaction-A.sql · setup
CREATE TABLE accounts (
  id      int  PRIMARY KEY,
  name    text NOT NULL,
  balance int  NOT NULL CHECK (balance >= 0)
);

-- Reset (প্রতিটা level-এর আগে)
TRUNCATE accounts;
INSERT INTO accounts VALUES (1, 'Rahim', 1000), (2, 'Karim', 500);

?Isolation কী ঠেকায় — ৪টি সমস্যা

দুটো transaction একসাথে চললে এই চারটা গোলমাল হতে পারে। Isolation level যত উঁচু, তত বেশি সমস্যা বন্ধ — কিন্তু তত বেশি অপেক্ষা বা retry।

Dirty Readuncommitted data পড়া

B এখনো commit করেনি, অথচ A তার পরিবর্তন দেখে ফেলল। পরে B rollback করলে A এমন data দেখেছে যা কখনো ছিলই না।

Non-repeatable Readএকই row, দুই মান

A একই row দুবার পড়ল, মাঝে B সেটা UPDATE করে commit করেছে — তাই দুবার দুই রকম মান।

Phantom Readনতুন row হাজির

একই WHERE দুবার চালাল, মাঝে B নতুন row INSERT করেছে — দ্বিতীয়বার একটা "ভূত" row বেশি।

Serialization Anomalywrite skew

দুটো transaction আলাদাভাবে ঠিক, কিন্তু একসাথে চললে এমন ফল দেয় যা একটার পর আরেকটা চালালে কখনো হতো না।

1READ UNCOMMITTED

প্রশ্ন: B-এর commit-না-হওয়া পরিবর্তন কি A দেখতে পায়?
ফল: PostgreSQL-এ dirty read হয় না — level-টা read uncommitted দেখালেও (SHOW transaction_isolation) ভেতরে Read Committed-এর মতো চলে। MVCC-তে প্রতিটা query শুধু commit হওয়া row version দেখে, তাই uncommitted data পড়ার কোনো রাস্তাই নেই। অন্য database (যেমন SQL Server, MySQL) এখানে 500 দেখাত।

2READ COMMITTED · default

প্রশ্ন: একই transaction-এর ভেতরে একই query দুবার চালালে কি একই উত্তর আসে?
ফল: প্রতিটা statement নতুন snapshot নেয়, তাই A মাঝপথে B-এর commit করা পরিবর্তন দেখে ফেলে। [2.6]-এ non-repeatable read, [2.7]-এ phantom read। B এখানে BEGIN ছাড়া চালাচ্ছে — psql-এ প্রতিটা statement নিজেই একটা transaction (autocommit)।

বোনাস: দুজনেই একই row UPDATE করলে?

ফল: প্রথম UPDATE row-টায় lock নেয়, দ্বিতীয়টা অপেক্ষা করে। A commit করলে B row-টা আবার পড়ে (1100) তার উপর +200 করে — শেষে 1300, কোনো update হারায় না। কিন্তু app যদি আগে SELECT করে, তারপর হিসাব করে SET balance = 1100 লেখে, তাহলে এই level-এ lost update হতে পারে — তখন SELECT … FOR UPDATE বা উঁচু level লাগবে।

3REPEATABLE READ

প্রশ্ন: B মাঝপথে commit করলেও A কি পুরো transaction জুড়ে একই data দেখে?
ফল: A-র প্রথম query-তে একটা snapshot নেওয়া হয়, transaction শেষ পর্যন্ত সেটাই — তাই balance আর count কোনোটাই বদলায় না। কিন্তু A যখন সেই পুরনো row-টাই বদলাতে যায় যেটা B ইতিমধ্যে বদলে ফেলেছে, PostgreSQL lost update হতে না দিয়ে error দেয়। App-কে তখন পুরো transaction আবার চালাতে (retry) হবে।

4SERIALIZABLE

নিয়ম: Rahim + Karim মিলিয়ে কমপক্ষে 1000 থাকতে হবে। দুজন একসাথে 500 করে তুললে?
ফল: A আর B আলাদা row বদলেছে, তাই কোনো lock conflict নেই। কিন্তু দুজনেই এমন data পড়ে সিদ্ধান্ত নিয়েছে যেটা অন্যজন বদলে দিয়েছে। দুটোই commit হলে sum হতো 500 — নিয়ম ভাঙত। PostgreSQL এই read/write নির্ভরতা ধরে ফেলে (SSI) আর একটাকে বাতিল করে। Retry করলে B এবার নতুন sum (1000) দেখবে আর নিজেই থেমে যাবে।

একই ধাপ REPEATABLE READ-এ চালালে

Write skew: দুটো COMMIT-ই সফল, sum এখন 500। Repeatable Read শুধু একই row-এর conflict ধরে, আলাদা row মিলিয়ে বানানো নিয়ম (invariant) না। এটা ঠেকাতে Serializable লাগে, অথবা Read Committed-এ SELECT … FOR UPDATE দিয়ে row গুলো lock করতে হয়।

⚙ভেতরে কী হয় — MVCC

PostgreSQL কোনো row জায়গায় বসে overwrite করে না। প্রতিটা UPDATE একটা নতুন row version বানায় (xmin = যে transaction বানাল, xmax = যে মুছল)। Snapshot হলো "কোন কোন transaction commit হয়েছে" তার একটা তালিকা — query শুধু সেই version গুলো দেখে। Level গুলোর পার্থক্য আসলে snapshot কখন নেওয়া হয়, সেটাই।

LevelSnapshot কখনConflict হলে
READ COMMITTEDপ্রতিটা statement-এর শুরুতে নতুনLock-এ অপেক্ষা, তারপর নতুন version-এর উপর আবার চালায়
REPEATABLE READTransaction-এর প্রথম statement-এ একবারএকই row অন্য কেউ বদলালে 40001 error
SERIALIZABLERepeatable Read-এর মতোসাথে কে কী পড়ল তাও ট্র্যাক করে (SSI); বিপজ্জনক চক্র পেলে 40001

Reader কখনো writer-কে আটকায় না, writer-ও reader-কে না — শুধু দুজন writer একই row ছুঁলে অপেক্ষা। এ কারণেই PostgreSQL-এ SELECT কখনো lock-এ আটকে থাকে না।

✓কোনটা কখন

READ COMMITTED

বেশিরভাগ web app। Single-statement update (balance = balance - 500) নিরাপদ। Read-then-write লাগলে SELECT … FOR UPDATE।

REPEATABLE READ

Report, export, backup — পুরো transaction জুড়ে একটা স্থির ছবি দরকার। Write করলে retry রাখতে হবে।

SERIALIZABLE

টাকা, inventory, seat booking — যেখানে নিয়ম একাধিক row জুড়ে। Retry loop বাধ্যতামূলক।

READ UNCOMMITTED

PostgreSQL-এ আলাদা কিছু না, Read Committed-ই পাবে। ব্যবহারের কারণ নেই।

Level সেট করার উপায়

BEGIN ISOLATION LEVEL SERIALIZABLE;                    -- শুধু এই transaction
BEGIN; SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; -- BEGIN-এর ঠিক পরে
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- পুরো session
ALTER DATABASE bank SET default_transaction_isolation = 'serializable';    -- নতুন সব connection
SHOW transaction_isolation;                            -- এখন কোনটা চলছে

Retry ছাড়া Serializable অর্ধেক কাজ

Error code 40001 (serialization_failure) মানে "কিছু ভুল হয়নি, আবার চালাও"। C# (Npgsql) দিয়ে:

async Task WithdrawAsync(NpgsqlDataSource db, int id, int amount)
{
    for (var attempt = 1; ; attempt++)
    {
        await using var conn = await db.OpenConnectionAsync();
        await using var tx = await conn.BeginTransactionAsync(IsolationLevel.Serializable);
        try
        {
            var sum = (long)(await new NpgsqlCommand(
                "SELECT sum(balance) FROM accounts", conn, tx).ExecuteScalarAsync())!;
            if (sum - amount < 1000) throw new InvalidOperationException("Joint balance too low");

            var upd = new NpgsqlCommand(
                "UPDATE accounts SET balance = balance - @amt WHERE id = @id", conn, tx);
            upd.Parameters.AddWithValue("amt", amount);
            upd.Parameters.AddWithValue("id", id);
            await upd.ExecuteNonQueryAsync();

            await tx.CommitAsync();
            return;
        }
        catch (PostgresException e) when (e.SqlState == PostgresErrorCodes.SerializationFailure && attempt < 5)
        {
            await tx.RollbackAsync();   // নতুন snapshot নিয়ে আবার শুরু
        }
    }
}

QInterview-এ যা আসে

PostgreSQL-এর default isolation level কোনটা?

READ COMMITTED। MySQL (InnoDB)-এর default REPEATABLE READ।

PostgreSQL-এ dirty read করা যায়?

না। READ UNCOMMITTED চাইলেও MVCC-র কারণে শুধু commit হওয়া data দেখা যায় — আচরণ READ COMMITTED-এর মতো।

Non-repeatable read আর phantom read-এর পার্থক্য?

Non-repeatable: আগে পড়া একটা row-এর মান বদলে গেছে (UPDATE/DELETE)। Phantom: একই শর্তের query-তে row-এর সংখ্যা বদলে গেছে (INSERT)।

Repeatable Read থাকলে Serializable কেন লাগে?

Write skew-এর জন্য। দুটো transaction আলাদা row বদলায়, কিন্তু একে অপরের পড়া data-র উপর ভর করে সিদ্ধান্ত নেয় — Repeatable Read এটা ধরে না, Serializable ধরে।

"could not serialize access" error এলে কী করবে?

পুরো transaction ROLLBACK করে শুরু থেকে আবার চালাবে। এটা bug না — উঁচু level-এর দাম। App-এ retry loop রাখতে হবে।

উঁচু level মানেই কি ধীর?

PostgreSQL-এ read অপেক্ষা করে না, তাই খুব বেশি না। খরচ আসে retry থেকে — conflict যত বেশি, তত বেশি transaction বাতিল হয়ে আবার চলে।
