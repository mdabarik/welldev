AAtomicity

All or nothing — transaction ভাঙা যায় না

একটা transaction-এর ভেতরের সব statement মিলে একটা একক কাজ। একটাও fail করলে আগের গুলোও মুছে যায় — database এমন অবস্থায় ফেরে যেন transaction শুরুই হয়নি।

বাস্তবে: bKash-এ টাকা পাঠালে — তোমার account থেকে কাটল, কিন্তু network চলে যাওয়ায় বন্ধুর account-এ পৌঁছাল না। Atomicity না থাকলে টাকাটা মাঝপথে হাওয়া হয়ে যেত।

Karim-এর আছে 500, সে 2000 পাঠাতে চায়

psqlfail → সব বাতিল
BEGIN;
UPDATE accounts SET balance = balance + 2000 WHERE id = 1;   -- Rahim +2000
SELECT * FROM accounts ORDER BY id;
--  1 | Rahim | 3000     ← এই transaction-এর ভেতরে দেখা যাচ্ছে
--  2 | Karim |  500

UPDATE accounts SET balance = balance - 2000 WHERE id = 2;   -- Karim −2000
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"
DETAIL:  Failing row contains (2, Karim, -1500).

SELECT * FROM accounts;
ERROR:  current transaction is aborted, commands ignored until end of transaction block

COMMIT;
ROLLBACK          -- COMMIT চাইলেও PostgreSQL rollback করে
পরেকিছুই বদলায়নি
SELECT * FROM accounts ORDER BY id;
--  1 | Rahim | 1000     ← +2000 টাও মুছে গেছে
--  2 | Karim |  500
SAVEPOINT — আংশিক rollback
BEGIN;
UPDATE accounts SET balance = balance - 200 WHERE id = 1;
SAVEPOINT before_risky;
UPDATE accounts SET balance = balance - 9999 WHERE id = 2;
ERROR:  ... violates check constraint "accounts_balance_check"
ROLLBACK TO SAVEPOINT before_risky;   -- শুধু পরের অংশ বাতিল
UPDATE accounts SET balance = balance + 200 WHERE id = 2;
COMMIT;
--  1 | Rahim |  800
--  2 | Karim |  700
PostgreSQL কীভাবে করে:
  • UPDATE পুরনো row মুছে না, নতুন version লেখে — তাতে transaction ID (xmin) বসানো থাকে।
  • Transaction commit না rollback, সেটা আলাদা জায়গায় (pg_xact) লেখা থাকে। Rollback হলে নতুন version গুলো কেউ কখনো দেখে না, পরে VACUUM সেগুলো সরিয়ে দেয়।
  • তাই rollback প্রায় তাৎক্ষণিক — কোনো "undo" করে ফেরত লিখতে হয় না।

Application code-এ — C# (Npgsql)

ভুল — transaction নেইটাকা হারাতে পারে
// প্রতিটা command নিজে নিজে commit হয় (autocommit)
await Exec(conn, "UPDATE accounts SET balance = balance - 300 WHERE id = 1");
// ← এখানে app crash / exception হলে?
//   Rahim-এর 300 কাটা গেছে, Karim পায়নি।
await Exec(conn, "UPDATE accounts SET balance = balance + 300 WHERE id = 2");
সঠিক — এক transactionall or nothing
await using var tx = await conn.BeginTransactionAsync();
try
{
    await Exec(conn, "UPDATE accounts SET balance = balance - 300 WHERE id = 1", tx);
    await Exec(conn, "UPDATE accounts SET balance = balance + 300 WHERE id = 2", tx);
    await tx.CommitAsync();      // দুটো একসাথে স্থায়ী
}
catch
{
    await tx.RollbackAsync();    // দুটোই বাতিল
    throw;
}

CConsistency

Valid state → valid state

Transaction শুরুর আগে database যদি সব নিয়ম মেনে চলে, শেষেও মেনে চলবে। নিয়ম ভাঙে এমন কোনো লেখা database নিজেই ফিরিয়ে দেয় — app-এ bug থাকলেও।

বাস্তবে: ব্যাংকের নিয়ম — balance কখনো negative হবে না, একই account number দুবার থাকবে না, আর transfer-এর আগে-পরে মোট টাকা একই থাকবে।

Database-এর নিয়ম ভাঙার চেষ্টা

UPDATE accounts SET balance = -50 WHERE id = 1;
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_check"

INSERT INTO accounts VALUES (1, 'Duplicate', 10);
ERROR:  duplicate key value violates unique constraint "accounts_pkey"
DETAIL:  Key (id)=(1) already exists.

INSERT INTO accounts VALUES (9, NULL, 10);
ERROR:  null value in column "name" of relation "accounts" violates not-null constraint
-- সফল transfer: আগে-পরে মোট টাকা একই
SELECT sum(balance) FROM accounts;   -- 1500

BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
UPDATE accounts SET balance = balance + 300 WHERE id = 2;
COMMIT;

SELECT sum(balance) FROM accounts;   -- 1500 ✓
কার দায়িত্ব কোনটা:
  • Database: যা declare করা আছে — CHECK, PRIMARY KEY, UNIQUE, NOT NULL, FOREIGN KEY, trigger। এগুলো কোনো transaction পেরোতে পারে না।
  • Application: business logic — যেমন "মোট টাকা একই থাকবে" নিশ্চিত হয় কারণ app debit আর credit একই transaction-এ রাখে (Atomicity)।
  • একাধিক row জুড়ে নিয়ম (যেমন "Rahim + Karim ≥ 1000") একসাথে চলা transaction ভাঙতে পারে — তার জন্য SERIALIZABLE লাগে।

IIsolation

একসাথে চললেও যেন একা চলছে

একাধিক transaction একই সময়ে চললে কেউ কারো অর্ধেক-শেষ কাজ দেখবে না। নিচে A টাকা পাঠাচ্ছে, আর একই মুহূর্তে B (ধরো, অডিট report) মোট টাকা গুনছে।

Isolation না থাকলে: t3-এ B দেখত Rahim থেকে 300 কাটা কিন্তু Karim-এ যোগ হয়নি — মোট 1200, অডিট বলত 300 টাকা উধাও। PostgreSQL-এ MVCC-র কারণে B শুধু commit হওয়া data দেখে, আর reader কখনো writer-এর জন্য অপেক্ষা করে না।

DDurability

COMMIT একবার হলে আর হারাবে না

COMMIT সফল বললে সেই data disk-এ নিরাপদ — পরের মুহূর্তে বিদ্যুৎ চলে গেলেও, server crash করলেও। আর যেটা commit হয়নি, restart-এর পর সেটার কোনো চিহ্ন থাকবে না।

বাস্তবে: ATM "Transaction successful" দেখানোর পর ব্যাংকের server reboot হলো। টাকা তো তুমি হাতে পেয়েছ — balance থেকেও অবশ্যই কাটা থাকতে হবে।

PostgreSQL কীভাবে করে — WAL (Write-Ahead Log):
  • Table-এর data file-এ লেখার আগে পরিবর্তনটা WAL নামের একটা append-only log-এ লেখা হয়।
  • COMMIT-এ শুধু WAL-টা fsync করে disk-এ পাঠানো হয় — ছোট, পরপর লেখা, তাই দ্রুত। আসল table page পরে checkpoint-এ লেখা হয়।
  • Crash-এর পর PostgreSQL শেষ checkpoint থেকে WAL আবার চালায় (redo) — commit হওয়া সব ফিরে আসে, uncommitted গুলো অদৃশ্য থাকে।
  • synchronous_commit = off দিলে commit দ্রুত হয়, কিন্তু crash-এ শেষ কয়েকটা commit হারাতে পারে (data নষ্ট হয় না)। fsync = off production-এ কখনো না — crash-এ পুরো database নষ্ট হতে পারে।

QInterview-এ যা আসে

ACID-এর কোনটা database একা নিশ্চিত করতে পারে না?

Consistency। Database শুধু declare করা constraint রক্ষা করে; business rule ঠিক রাখা app-এর দায়িত্ব — সঠিকভাবে transaction ব্যবহার করে। A, I, D database engine নিজেই দেয়।

ACID-এর C আর CAP theorem-এর C কি একই?

না। ACID-এর C মানে নিয়ম (constraint) ঠিক থাকা। CAP-এর C মানে distributed system-এর সব node একই সময়ে একই data দেখানো (linearizability)।

Transaction-এর মাঝে error হলে PostgreSQL কী করে?

পুরো transaction "aborted" অবস্থায় যায় — পরের সব command ignore করে, আর COMMIT দিলেও ROLLBACK হয়। শুধু একটা অংশ বাঁচাতে চাইলে আগে SAVEPOINT রাখতে হয়।

WAL থাকলে commit দ্রুত হয় কেন?

Commit-এ ছড়ানো table page গুলো disk-এ লিখতে হয় না — শুধু WAL-এর শেষে পরপর কয়েকটা byte যোগ করে fsync। Random write-এর বদলে sequential write।

psql-এ BEGIN না লিখলে কি transaction হয় না?

হয় — প্রতিটা statement নিজেই একটা transaction (autocommit)। একটা statement-এর ভেতরে ACID থাকে, কিন্তু একাধিক statement একসাথে রাখতে BEGIN … COMMIT লাগে।

NoSQL database কি ACID মানে?

অনেকে আংশিকভাবে। যেমন MongoDB 4.0 থেকে multi-document transaction দেয়; অনেক system BASE (Basically Available, Soft state, Eventually consistent) মডেলে চলে — availability-র জন্য তাৎক্ষণিক consistency ছাড়ে।
