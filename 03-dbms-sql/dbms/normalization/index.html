Normalization — 1NF থেকে BCNF

Registrar office-এর একটা Excel sheet — এক cell-এ "CSE220, CSE221", একই department head-এর নাম বারবার। সেটাকে ধাপে ধাপে ভেঙে এমন table বানানো যেখানে প্রতিটা তথ্য থাকে ঠিক এক জায়গায়। প্রতিটা normal form-এর official definition, ভাঙা table, সমাধান আর PostgreSQL 18-এ চালানো DDL + JOIN।

1NFAtomic values

প্রতিটা cell-এ একটাই মান, কোনো list না।

সরায়: repeating group 2NFWhole key

Non-key column পুরো key-র উপর নির্ভর করবে।

সরায়: partial dependency 3NFNothing but the key

Non-key column অন্য non-key-র উপর নির্ভর করবে না।

সরায়: transitive dependency BCNF3.5NF

যে-ই কিছু determine করে, সে super key।

সরায়: non-superkey determinant

↗সিঁড়ি — প্রতি ধাপে কী সরে

প্রতিটা normal form আগেরটার সব শর্ত মানে, সাথে একটা নতুন শর্ত যোগ করে। তাই BCNF table মানেই 3NF, 3NF মানেই 2NF — উল্টোটা সবসময় না।

UNFশুরুএক cell-এ list — "CSE220, CSE221" 1NFসরায়repeating group, multi-valued cell 2NFসরায়partial dependency — key-র অংশ → non-key 3NFসরায়transitive dependency — non-key → non-key BCNFসরায়যেকোনো determinant যা super key না

0শুরুর আগে — চারটা ধারণা

Normalization মানে table-কে এমনভাবে ভাগ করা যাতে একটা তথ্য একবারই লেখা থাকে। এর ভাষা হলো functional dependency আর key — এই দুটো পরিষ্কার থাকলে সব normal form এক লাইনে বোঝা যায়।

কেন normalize — redundancy থেকে তিনটা anomaly

একই তথ্য (যেমন "CSE-এর head Dr. Nazmul Hasan") যদি ১০০টা row-তে থাকে, শুধু জায়গা নষ্ট না — তিন রকম bug-এর দরজা খোলে:

Insertion anomaly

একটা তথ্য রাখতে গিয়ে অন্য, অপ্রাসঙ্গিক তথ্য লাগে — নতুন course খুলতে কোনো student লাগবে কেন?

Update anomaly

একটা fact বদলাতে অনেক row বদলাতে হয়; একটা বাদ পড়লেই database নিজের সাথে নিজে অমিল।

Deletion anomaly

একটা তথ্য মুছতে গিয়ে অন্য দরকারি তথ্যও মুছে যায় — শেষ student চলে গেলে course-টাই হারিয়ে যায়।

Functional dependency — X → Y

X → Y পড়ো "X determines Y"। মানে: দুইটা row-তে X-এর মান এক হলে Y-এর মানও অবশ্যই এক। student_id → student_name — 101 যেখানেই থাকুক, নাম সবসময় Rahim Uddin।

FD আসে business rule থেকে, data দেখে না। Data শুধু কোনো FD-কে ভুল প্রমাণ করতে পারে। আর X → Y যেখানে Y ⊆ X (যেমন {a, b} → a) — সেটা trivial FD, normalization-এ গোনা হয় না।

Keys recap

বিস্তারিত আছে Keys গাইডে। এখানে শুধু যা লাগবে — নিচের enrollment table (একটা row = একজন student-এর একটা course) দিয়ে:

Termমানেenrollment-এ উদাহরণ
Super keyযে column set একটা row-কে unique ভাবে চেনায়{student_id, course_code, grade}
Candidate keyMinimal super key — একটা column সরালেই আর unique না{student_id, course_code}
Primary keyCandidate key-গুলোর মধ্যে যেটা বেছে নেওয়া হলো(student_id, course_code)
Prime attributeযে column কোনো একটা candidate key-র অংশstudent_id, course_code
Non-prime attributeকোনো candidate key-তেই নেইstudent_name, dept, course_title, grade …

Partial vs transitive dependency

Partial dependency — non-prime column composite candidate key-র একটা অংশের উপর নির্ভর করে।

student_idcourse_code→gradefull ✓
student_id→student_namepartial ✗

Key এক column-এর হলে partial dependency হওয়া সম্ভবই না। 2NF এটা সরায়।

Transitive dependency — key একটা non-key column-কে determine করে, আর সেটা আরেকটাকে: A → B → C, যেখানে B কোনো key না।

student_id→dept→dept_headtransitive ✗

dept_head আসলে student-এর তথ্য না, department-এর তথ্য — ভুল table-এ বসে আছে। 3NF এটা সরায়।

1NFFirst Normal Form

প্রতিটা cell-এ একটা, ভাঙা যায় না এমন মান

Definition

সহজ বাংলায়: table-এর প্রতিটা ঘরে একটাই মান থাকবে — comma দিয়ে list না, course1, course2, course3 নামে একই জিনিসের জন্য বারবার column না। আর relation-এ duplicate row থাকে না, তাই প্রতিটা row আলাদা করে চেনার মতো একটা key থাকতে হবে।

এই sheet-এর পেছনের business rule (FD) — পরের সব ধাপ এগুলোর উপরেই দাঁড়িয়ে:

2NFSecond Normal Form

Non-key column নির্ভর করবে পুরো key-র উপর — অর্ধেকের উপর না

Definition

সহজ বাংলায়: key যদি একাধিক column মিলে হয় (composite), তাহলে প্রতিটা non-key column-কে জানতে key-র সব column লাগবে। শুধু student_id জানলেই যদি student_name জানা যায়, তাহলে নামটা (student_id, course_code)-ওয়ালা table-এ থাকার কথা না — সেটা student-এর তথ্য, enrollment-এর না।

কেন এখন 2NF:
  • student আর course-এর key এক column-এর — partial dependency হওয়ার মতো "অংশ"-ই নেই।

PostgreSQLDDL + JOIN দিয়ে আগের table

2NF schema
CREATE TABLE student (
  student_id   int  PRIMARY KEY,
  student_name text NOT NULL,
  dept         text NOT NULL,
  dept_head    text NOT NULL
);
CREATE TABLE course (
  course_code  text PRIMARY KEY,
  course_title text NOT NULL,
  credit       int  NOT NULL
);
CREATE TABLE enrollment (
  student_id  int  REFERENCES student,
  course_code text REFERENCES course,
  grade       text NOT NULL,
  PRIMARY KEY (student_id, course_code)
);

3NFThird Normal Form

Non-key column শুধু key-র কথা বলবে — অন্য non-key-র না

Definition

সহজ বাংলায়: কোনো non-key column যেন অন্য একটা non-key column দিয়ে নির্ধারিত না হয়। dept_head জানতে student_id লাগে না, dept জানলেই হয় — মানে এটা department-এর তথ্য, student table-এ বসে আছে। মনে রাখার লাইন (William Kent): প্রতিটা non-key column নির্ভর করবে "the key, the whole key, and nothing but the key"-এর উপর। "whole key" = 2NF, "nothing but the key" = 3NF।

BCNFBoyce–Codd Normal Form (3.5NF)

যে column কিছু determine করে, তাকে super key হতেই হবে

Definition

সহজ বাংলায়: table-এ যে column (বা column set) অন্য কোনো column-এর মান ঠিক করে দেয়, সেটা অবশ্যই পুরো row চেনার মতো key হতে হবে — কোনো ব্যতিক্রম নেই। 3NF একটা ছাড় দিত: ডানপাশের column যদি নিজেই কোনো candidate key-র অংশ (prime) হয়, তাহলে চলবে। এই ছাড় কাজে লাগে শুধু তখন, যখন table-এ একাধিক composite candidate key একে অপরের সাথে overlap করে।

কোনটা বেছে নেবে:
  • Theory: যেকোনো relation-কে সবসময় lossless + dependency-preserving ভাবে 3NF-এ ভাঙা যায় (synthesis algorithm)। BCNF-এ lossless ভাঙা সবসময় যায়, কিন্তু dependency preservation-এর গ্যারান্টি নেই — এই উদাহরণটাই তার প্রমাণ।
  • BCNF-এ যাও যদি হারানো rule-টা trigger বা application code দিয়ে check করতে রাজি থাকো (concurrency-তে সঠিক রাখতে SERIALIZABLE বা lock লাগবে)।
  • 3NF-এ থাকো (ডানের বিকল্প) যদি constraint দিয়েই সব rule চাও। "Mahbub → CSE220" কয়েকবার লেখা থাকে, কিন্তু composite FK থাকায় কখনো অমিল হতে পারে না — redundancy আছে, anomaly নেই।

⇄কখন denormalize করবে

Normalization write-কে নিরাপদ করে, কিন্তু read-এ JOIN বাড়ায়। আগে normalize করো, measure করো, তারপর শুধু hot path-টা ইচ্ছাকৃতভাবে denormalize করো — আর source of truth normalized-ই রাখো।

যেখানে মানায়:
  • Read-heavy reporting / dashboard: প্রতি request-এ ৫টা table JOIN না করে একটা pre-joined table বা materialized view।
  • Data warehouse: star schema — dimension table ইচ্ছা করেই denormalized, কারণ data প্রায় শুধু পড়া হয়।
  • Cached aggregate: post.comment_count রাখা, প্রতিবার count(*) না করে — trigger বা app দিয়ে update।
  • Cache layer: Redis-এ পুরো profile JSON — DB normalized থাকে, cache-এ কপি।

QInterview-এ যা আসে

3NF আর BCNF-এর পার্থক্য কী?

দুটোতেই প্রতিটা nontrivial FD X → A দেখা হয়। BCNF বলে X অবশ্যই super key। 3NF একটা ছাড় দেয়: X super key না হলেও চলবে যদি A একটা prime attribute হয়। পার্থক্য দেখা যায় শুধু overlapping composite candidate key থাকলে — যেমন (student_id, course_code, instructor) যেখানে instructor → course_code।

প্রতিটা BCNF table কি 3NF-ও? আর উল্টোটা?

হ্যাঁ, BCNF মানলে 3NF-এর শর্ত (a) সবসময় পূরণ হয়, তাই BCNF ⊂ 3NF। উল্টোটা না — course_instructor 3NF কিন্তু BCNF না। তবে যে 3NF table-এ একাধিক overlapping candidate key নেই, সেটা নিশ্চিতভাবে BCNF।

Transitive dependency কী? উদাহরণ দাও।

A → B আর B → C, যেখানে B কোনো candidate key না (বা তার অংশ না) এবং C non-prime — তখন A → C হলো transitive। যেমন student_id → dept → dept_head: head-এর নাম student-এর তথ্য না, department-এর। সমাধান: department(dept, dept_head) আলাদা table।

Single-column primary key-ওয়ালা table কি 2NF ভাঙতে পারে?

যদি সেটাই একমাত্র candidate key হয় — না, partial dependency-র জন্য key-র "অংশ" লাগে, তাই table নিজে থেকেই 2NF (তবে 3NF ভাঙতে পারে)। কিন্তু যদি আরেকটা composite candidate key থাকে — যেমন surrogate id PK আর UNIQUE (student_id, course_code), সাথে course_title — তাহলে course_code → course_title ওই candidate key-র অংশের উপর নির্ভর করে, 2NF ভাঙে। Surrogate key সমস্যা লুকায়, সমাধান করে না।

Lossless join decomposition কী, কীভাবে check করবে?

ভাঙা table গুলো আবার natural JOIN করলে ঠিক আসল row গুলো ফেরে — কম না, বাড়তি (spurious) row-ও না। দুই ভাগের জন্য নিয়ম: R1 ∩ R2 → R1 অথবা R1 ∩ R2 → R2 — মানে common column গুলো অন্তত একপাশের key। যেমন student ∩ department = {dept}, যেটা department-এর key।

Dependency preservation কেন গুরুত্বপূর্ণ? BCNF কি সবসময় সেটা দেয়?

প্রতিটা FD যদি কোনো একটা table-এর ভেতরে থাকে, তাহলে PK/UNIQUE দিয়েই সস্তায় enforce করা যায়, JOIN করে check লাগে না। 3NF-এ সবসময় lossless + dependency-preserving decomposition পাওয়া যায়; BCNF-এ সবসময় না — instructor উদাহরণে {student_id, course_code} → instructor হারিয়ে যায়। তাই অনেক team 3NF-এই থামে।

PostgreSQL-এর array বা JSONB column কি 1NF ভাঙে?

Classic অর্থে, যদি তুমি ভেতরের element ধরে query, update বা join করো — হ্যাঁ, সেটা repeating group। "Atomic" নির্ভর করে ব্যবহারের উপর: tags পুরোটা একসাথে পড়া-লেখা হলে array ঠিক আছে। কিন্তু element-এ FK দরকার, বা "এই course কারা নিয়েছে" ধরনের প্রশ্ন বারবার হলে আলাদা table-ই ভালো (GIN index খোঁজা দ্রুত করে, কিন্তু FK দেয় না)।

Normalization কি সবসময় ভালো? Performance-এর কী হবে?

Write-heavy OLTP-তে normalization data-কে সঠিক রাখে আর write ছোট রাখে। Read-heavy reporting-এ বেশি JOIN ধীর হতে পারে — তখন materialized view, summary table বা cache দিয়ে বেছে বেছে denormalize। নিয়ম: আগে 3NF/BCNF, তারপর measure, তারপর denormalize — আর denormalized কপি কে update রাখবে সেটা পরিষ্কার রাখা।
