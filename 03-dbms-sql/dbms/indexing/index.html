Indexing — ডেটা খুঁজে পাওয়ার শর্টকাট

Index ছাড়া database প্রতিটা query-তে পুরো table পড়ে। Index থাকলে কয়েকটা page পড়েই row পেয়ে যায়। এই গাইডে দেখব index disk-এর কোথায় থাকে, কীভাবে বানায়, B-tree আর B+ tree ভেতরে কীভাবে কাজ করে (animation সহ), planner কখন index নেয় আর কখন নেয় না, আর Hash, Partial ও GIN index। প্রতিটা উদাহরণ PostgreSQL 18-এ চালিয়ে আসল output দেওয়া।

1Index কী, কেন

বইয়ের পেছনের সূচি — sorted key + পাতার ঠিকানা

Index হলো table-এর একটা বা কয়েকটা column-এর আলাদা, sorted একটা data structure, যার প্রতিটা entry বলে দেয় সেই value-র row-টা disk-এর কোন page-এর কোন slot-এ আছে। Table নিজে কোনো ক্রমে সাজানো থাকে না, index থাকে।

বইয়ের উদাহরণ: ৬০০ পাতার DBMS বইয়ে "Normalization" খুঁজছ। Index না থাকলে পাতা ১ থেকে ৬০০ পর্যন্ত উল্টাতে হবে — এটাই Seq Scan। বইয়ের শেষে alphabetical সূচিতে "Normalization … 213" দেখে সরাসরি ২১৩ নম্বর পাতায় যাওয়া — এটাই Index Scan। সূচিটা sorted বলে "N" খুঁজে পাওয়া সহজ, আর "213" হলো row-এর ঠিকানা (PostgreSQL-এ যাকে বলে ctid)।

প্রমাণ — একই query, index ছাড়া আর index সহ

Seq Scan মানে table-এর প্রতিটা page প্রথম থেকে শেষ পর্যন্ত পড়া। 1 লাখ row-এর প্রতিটায় customer_id = 4242 চেক করে 99,992টা বাদ দিয়ে মাত্র 8টা পেল। Buffers: shared hit=1031 — table-এর সব 1031টা page (প্রতিটা 8 KB) ছুঁতে হয়েছে।

index সহ~10টা page
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX          -- Time: 62 ms

  Recheck Cond: (customer_id = 4242)
  Heap Blocks: exact=8
  Buffers: shared hit=8 read=2
  ->  Bitmap Index Scan on orders_customer_id_idx

এবার index-এর 2টা page পড়ে 8টা row-এর ঠিকানা পেল, তারপর heap-এর ঠিক সেই 8টা page পড়ল — মোট 10টা page, 1031-এর বদলে। সময় 4.7 ms থেকে 0.04 ms — ~100 গুণ দ্রুত। Table যত বড় হবে, পার্থক্য তত বাড়বে, কারণ Seq Scan বাড়ে row-এর সাথে সমানুপাতে (O(n)), আর B-tree search বাড়ে log(n) হারে।

Index-এর দাম — free lunch নেই

একই 100,000 row insert — 0 বনাম 5টা index

CREATE TABLE t_5idx  (LIKE t_noidx);   -- একই column
CREATE INDEX ON t_5idx (id);     CREATE INDEX ON t_5idx (customer_id);
CREATE INDEX ON t_5idx (email);  CREATE INDEX ON t_5idx (amount);

Time: 141.858 ms

       pg_size_pretty(pg_indexes_size('t_5idx'))   AS idx;
  heap   |   idx
 7480 kB | 9496 kB     ← index গুলো table-এর চেয়েও বড়!
খরচগুলো কোথায়:
  • Write amplification: একটা INSERT মানে heap-এ একটা লেখা + প্রতিটা index-এ একটা করে লেখা (সঠিক sorted জায়গা খুঁজে, দরকারে page split করে)। 5টা index = একটা row-এ 6 জায়গায় লেখা, আর প্রতিটা লেখা WAL-এও যায়।
  • UPDATE: PostgreSQL UPDATE-এ নতুন row version লেখে, তার ctid নতুন — তাই সাধারণত সব index-এ নতুন entry লাগে। ব্যতিক্রম HOT update: কোনো indexed column বদলায়নি আর একই page-এ জায়গা আছে, তাহলে index ছোঁয়াই লাগে না। বেশি index = HOT কম সম্ভব।
  • DELETE: index entry সাথে সাথে মোছে না; পরে VACUUM dead entry পরিষ্কার করে। ততক্ষণ index ফুলে থাকে (bloat)।
  • Disk ও RAM: index-ও disk-এ জায়গা নেয়, আর shared_buffers-এ cache হওয়ার জন্য table-এর page-এর সাথে প্রতিযোগিতা করে।
  • Planner-এর কাজ: প্রতিটা query-তে planner সব প্রাসঙ্গিক index বিবেচনা করে — অপ্রয়োজনীয় index planning time বাড়ায়।

তাই নিয়ম: যে query আসলে চলে, তার জন্য index — "প্রতিটা column-এ একটা" না।

2Disk-এ table আর index কোথায় থাকে

প্রতিটা table আর প্রতিটা index = disk-এ আলাদা file

PostgreSQL-এর সব data থাকে একটা folder-এ — data directory ($PGDATA)। তার ভেতর base/<database oid>/ folder-এ প্রতিটা table আর প্রতিটা index একটা করে আলাদা file, নাম একটা সংখ্যা (relfilenode)। প্রতিটা file 8 KB page-এ ভাগ করা — disk থেকে পড়া, RAM-এ রাখা, সব কিছুর একক এই page।

একটা index lookup: ① planner users_pkey দিয়ে Index Scan ঠিক করে → ② B-tree-র page গুলো (meta → root → … → leaf) shared_buffers থেকে পড়ে; না থাকলে disk-এর file 16392 থেকে এনে cache-এ রাখে → ③ leaf-এ 63 পেয়ে তার পাশের ctid (0,5) = heap-এর page 0, slot 5 → ④ heap file 16385-এর page 0 (cache-এ না থাকলে disk থেকে) পড়ে slot 5-এর row ফেরত দেয়। W — যেকোনো লেখা আগে WAL-এ যায়, COMMIT-এ WAL fsync হয়; table/index page পরে checkpoint-এ disk-এ লেখা হয়।

Index file 16384 byte = 2 page: page 0 হলো meta page (root কোথায় লেখা), page 1-এ 15টা key — এত কম যে একটা page-ই root আর leaf দুটোই। _fsm (কোন page-এ কত খালি জায়গা) আর _vm (কোন page-এর সব row সবার কাছে visible) হলো fork — প্রথম VACUUM-এর পর তৈরি হয়েছে; আগে শুধু main file ছিল। pg_relation_size একটা relation, pg_indexes_size একটা table-এর সব index মিলিয়ে, pg_total_relation_size সব মিলিয়ে।

এটা disk-এ index page-এর আসল ভেতরটা। data হলো key — hex-এ, little-endian: 3f = 63, 05 = 5। Key গুলো sorted (5, 8, 11, 17 …) আর প্রতিটার পাশে heap-এর ctid। Index-এ 63 পেলেই জানা যায় row-টা (0,5)-এ।

তাহলে index lookup-এর পুরো ধাপ:
  1. Index-এর meta page → root page → (মাঝের page) → leaf page পড়া। বড় table-এও এটা সাধারণত 3–4টা page।
  2. Leaf-এ key খুঁজে ctid নেওয়া।
  3. ctid-এর page নম্বর ধরে heap page পড়া, slot থেকে row বের করা।
  4. Row-টা এই transaction-এর কাছে visible কিনা (MVCC: xmin/xmax) চেক করা — এই তথ্য শুধু heap-এ থাকে, index-এ না।

৩-৪ নম্বর ধাপ এড়ানো যায় যদি দরকারি সব column index-এই থাকে আর visibility map বলে ওই heap page-এর সব row সবার কাছে visible — তখন হয় Index Only Scan (section 7-এ প্রমাণ)।

3Index তৈরি, দেখা, মোছা

CREATE INDEX name ON table [USING method] (columns) [WHERE …]

Syntax ছোট, কিন্তু প্রতিটা অংশের মানে আছে। নিচের প্রতিটা command orders আর users table-এ চালানো।

সাধারণ index
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX

USING না লিখলে B-tree। নামের convention: <table>_<column>_idx — না দিলে PostgreSQL নিজে orders_customer_id_idx জাতীয় নাম বানায়। সাধারণ CREATE INDEX চলাকালীন table-এ SHARE lock থাকে: SELECT চলবে, কিন্তু INSERT/UPDATE/DELETE অপেক্ষা করবে যতক্ষণ index বানানো শেষ না হয়। বড় production table-এ সেটা মিনিটের পর মিনিট লেখা বন্ধ।

UNIQUE index — duplicate ঠেকায়
CREATE UNIQUE INDEX users_name_city_uq ON users (name, city);
INSERT INTO users VALUES (100, 'Rahim', 'rahim2@mail.com', 'Dhaka');
ERROR:  duplicate key value violates unique constraint "users_name_city_uq"
DETAIL:  Key (name, city)=(Rahim, Dhaka) already exists.

Unique index দ্রুত খোঁজার সাথে একটা নিয়মও চাপায়: একই value দুবার ঢুকবে না। Insert-এর সময় B-tree-তে ঠিক জায়গায় গিয়ে আগে দেখে নেয় একই key আছে কিনা — তাই uniqueness check-ও O(log n)।

Multicolumn (composite) index — column-এর ক্রম গুরুত্বপূর্ণ

ফোনবুকের মতো: ফোনবুক সাজানো (পদবি, নাম) ক্রমে। "পদবি = Hossain" খোঁজা সহজ, "Hossain, Rafi" আরো সহজ। কিন্তু শুধু "নাম = Rafi" খুঁজতে পুরো বই দেখতে হবে — কারণ Rafi-রা সব পদবির নিচে ছড়ানো। Index (a, b) আগে a দিয়ে sorted, একই a-র ভেতরে b দিয়ে। এটাকে বলে leftmost prefix rule।

CREATE INDEX orders_cust_created_idx ON orders (customer_id, created_at);

Customer 4242-এর order গুলো index-এ created_at ক্রমে পাশাপাশি সাজানো। শেষ থেকে উল্টো দিকে (Backward) 5টা পড়লেই সবচেয়ে নতুন 5টা — কোনো sort নেই। B-tree-র leaf page গুলো দুই দিকেই linked বলে উল্টো দিকে হাঁটা যায়।

-- PostgreSQL 18-এ নতুন: B-tree skip scan
CREATE INDEX orders_status_created_idx ON orders (status, created_at);
EXPLAIN (ANALYZE, COSTS OFF) SELECT * FROM orders
WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02';
Index Scan using orders_status_created_idx on orders (actual rows=288.00)
  Index Cond: ((created_at >= …) AND (created_at < …))
  Index Searches: 9

প্রথম column status-এর মাত্র 4টা আলাদা value। PG 18 তখন প্রতিটা status-এর জন্য আলাদা করে index-এ নামে ("skip" করে) — Index Searches: 9 মানে index-এ 9 বার descend করেছে। কিন্তু customer_id-এর মতো 10,000 value-র column আগে থাকলে এটা লাভজনক না, তখন Seq Scan। Interview উত্তর: "সাধারণত leftmost prefix লাগে; PG 18+ low-cardinality leading column-এ skip scan করতে পারে।"

Column-এর ক্রম কীভাবে ঠিক করবে:
  • = দিয়ে filter হওয়া column আগে, range (>, BETWEEN) বা ORDER BY-এর column পরে — যেমন (customer_id, created_at)।
  • (a, b) থাকলে আলাদা (a) index সাধারণত বাড়তি। আমরা orders_customer_id_idx drop করার পরেও customer_id = 4242 composite index ব্যবহার করেছে।
  • শুধু index থেকে উত্তর দিতে চাইলে বাড়তি column INCLUDE করা যায়: CREATE INDEX ON orders (customer_id) INCLUDE (amount) — amount leaf-এ থাকে কিন্তু sort/search-এ অংশ নেয় না (covering index)।

4৩ ধরনের index

Primary · Secondary · Unique — আর composite

Textbook আর interview-এ index-কে সাধারণত এই তিন ভাগে ভাগ করা হয়। এটা ভূমিকা অনুযায়ী ভাগ — ভেতরের data structure (B-tree, Hash …) আলাদা প্রশ্ন, সেটা এই section-এর শেষে।

1 · Primary / clustered Primary index

Primary key-র উপর index। Table-এ একটাই। Classic সংজ্ঞায় data file নিজেই এই key অনুযায়ী sorted থাকে, তাই একে clustered index-ও বলে।

  • PostgreSQL-এ: PRIMARY KEY দিলে নিজে থেকে users_pkey (unique B-tree) বানায়।
  • কিন্তু PostgreSQL-এ table আসলে sorted থাকে না — নিচে দেখো।
2 · Secondary / non-clustered Secondary index

অন্য যেকোনো column-এ index (customer_id, email …)। যতগুলো দরকার বানানো যায়। Data file-এর ক্রমের সাথে কোনো সম্পর্ক নেই — index আলাদা sorted structure, row-কে pointer দিয়ে দেখায়।

  • Duplicate value থাকতে পারে (এক customer-এর অনেক order)।
  • প্রতিটা lookup-এ index → heap, দুই জায়গায় যেতে হয়।
3 · Unique Unique index

Secondary index + নিয়ম: একই value দুবার না। UNIQUE constraint বা CREATE UNIQUE INDEX।

  • NULL একাধিকবার থাকতে পারে (NULL ≠ NULL) — PG 15+-এ NULLS NOT DISTINCT দিলে একটাই।
  • PK = unique + NOT NULL।

Composite (multicolumn) index আলাদা "ধরন" না — উপরের যেকোনোটাই একাধিক column-এ হতে পারে: composite primary key PRIMARY KEY (order_id, product_id), composite secondary (customer_id, created_at), composite unique (name, city)। নিয়ম একটাই: leftmost prefix (section 3)।

PostgreSQL বনাম MySQL InnoDB / SQL Server:
  • PostgreSQL: table হলো heap — যেখানে খালি জায়গা, row সেখানে বসে। Primary key সহ সব index আলাদা file, সবার leaf-এ heap-এর ctid। এই অর্থে PostgreSQL-এর সব index-ই "secondary"।
  • CLUSTER একবারের জন্য heap-কে index-এর ক্রমে নতুন করে লেখে (ACCESS EXCLUSIVE lock — পড়াও বন্ধ)। পরের insert/update সেই ক্রম মানে না, উপরে id 1 গিয়ে বসল (0,15)-এ। \d people-এ index-এর পাশে শুধু CLUSTER চিহ্ন থাকে, পরে আবার চালানোর জন্য।
  • MySQL InnoDB: table নিজেই primary key-র B+ tree — leaf-এ পুরো row। এটাই আসল clustered index। Secondary index-এর leaf-এ ctid না, primary key-র value থাকে; তাই secondary lookup = secondary tree → PK tree, দুইবার tree নামা। এজন্য InnoDB-তে ছোট, ক্রমবর্ধমান PK (auto-increment) ভালো; random UUID PK দিলে page split বেশি।
  • SQL Server: একটা clustered index বেছে নেওয়া যায় (default PK); বাকিগুলো non-clustered।

মনে রাখার মতো:
  • PRIMARY KEY = UNIQUE + NOT NULL, table-এ একটাই। নাম হয় <table>_pkey। UNIQUE যতগুলো খুশি, নাম <table>_<column>_key।
  • UNIQUE column-এ NULL একাধিক থাকতে পারে — যাচাই করা: UNIQUE column-এ দুইটা NULL insert → INSERT 0 2; UNIQUE NULLS NOT DISTINCT দিলে দ্বিতীয়টায় ERROR: duplicate key … Key (email)=(null) already exists।
  • PK/UNIQUE-এর জন্য আলাদা করে আরেকটা index বানানো অপচয় — একই column-এ দুটো B-tree, দ্বিগুণ write।
  • Foreign key column-এ PostgreSQL নিজে index বানায় না (MySQL InnoDB বানায়)। orders.customer_id REFERENCES customers থাকলে join আর parent row delete দ্রুত করতে নিজে index দিতে হয় — বিস্তারিত Keys গাইডে।

6B-tree — গঠন আর কীভাবে তৈরি হয়

Sorted · balanced · প্রতিটা node = একটা disk page

B-tree হলো এমন একটা search tree যার প্রতিটা node-এ অনেকগুলো sorted key আর key-গুলোর মাঝখানে child pointer। Binary tree-তে প্রতি node-এ 1টা key আর 2টা child; B-tree-তে শত শত — কারণ একটা node = একটা 8 KB page, আর disk থেকে একটা page পড়তে যে সময়, তাতে 1টা key না পড়ে 300টা পড়াই লাভ।

B-tree-র নিয়ম (order m — প্রতি node-এ সর্বোচ্চ m টা child):
  • প্রতিটা node-এ key গুলো sorted; সর্বোচ্চ m − 1টা key।
  • Root ছাড়া প্রতিটা node অন্তত অর্ধেক ভরা (⌈m/2⌉ − 1 key)।
  • k টা key থাকলে k + 1 টা child। Key K-এর বামের subtree-তে সব < K, ডানে সব > K।
  • সব leaf একই গভীরতায় — tree সবসময় balanced। তাই যেকোনো key খুঁজতে একই সংখ্যক page: O(logm n)।
  • Tree নিচে না, উপরের দিকে বাড়ে: leaf ভরে গেলে split হয়, মাঝের key উপরে ওঠে; root split হলে নতুন root — তখনই height ১ বাড়ে।

Root page-এ 274টা entry, প্রতিটা একটা leaf page-এ যায়, প্রতি leaf-এ ~365টা key → 1 লাখ row মাত্র 2 তলায়। Fan-out ~300 ধরলে 3 তলায় ~2.7 কোটি, 4 তলায় ~800 কোটি row। এজন্যই বাস্তবে index lookup প্রায় সবসময় 3–4 page — আর root ও উপরের তলা সাধারণত RAM-এ থাকেই।

বোঝার সুবিধার জন্য খুব ছোট order: order 4 — প্রতি node-এ সর্বোচ্চ 3টা key, 4টা child (আসল PostgreSQL-এ শত শত)। Setup-এর users table-এর 15টা row যে ক্রমে insert হয়েছিল, সেই ক্রমে id গুলো ঢুকবে। প্রতিটা key-র নিচে ছোট করে লেখা heap-এর ctid — section 2-এর আসল ctid-ই। Classic B-tree-তে প্রতিটা node-এ (internal-ও) key-র সাথে data pointer থাকে। Overflow হলে (4টা key) node লাল হবে, তারপর split: মাঝের key উপরে উঠবে।

Insert algorithm, ধাপে ধাপে:
  1. Root থেকে শুরু করে প্রতিটা node-এ key-গুলোর সাথে তুলনা করে সঠিক child-এ নামো, যতক্ষণ না leaf-এ পৌঁছাও।
  2. Leaf-এ sorted জায়গায় key বসাও (সাথে ctid)।
  3. Leaf-এ key সংখ্যা max ছাড়ালে split: মাঝের key parent-এ উঠে যায়, বাম আর ডান অর্ধেক দুইটা আলাদা node হয়।
  4. Parent-ও overflow হলে একই ভাবে split, উপরের দিকে চলতে থাকে। Root split হলে নতুন root তৈরি — height +1। উপরের animation-এ id 5 (৪র্থ insert) আর id 80 (১৪তম) root split ঘটায়; id 80-তে split leaf থেকে root পর্যন্ত দুই তলা ছড়ায় (cascade)।

Search (WHERE id = 63): root [71] → 63 < 71, বামে → [17 | 42] → 63 ≥ 42, ডানে → leaf-এ 63, ctid (0,5) → heap-এর সবুজ row। 15টা row-এর বদলে 3টা node। Search 71 দিয়ে দেখো — classic B-tree-তে root-এই পাওয়া যায়, নিচে নামতে হয় না।

B+ tree — database আসলে যেটা ব্যবহার করে

B+ tree হলো B-tree-র একটা রূপ যেখানে দুইটা বড় পার্থক্য: (১) সব data pointer (ctid) শুধু leaf-এ — internal node শুধু রাস্তা দেখায় (routing key), (২) leaf গুলো একে অপরের সাথে linked — বাম থেকে ডানে একটা sorted list। তাই প্রতিটা key leaf-এ অবশ্যই থাকে; internal node-এর key হলো শুধু একটা "copy"।

users heap · page 0 — range scan-এ পাওয়া row গুলো সবুজ হবে
B+ tree-তে insert আর split:
  • Search সবসময় leaf পর্যন্ত যায় (internal-এ key মিললেও থামে না)। নিয়ম: key ≥ separator হলে ডানে।
  • Leaf split: 4টা key → বাম 2 + ডান 2। ডান leaf-এর প্রথম key-র copy parent-এ যায় — leaf-এও থেকে যায়, কারণ data শুধু leaf-এ। নতুন leaf-টা linked list-এ ঢোকে (বাম → নতুন → পুরনো ডান)।
  • Internal split: classic B-tree-র মতো — মাঝের key উপরে move হয় (copy না), কারণ internal key শুধু রাস্তা।
  • Range scan (BETWEEN 20 AND 60): একবার নেমে 20-এর leaf খুঁজে নাও, তারপর উপরে না উঠে sibling link ধরে ডানে হাঁটো যতক্ষণ key ≤ 60। Animation-এ সবুজ dashed arrow গুলো এই link।
Database কেন B+ tree নেয়:
  • বেশি fan-out, কম তলা: internal page-এ ctid/row রাখতে হয় না, শুধু key + child pointer — একই 8 KB-তে বেশি key, tree আরো চ্যাপ্টা, কম disk read।
  • Range আর ORDER BY: leaf chain ধরে sequential হাঁটা — BETWEEN, >, ORDER BY … LIMIT সব সস্তা। Classic B-tree-তে range-এর জন্য tree-তে উপরে-নিচে in-order traversal লাগত।
  • অনুমানযোগ্য খরচ: সব lookup একই সংখ্যক page — query planner-এর হিসাব সহজ।
  • PostgreSQL-এর nbtree হলো Lehman & Yao-র B-link tree: প্রতিটা page-এ (শুধু leaf না, প্রতিটা level-এ) ডান-sibling link আর একটা "high key"। Split চলাকালীন কোনো reader ভুল page-এ নামলে high key দেখে বোঝে আর ডানে সরে যায় — তাই পুরো tree lock না করেই অনেক session একসাথে পড়া-লেখা করতে পারে। Leaf-এ বাম link-ও আছে (Index Scan Backward)। এছাড়া PG 13+-এ duplicate key-র deduplication আর internal key-র suffix truncation।

7Query কীভাবে index ব্যবহার করে

EXPLAIN = planner-এর পরিকল্পনা · EXPLAIN ANALYZE = আসলে চালিয়ে দেখা

Index বানালেই query সেটা ব্যবহার করবে, এমন না। প্রতিটা query-তে planner statistics দেখে আন্দাজ করে কতগুলো row আসবে, তারপর প্রতিটা সম্ভাব্য পথের খরচ (cost) হিসাব করে সবচেয়ে সস্তাটা নেয়। EXPLAIN সেই plan দেখায়।

Plan পড়তে শেখো:
  • cost=4.37..41.54 — প্রথম row দেওয়ার আগের খরচ .. মোট খরচ। একক কাল্পনিক (একটা sequential page পড়া = 1.0)।
  • rows=10 — planner-এর আন্দাজ। actual … rows=8.00 — আসলে কত (শুধু ANALYZE-এ)। দুটো খুব আলাদা হলে statistics পুরনো।
  • Buffers: shared hit=8 read=2 — 8টা page RAM-এ পেয়েছে, 2টা disk/OS থেকে পড়েছে (BUFFERS PG 18-এ ANALYZE-এর সাথে default)।
  • Index Searches: 1 — PG 18-এ নতুন: index-এ কতবার নামতে হয়েছে।
  • সাবধান: EXPLAIN ANALYZE query সত্যিই চালায়। UPDATE/DELETE-এ BEGIN; EXPLAIN ANALYZE …; ROLLBACK;।

Index Scan: index-এর leaf ধরে হাঁটে, প্রতিটা entry-র ctid দিয়ে সাথে সাথে heap থেকে row আনে। id < 200-এ 199 row মাত্র 5 page — কারণ id ক্রমেই row গুলো heap-এ পাশাপাশি লেখা (correlation = 1)।

Bitmap scan দুই ধাপে: আগে index থেকে সব মিলে যাওয়া ctid নিয়ে RAM-এ একটা page-এর bitmap বানায়, তারপর heap page গুলো disk-এর ক্রমে, প্রতিটা একবারই পড়ে। 1947 row ছড়ানো 889টা page-এ — Index Scan হলে একই page বারবার, এলোমেলো ক্রমে পড়ত। Bitmap খুব বড় হলে শুধু page মনে রাখে (lossy), তাই Recheck Cond দিয়ে আবার মিলিয়ে নেয়। দুইটা index-এর bitmap AND/OR করেও জোড়া লাগাতে পারে।

Planner-এর মোটামুটি নিয়ম (selectivity = কত % row আসবে):
  • খুব কম row (1–কয়েকটা) → Index Scan; দরকারি সব column index-এ + page all-visible → Index Only Scan।
  • মাঝারি (কয়েকশো–কয়েক হাজার, অনেক page-এ ছড়ানো) → Bitmap Heap Scan।
  • অনেক row (মোটামুটি ১০–২০%-এর বেশি, data-র উপর নির্ভর) → Seq Scan। পুরো table sequential পড়া, অর্ধেক table random পড়ার চেয়ে সস্তা — random_page_cost = 4 বনাম seq_page_cost = 1।

Index থাকলেও planner যখন নেয় না

① ছোট table
VACUUM ANALYZE users;            -- 15 row, 1 page

পুরো table একটাই page। Index দিয়ে গেলে index-এর 2 page + heap-এর 1 page = 3 page; সরাসরি পড়লে 1 page। Seq Scan-ই সস্তা — এটা bug না। (ANALYZE-এর আগে relpages = 0 ছিল, তখন planner অনুমান করে Index Scan নিয়েছিল — statistics কত গুরুত্বপূর্ণ।)

④ LIKE — শুরুতে wildcard, আর collation

  Index Cond: ((email ~>=~ 'user4242'::text) AND (email ~<~ 'user4243'::text))

-- '%…' এর জন্য: pg_trgm extension + GIN
CREATE EXTENSION pg_trgm;
CREATE INDEX orders_email_trgm ON orders USING gin (email gin_trgm_ops);
EXPLAIN SELECT * FROM orders WHERE email LIKE '%4242@mail.com';
Bitmap Heap Scan on orders
  ->  Bitmap Index Scan on orders_email_trgm

শুরুতে % মানে "যেকোনো কিছু দিয়ে শুরু" — sorted list-এ কোথা থেকে খুঁজবে জানা নেই। ফোনবুকে "নামের শেষে -uddin" খোঁজার মতো। আর 'user4242%'-কে planner >= 'user4242' AND < 'user4243' range-এ বদলায় — কিন্তু en_US collation-এর sort ক্রম byte ক্রম না, তাই সাধারণ index দিয়ে এটা নিরাপদ না। text_pattern_ops byte ক্রমে sort করা index বানায় (বা database/column C collation-এ হলে সাধারণ index-ই চলে)।

⑤ Type mismatch — implicit cast column-এর উপর পড়ে

  Filter: ((customer_id)::text = '4242'::text)

500.0 একটা numeric। Bigint আর numeric তুলনা করতে PostgreSQL column-কে numeric-এ cast করে — ঠিক ③-এর মতো, column-এর উপর function, index অচল। ORM/driver যখন parameter ভুল type-এ পাঠায় (যেমন সব কিছু string বা decimal হিসেবে), তখন এটাই হয়। Plan-এ (id)::numeric জাতীয় cast দেখলেই সন্দেহ করবে।

8Hash index

hash(value) → bucket → ctid · শুধু “=”

Hash index প্রতিটা value-কে একটা hash function দিয়ে 32-bit সংখ্যায় বদলায়, সেই সংখ্যা দিয়ে ঠিক করে কোন bucket-এ যাবে। Search-এ একই hash বের করে সরাসরি সেই bucket-এর page — tree-তে নামার দরকার নেই। কিন্তু hash value-র কোনো ক্রম নেই, তাই শুধু সমান (=) খোঁজা সম্ভব।

CREATE TABLE sessions (
  token      text NOT NULL,        -- 32-অক্ষরের md5 token
  user_id    int  NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO sessions (token, user_id)
SELECT md5(g::text), (g % 5000) + 1 FROM generate_series(1, 100000) g;

Hash index value-টা নিজে রাখে না, শুধু 4-byte hash code + ctid। তাই লম্বা key-তে B-tree-র চেয়ে ছোট (32-অক্ষরের token-এ 4.1 MB বনাম 5.8 MB)। আবার এজন্যই heap-এ গিয়ে আসল value মিলিয়ে দেখতে হয় (দুই value-র hash একই হতে পারে — collision)।

ভেতরে কীভাবে কাজ করে:
  • bucket = hash(token) & mask — এখানে 512টা bucket। প্রতিটা bucket এক বা একাধিক 8 KB page; ভরে গেলে overflow page chain-এ যোগ হয়।
  • ffactor = 307 — প্রতি bucket-এ গড়ে যত tuple রাখার লক্ষ্য। Row বাড়লে একবারে সব না, একটা একটা bucket split করে বাড়ে (linear hashing), যাতে বড় হঠাৎ বিরতি না হয়।
  • Search: hash বের করো → bucket page → সেখানে hash code মেলাও → ctid → heap-এ value recheck।
  • PostgreSQL 10-এর আগে hash index WAL-logged ছিল না — crash-এর পর নষ্ট হতে পারত, replication-এ যেত না। পুরনো ব্লগে "hash index ব্যবহার কোরো না" এই কারণে। 10+-এ নিরাপদ।
সীমাবদ্ধতা (PG 18-এ যাচাই করা):
  • শুধু =; < > BETWEEN LIKE না, ORDER BY-এ কাজে লাগে না।
  • Unique হয় না: ERROR: access method "hash" does not support unique indexes
  • Multicolumn হয় না: ERROR: access method "hash" does not support multicolumn indexes
  • Index Only Scan হয় না (value রাখে না)।
  • কখন নেবে: খুব বড় table, লম্বা key (UUID-string, token, URL), আর query শুধুই =। বাকি প্রায় সব ক্ষেত্রে B-tree-ই যথেষ্ট আর বহুমুখী — বাস্তবে hash index কমই দেখা যায়।

9Partial index

CREATE INDEX … WHERE condition — শুধু যে row-গুলো দরকার

Partial index-এ WHERE দিয়ে বলে দাও কোন row index-এ ঢুকবে। বাকি row index-এ থাকেই না — তাই index অনেক ছোট, RAM-এ সহজে থাকে, আর যেসব row-এ condition মেলে না তাদের INSERT/UPDATE-এ index ছোঁয়াই লাগে না।

বাস্তবে: Daraz-এর মতো e-commerce-এ admin panel সারাদিন দেখে "কোন order এখনো pending, পুরনোটা আগে"। 1 লাখ order-এর মাত্র 2% pending। বাকি 98% delivered/shipped order-এর জন্য index রাখা অপচয় — সেগুলো এই query কখনো চায় না।

CREATE INDEX orders_status_full_idx ON orders (status, created_at);
CREATE INDEX orders_pending_idx     ON orders (created_at)
  WHERE status = 'pending';

প্রথম query-তে কোনো Index Cond-ও নেই — index-এর প্রতিটা entry-ই pending, আর সেগুলো created_at ক্রমে সাজানো; প্রথম 20টা পড়লেই উত্তর, Sort নেই। দ্বিতীয়টায় status column index-এ না থাকলেও Index Only Scan — কারণ index-এর সংজ্ঞাই বলে সব row pending।

Planner কখন partial index নিতে পারে:

Query-র WHERE থেকে যদি প্রমাণ করা যায় যে index-এর condition সত্য (query predicate ⟹ index predicate)। status = 'pending' ⟹ status = 'pending' ✓। status IN ('pending','shipped') থেকে সেটা প্রমাণ হয় না — shipped row index-এ নেই। $1 parameter-ওয়ালা generic plan-এ value-ই অজানা, তাই প্রমাণ করা যায় না। ORM-এ এই কারণে partial index "কাজ করছে না" মনে হয় — status-টা query-তে literal হিসেবে লেখো।

10GIN index

Generalized Inverted Index — element → কোন কোন row-এ আছে

B-tree প্রতিটা row-এর একটা value index করে। কিন্তু একটা row-এ যদি অনেকগুলো জিনিস থাকে — array-তে কয়েকটা tag, jsonb-তে কয়েকটা key-value, একটা লেখায় অনেক শব্দ — আর প্রশ্ন হয় "কোন row-এ 'watch' tag আছে?", তখন দরকার inverted index: প্রতিটা element-এর জন্য একটা entry, তার সাথে সেই element থাকা সব row-এর sorted list (posting list)। বইয়ের শেষের সূচিও আসলে inverted index — শব্দ → পাতার তালিকা।

products (heap) — প্রথম 8 row

row 1{laptop, sale}
row 2{tablet, sale}
row 3{watch, sale}
row 4{camera, sale}
row 5{phone, new}
row 6{laptop, new}
row 7{tablet, new}
row 8{watch, new}
→

GIN (tags) — key B-tree + posting list

camera4
laptop1, 6
new5, 6, 7, 8
phone5
sale1, 2, 3, 4
tablet2, 7
watch3, 8

tags @> '{watch,new}' = দুইটা list-এর intersection → row 8। আসলে list-এ row নম্বর না, ctid থাকে (sorted, compress করা)।

GIN-এর ভেতর:
  • Entry tree: সব আলাদা element (tag, jsonb key/value, শব্দ) একটা B-tree-তে sorted। প্রতিটা entry-র সাথে posting list (কম row হলে) বা posting tree (অনেক row হলে আলাদা B-tree) — ctid-গুলো sorted ও compress করা।
  • লেখা কেন ধীর: একটা row insert = তার প্রতিটা element-এর posting list-এ একটা করে যোগ। একটা লেখায় ৩০টা শব্দ থাকলে ৩০ জায়গায় লেখা।
  • fastupdate / pending list (default on): নতুন row-গুলো আগে একটা unsorted pending list-এ জমে (উপরে 20,000 tuple, 101 page)। পরে VACUUM/autovacuum, pending list gin_pending_list_limit (4 MB) ছাড়ালে, বা gin_clean_pending_list() ডাকলে একসাথে মূল tree-তে merge — bulk-এ করলে সস্তা। দাম: search-এর সময় pending list পুরোটা scan করতে হয়, আর মাঝে মাঝে কোনো এক INSERT হঠাৎ ধীর হয় (সেই flush করে)। WITH (fastupdate = off) দিলে প্রতিটা insert সরাসরি tree-তে।
  • শুধু Bitmap scan: GIN row-গুলো কোনো ক্রমে দিতে পারে না, Index Scan/ORDER BY হয় না — সব plan-এ Bitmap Index Scan খেয়াল করো। Unique-ও হয় না।
  • আকার: full-text index (6.4 MB) সবচেয়ে বড় — প্রতিটা লেখায় অনেক শব্দ। এই 20,000 row insert-এর পর products_attrs_gin 1200 kB থেকে বেড়ে 4760 kB হয়েছিল; REINDEX-এ আবার 1352 kB — ঘন ঘন লেখা হয় এমন GIN ফুলে ওঠে।
  • jsonb_path_ops: USING gin (attrs jsonb_path_ops) — শুধু @> সমর্থন করে, কিন্তু ছোট (এখানে 808 kB বনাম 1352 kB)। ? (key আছে কিনা) লাগলে default jsonb_ops।

  • Foreign key column — PostgreSQL নিজে দেয় না; join আর parent delete-এ লাগে।

QInterview-এ যা আসে

Clustered আর non-clustered index-এর পার্থক্য কী? PostgreSQL-এ clustered index আছে?

Clustered index-এ table-এর row-গুলো নিজেই index-এর ক্রমে রাখা থাকে (index-এর leaf-ই data), তাই table-এ একটাই হতে পারে — MySQL InnoDB-তে primary key। Non-clustered index আলাদা structure, leaf-এ row-এর ঠিকানা। PostgreSQL-এ table সবসময় unordered heap, সব index (PK সহ) non-clustered, leaf-এ ctid। CLUSTER command একবার heap-কে index ক্রমে সাজায়, কিন্তু পরের লেখায় সেই ক্রম রক্ষা হয় না।

Index থাকা সত্ত্বেও PostgreSQL Seq Scan করছে কেন?

সম্ভাব্য কারণ: (১) table ছোট, (২) query অনেক row ফেরত দেবে (low selectivity) — তখন sequential পড়াই সস্তা, (৩) column-এ function বা cast (lower(email), id = 500.0 → (id)::numeric), (৪) LIKE '%x' বা non-C collation-এ prefix LIKE, (৫) composite index-এর প্রথম column query-তে নেই, (৬) statistics পুরনো — ANALYZE চালাও, (৭) partial index-এর শর্ত query থেকে প্রমাণ হয় না। EXPLAIN ANALYZE-এ estimated বনাম actual rows মিলিয়ে দেখো।

B-tree আর B+ tree-র পার্থক্য কী? Database কেন B+ tree ব্যবহার করে?

B+ tree-তে data pointer শুধু leaf-এ, internal node শুধু routing key রাখে, আর leaf-গুলো linked list। ফলে internal page-এ বেশি key ধরে (বেশি fan-out, কম height, কম disk I/O), range query আর ORDER BY একবার নেমে leaf chain ধরে হাঁটলেই হয়, আর সব lookup সমান খরচের। PostgreSQL-এর nbtree হলো Lehman-Yao B-link tree — প্রতিটা level-এ right-link আর high key থাকায় split চলাকালীনও lock ছাড়া concurrent search চলে।

Composite index (a, b) থাকলে WHERE b = ? কি index ব্যবহার করবে?

সাধারণত না — index আগে a দিয়ে sorted, b-র মানগুলো সব a-র নিচে ছড়ানো (leftmost prefix rule)। WHERE a = ? আর WHERE a = ? AND b = ? ব্যবহার করবে। PostgreSQL 18-এ নতুন skip scan: a-র distinct value কম হলে planner প্রতিটা a-র জন্য আলাদা করে নেমে b খুঁজতে পারে (আমাদের (status, created_at) উদাহরণে Index Searches: 9)। Column ক্রম: equality column আগে, range/sort column পরে।

Index Only Scan কী? Heap Fetches শূন্য না হলে কী বুঝবে?

Query-র দরকারি সব column index-এ থাকলে PostgreSQL heap না পড়েই উত্তর দিতে পারে। কিন্তু row visible কিনা সেই তথ্য heap-এ, তাই visibility map দেখে — page "all-visible" হলে heap বাদ, না হলে heap-এ গিয়ে চেক (Heap Fetches)। Heap Fetches বেশি মানে সম্প্রতি অনেক UPDATE/DELETE হয়েছে আর VACUUM এখনো চলেনি। INCLUDE দিয়ে বাড়তি column যোগ করে covering index বানানো যায়।

Hash index কখন B-tree-র চেয়ে ভালো?

শুধু equality (=) query, লম্বা key (token, URL, UUID-string), বড় table — hash index শুধু 4-byte hash code রাখে বলে ছোট হয় (আমাদের উদাহরণে 4.1 MB বনাম 5.8 MB)। কিন্তু range, ORDER BY, unique, multicolumn, Index Only Scan কোনোটাই পারে না। তাই default উত্তর B-tree; hash একটা বিশেষ ক্ষেত্রের optimization।

Partial index কী, কখন দেবে? ORM-এ কাজ না করার কারণ?

CREATE INDEX … WHERE condition — শুধু শর্ত মেলা row index-এ। অসম data-তে (2% pending, শুধু active subscription, not-deleted user) index ছোট আর দ্রুত হয়; partial unique index দিয়ে শর্তসাপেক্ষ uniqueness ("প্রতি user-এর একটাই active subscription")। Planner তখনই নেয় যখন query-র WHERE থেকে index-এর WHERE প্রমাণ হয়। ORM যদি status = $1 parameter দিয়ে generic plan বানায়, value অজানা বলে partial index বাদ পড়ে — literal লেখো।

GIN index কী, write ধীর কেন?

Inverted index — প্রতিটা element (array item, jsonb key/value, শব্দ) থেকে সেই element থাকা row-গুলোর sorted list। jsonb @>, array @>/&&, full-text @@-এর জন্য। একটা row-এ অনেক element থাকলে insert-এ অনেক posting list হালনাগাদ লাগে — তাই ধীর; এজন্য fastupdate pending list-এ জমিয়ে পরে একসাথে merge করে। শুধু bitmap scan, unique হয় না।

বেশি index দিলে সমস্যা কী?

প্রতিটা INSERT/UPDATE/DELETE সব index-এ লেখে (আমাদের পরীক্ষায় 5টা index-এ insert প্রায় 10 গুণ ধীর, index-এর মোট আকার table-এর চেয়েও বড়), WAL বাড়ে, HOT update কমে, RAM-এ cache-এর জায়গা নিয়ে প্রতিযোগিতা, planning time বাড়ে। pg_stat_user_indexes.idx_scan = 0 থাকা index খুঁজে drop করো।
