Keys — কোন row কে, কীভাবে চিনবে

একটা table-এ হাজার হাজার row। তার মধ্যে ঠিক একটা row-কে আলাদা করে চেনার উপায়ই key — আর এক table থেকে আরেক table-কে জোড়ার সুতাও key। এখানে একটা university database দিয়ে সব রকম key একই data-র ওপর দেখানো হয়েছে। প্রতিটা DDL আর error PostgreSQL 18-এ চালিয়ে আসল output দেওয়া।

পুরো DDL — এক জায়গায়

CREATE TABLE departments (
  dept_id  int  PRIMARY KEY,
  code     text NOT NULL UNIQUE,                 -- alternate key
  name     text NOT NULL
);

CREATE TABLE students (
  student_id int  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- surrogate PK
  nid        text NOT NULL UNIQUE,               -- alternate key (natural)
  email      text NOT NULL UNIQUE,               -- alternate key (natural)
  phone      text UNIQUE,                        -- unique key, NULL চলে
  name       text NOT NULL,
  dept_id    int  REFERENCES departments(dept_id) ON DELETE SET NULL
);

CREATE TABLE courses (
  course_id  text PRIMARY KEY,                   -- natural PK
  title      text NOT NULL,
  dept_id    int  NOT NULL REFERENCES departments(dept_id),   -- NO ACTION (default)
  prereq_id  text REFERENCES courses(course_id)                -- self-referencing FK
);

CREATE TABLE enrollments (
  student_id int  REFERENCES students(student_id) ON DELETE CASCADE,
  course_id  text REFERENCES courses(course_id)  ON DELETE RESTRICT,
  semester   text,
  grade      text,
  PRIMARY KEY (student_id, course_id, semester)  -- composite PK
);

1Key-এর পরিবার

Super ⊇ Candidate ⊇ Primary

Key মানে এক বা একাধিক attribute-এর এমন একটা set, যার মান দেখে table-এর ঠিক একটা row চেনা যায়। সব key একই পরিবারের — বড় বৃত্তের ভেতরে ছোট বৃত্ত। নিচে students-এর 6টা column দিয়ে বানানো সম্ভাব্য 63টা column-set কোথায় পড়ে:

সব column-set2⁶ − 1 = 63টা
{name}{dept_id}{phone}{name, dept_id}… মোট 7টা key না
Super keysstudent_id / nid / email — এর অন্তত একটা আছে · 56টা
{email, name}{student_id, phone}{nid, email}{nid, name, dept_id}{all 6}… আরো 48টা
Candidate keysminimal — একটা column-ও বাদ দেওয়া যায় না · 3টা
Primary keyবাছাই করা
{student_id}
Alternate keysবাকি candidate
{nid}{email}
Alternate keys = Candidate keys − Primary key

কাটা দাগ দেওয়া column গুলো বাড়তি — ওগুলো ছাড়াও set-টা row চিনতে পারে। বাড়তি থাকলে super key, একদম না থাকলে candidate key।

2Super Key

Row চেনাতে পারলেই হলো — বাড়তি থাকুক না থাকুক

যে কোনো attribute-set যার মান দুইটা row-তে কখনো এক হবে না, সেটাই super key। {email} একটা super key, তাই {email, name}, {email, name, phone} — email থাকা প্রতিটা set-ই super key। পুরো row (সব column একসাথে) সবসময় একটা super key, কারণ relation-এ duplicate row থাকে না।

বাস্তবে: "সাদা শার্ট পরা, চশমা আছে, roll 17" — roll 17 বললেই চলত, বাকিগুলো বাড়তি তথ্য। তবু পুরো বর্ণনাটা দিয়েও মানুষটাকে চেনা যায় — এটাই super key।

নিজে চেষ্টা করো — কোনটা key?

students-এর কোন column গুলো নিলে প্রতিটা row আলাদা করে চেনা যায়? Tick দাও:

চেষ্টা করো:

Declared rule: student_id PK, nid ও email UNIQUE NOT NULL, phone UNIQUE (NULL চলে)। লাল row = নির্বাচিত column-এ একই মান।

Data দেখে key খোঁজার ফাঁদ

SELECT name, count(*) FROM students
GROUP BY name HAVING count(*) > 1;
 name  | count
-------+-------
 Rahim |     2       ← name key না, প্রমাণ

SELECT name, dept_id, count(*) FROM students
GROUP BY name, dept_id HAVING count(*) > 1;
(0 rows)             ← তাহলে {name, dept_id} key?
না! আজকের 5টা row-এ "Rahim, CSE" একজনই, কিন্তু কাল আরেক Rahim CSE-তে ভর্তি হতে পারে। Key হলো business rule — "এটা কখনো duplicate হবে না" — যেটা database-এ PRIMARY KEY/UNIQUE দিয়ে declare করা থাকে। Data দেখে শুধু বলা যায় কোনটা key না (একটা duplicate পেলেই), কোনটা key তা প্রমাণ করা যায় না।

3Candidate Key

Minimal super key — একটা column-ও বাড়তি নেই

যে super key থেকে কোনো একটা attribute সরালেই সেটা আর row চেনাতে পারে না, সেটাই candidate key। Primary key হওয়ার "প্রার্থী" — তাই নাম candidate। একটা table-এ একাধিক candidate key থাকতেই পারে।

Column-setSuper?Candidate?
{student_id}✓✓
{nid}✓✓
{email}✓✓
{email, name}✓✗ name বাড়তি
{phone}✗ NULL✗
{name, dept_id}✗ rule নেই✗
Candidate key-এর দুই শর্ত:
  • Uniqueness — দুইটা row-এ মান কখনো এক হবে না।
  • Minimality (irreducibility) — কোনো proper subset নিজে unique না।
  • Practically আরেকটা: NULL হবে না — যে মান নেই, তা দিয়ে কাউকে চেনা যায় না। তাই nullable phone candidate key না।
  • Composite candidate key-ও হয়: enrollments-এ {student_id, course_id, semester} — তিনটার কোনোটা বাদ দিলে duplicate সম্ভব।

4Primary Key

সব candidate-এর মধ্যে একজন — table-এর অফিসিয়াল পরিচয়

Candidate key গুলোর মধ্যে যেটাকে আমরা row-এর মূল পরিচয় হিসেবে বেছে নিই। PostgreSQL-এ PRIMARY KEY = UNIQUE + NOT NULL, আর প্রতি table-এ সর্বোচ্চ একটা। অন্য table-এর FK সাধারণত এটাকেই দেখায়।

কোনটা বাছবে: যেটা কখনো বদলায় না, ছোট, আর সবসময় থাকে। email বদলাতে পারে, nid ব্যক্তিগত তথ্য — তাই students-এ বানানো student_id PK, আর nid/email থাকল alternate key হয়ে।

PK ভাঙার চেষ্টা

INSERT INTO departments VALUES (10, 'MAT', 'Math');
ERROR:  duplicate key value violates unique constraint "departments_pkey"
DETAIL:  Key (dept_id)=(10) already exists.

INSERT INTO departments VALUES (NULL, 'MAT', 'Math');
ERROR:  null value in column "dept_id" of relation "departments" violates not-null constraint
DETAIL:  Failing row contains (null, MAT, Math).
-- দ্বিতীয় PK? না।
ALTER TABLE students ADD PRIMARY KEY (nid);
ERROR:  multiple primary keys for table "students" are not allowed

-- IDENTITY ALWAYS: হাতে id দেওয়া যায় না
INSERT INTO students (student_id, nid, email, name)
VALUES (1, '111', 'x@uni.edu', 'X');
ERROR:  cannot insert a non-DEFAULT value into column "student_id"
DETAIL:  Column "student_id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
PostgreSQL কীভাবে করে:
  • PRIMARY KEY দিলেই PostgreSQL নিজে থেকে students_pkey নামে একটা unique B-tree index বানায়। Insert/update-এ duplicate খোঁজা হয় এই index-এ — পুরো table scan করতে হয় না।
  • PK column গুলো automatically NOT NULL হয়ে যায় (PostgreSQL 18-এ pg_constraint-এ এগুলো আলাদা NOT NULL constraint হিসেবেও দেখা যায়)।
  • PK ছাড়াও table বানানো যায়, কিন্তু তখন duplicate row ঠেকানোর কিছু থাকে না, আর logical replication-এ UPDATE/DELETE-এর জন্য replica identity লাগে — practically প্রতিটা table-এ PK রাখো।

5Alternate (Secondary) Key

PK হয়নি এমন candidate key

students-এর candidate key তিনটা — student_id, nid, email। একটা PK হলো, বাকি দুইটা alternate key। এগুলোকে ভুলে গেলে চলবে না: UNIQUE NOT NULL দিয়ে declare না করলে একই NID দিয়ে দুইজন ছাত্র ঢুকে যাবে — surrogate PK তো প্রতিবার নতুন নম্বর দেবে।

INSERT INTO students (nid, email, name) VALUES ('1998123456701', 'new@uni.edu', 'New');
ERROR:  duplicate key value violates unique constraint "students_nid_key"
DETAIL:  Key (nid)=(1998123456701) already exists.

INSERT INTO students (nid, email, name) VALUES ('2002000000006', 'rahim@uni.edu', 'New');
ERROR:  duplicate key value violates unique constraint "students_email_key"
DETAIL:  Key (email)=(rahim@uni.edu) already exists.

INSERT INTO students (nid, email, name) VALUES ('2002000000007', NULL, 'New');
ERROR:  null value in column "email" of relation "students" violates not-null constraint
DETAIL:  Failing row contains (8, 2002000000007, null, null, New, null).
-- student_id 8?  আগের দুইটা fail হওয়া INSERT 6 আর 7 খরচ করে ফেলেছে — নিচে "gap" দেখো

"Secondary key" নামটা কেউ কেউ non-unique search column (যেটায় শুধু index আছে) বোঝাতেও ব্যবহার করে। Interview-এ বললে স্পষ্ট করো: alternate key = unique candidate key যেটা PK না।

6Composite / Compound Key

একা কেউ পারে না, মিলে পারে

যখন কোনো একটা column একা row চেনাতে পারে না, একাধিক column মিলে key হয়। enrollments-এ Karim (2) CSE101 দুবার নিয়েছে — Spring আর Fall-এ। তাই (student_id, course_id) যথেষ্ট না, semester-ও লাগবে।

PRIMARY KEY (student_id, course_id, semester)

INSERT INTO enrollments VALUES (2, 'CSE101', 'Fall-2025', 'B');
ERROR:  duplicate key value violates unique constraint "enrollments_pkey"
DETAIL:  Key (student_id, course_id, semester)=(2, CSE101, Fall-2025) already exists.

INSERT INTO enrollments VALUES (2, 'CSE101', NULL, 'B');
ERROR:  null value in column "semester" of relation "enrollments" violates not-null constraint
DETAIL:  Failing row contains (2, CSE101, null, B).

INSERT INTO enrollments VALUES (2, 'CSE201', 'Spring-2026', NULL);
INSERT 0 1   -- একটা অংশ আলাদা হলেই নতুন key
মনে রাখো:
  • Composite PK-ও একটাই PK — শুধু তার column একাধিক। প্রতিটা অংশ NOT NULL।
  • Column order গুরুত্বপূর্ণ। Index হয় (student_id, course_id, semester) ক্রমে — WHERE student_id = … এই index ব্যবহার করতে পারে, কিন্তু শুধু WHERE course_id = … পারে না (leftmost prefix rule)। বিস্তারিত: Indexing গাইড।
  • Compound key — অনেক বইয়ে composite-এরই আরেক নাম; কিছু বইয়ে সেই composite key যার প্রতিটা অংশ নিজেই একটা FK (যেমন junction table-এ student_id + course_id)।
  • FK যদি composite PK-কে দেখায়, FK-ও composite হবে — সব column নিয়ে।

7Unique Key

Duplicate না — কিন্তু "নেই" (NULL) হতে পারে

UNIQUE constraint থাকা column। PK-র সাথে পার্থক্য: NULL চলে, আর একটা table-এ যত খুশি থাকতে পারে। SQL-এ NULL = NULL সত্য না (unknown), তাই default-এ অনেকগুলো NULL একসাথে থাকতে পারে। phone ঠিক এরকম — সবার phone নাও থাকতে পারে, কিন্তু যার আছে, তা অন্য কারো সাথে মিলবে না।

INSERT INTO students (nid, email, phone, name)
VALUES ('2002000000008', 'sakib@uni.edu', NULL, 'Sakib');
INSERT 0 1   -- Nusrat-এরও NULL, তবু চলল

INSERT INTO students (nid, email, phone, name)
VALUES ('2002000000009', 'mitu@uni.edu', '01711000001', 'Mitu');
ERROR:  duplicate key value violates unique constraint "students_phone_key"
DETAIL:  Key (phone)=(01711000001) already exists.

SELECT student_id, name, phone FROM students WHERE phone IS NULL;
 student_id |  name  | phone
------------+--------+-------
          3 | Nusrat |
          9 | Sakib  |
-- PostgreSQL 15+: NULL-ও একটার বেশি না
CREATE TABLE t_phone (phone text UNIQUE NULLS NOT DISTINCT);
INSERT INTO t_phone VALUES (NULL);
INSERT 0 1
INSERT INTO t_phone VALUES (NULL);
ERROR:  duplicate key value violates unique constraint "t_phone_phone_key"
DETAIL:  Key (phone)=(null) already exists.

-- একাধিক column মিলে unique-ও হয়
-- UNIQUE (dept_id, roll_no)
Unique key vs candidate key: UNIQUE NOT NULL হলে সেটা candidate key (আমাদের nid, email — alternate key)। শুধু UNIQUE (nullable) হলে row চেনার নিশ্চয়তা নেই — Nusrat-কে phone দিয়ে খুঁজে পাবে না। PostgreSQL দুই ক্ষেত্রেই students_phone_key-এর মতো একটা unique B-tree index বানায়।

8Foreign Key

"এই মান ওই table-এ থাকতেই হবে"

এক table-এর column যেটা অন্য (বা একই) table-এর PK বা UNIQUE column-কে দেখায়। এটাই referential integrity: enrollment-এ এমন student থাকতে পারবে না যে students table-এ নেই। যে table দেখায় সেটা child / referencing, যাকে দেখায় সেটা parent / referenced।

দাগের এক মাথায় খাড়া দাগ = "1" (parent), অন্য মাথায় কাকের পা = "N" (child)। দাগের পাশের লেখা = সেই FK-এর ON DELETE নিয়ম।

FK violation — insert-এ আর delete-এ

child-এ এমন মান যা parent-এ নেইinsert block
INSERT INTO enrollments VALUES (99, 'CSE101', 'Spring-2026', NULL);
ERROR:  insert or update on table "enrollments" violates foreign key constraint "enrollments_student_id_fkey"
DETAIL:  Key (student_id)=(99) is not present in table "students".

INSERT INTO enrollments VALUES (1, 'MAT999', 'Spring-2026', NULL);
ERROR:  insert or update on table "enrollments" violates foreign key constraint "enrollments_course_id_fkey"
DETAIL:  Key (course_id)=(MAT999) is not present in table "courses".
parent মুছলে child অনাথ হবেdelete block
-- ON DELETE RESTRICT
DELETE FROM courses WHERE course_id = 'CSE301';
ERROR:  update or delete on table "courses" violates RESTRICT setting of foreign key constraint "enrollments_course_id_fkey" on table "enrollments"
DETAIL:  Key (course_id)=(CSE301) is referenced from table "enrollments".

-- কিছু না লিখলে = NO ACTION
DELETE FROM departments WHERE dept_id = 20;
ERROR:  update or delete on table "departments" violates foreign key constraint "courses_dept_id_fkey" on table "courses"
DETAIL:  Key (dept_id)=(20) is still referenced from table "courses".

ON DELETE — parent মুছলে child-এর কী হবে

CASCADE — student গেলে তার enrollment-ও যাবে
SELECT count(*) FROM enrollments WHERE student_id = 1;
 count
-------
     2
DELETE FROM students WHERE student_id = 1;
DELETE 1
SELECT count(*) FROM enrollments WHERE student_id = 1;
 count
-------

9Natural Key vs Surrogate Key

বাস্তব দুনিয়ার মান, নাকি database-এর বানানো নম্বর?

Natural key — data-র নিজের মধ্যেই থাকা অর্থবহ unique মান: NID, email, ISBN, course_id = 'CSE101'। Surrogate key — কোনো business অর্থ নেই, শুধু row চেনার জন্য database যে মান বানায়: student_id = 1, 2, 3… বা UUID। আমাদের schema দুটোই দেখায়: students-এ surrogate, courses-এ natural।

Natural key-এর ঝামেলা: email বদলায়, NID-তে ভুল থাকে, নিয়ম বদলায় (ধরো NID 10 থেকে 17 digit)। PK বদলালে প্রতিটা FK table-এ বদলাতে হয়। আর NID-কে PK বানালে ব্যক্তিগত তথ্য প্রতিটা child table, log, URL-এ ছড়িয়ে পড়ে।

Surrogate key-এর ঝামেলা: নিজে কোনো duplicate ঠেকায় না — একই Rahim দুবার insert হবে id 1 আর id 6 নিয়ে। তাই surrogate PK-র পাশাপাশি natural key-তে UNIQUE রাখতেই হবে। আর join ছাড়া id দেখে কিছু বোঝা যায় না।

10Partial Key — weak entity-র discriminator

নিজে একা অর্থহীন, মালিকের সাথে মিলে key

Weak entity হলো যার নিজের কোনো পূর্ণ key নেই — অন্য একটা owner entity-র ওপর নির্ভর করে বাঁচে। Course-এর section: "Section 1" বললে বোঝা যায় না কোন course-এর। section_no হলো partial key (discriminator) — owner-এর PK-র সাথে মিলে পুরো key হয়। ER diagram-এ weak entity দুই-দাগের বাক্স, partial key-র নিচে dashed দাগ।

CREATE TABLE sections (
  course_id  text REFERENCES courses(course_id) ON DELETE CASCADE,
  section_no int,                       -- partial key
  room       text,
  PRIMARY KEY (course_id, section_no)   -- owner PK + discriminator
);

11Prime vs Non-prime Attribute

Normalization-এ ঢোকার দরজা

যে attribute অন্তত একটা candidate key-র অংশ, সেটা prime। বাকিগুলো non-prime। শুধু PK না — যে কোনো candidate key ধরে হিসাব হয়।

কেন জানা দরকার — normal form গুলো এই ভাগ দিয়েই লেখা:
  • 2NF: কোনো non-prime attribute candidate key-র অংশের ওপর নির্ভর করবে না। enrollments-এ course_title রাখলে সেটা শুধু course_id-এর ওপর নির্ভর করে → partial dependency → 2NF ভাঙে।
  • 3NF: non-prime আরেক non-prime-এর ওপর নির্ভর করবে না। students-এ dept_name রাখলে student_id → dept_id → dept_name → transitive।
  • BCNF: প্রতিটা determinant-কে super key হতে হবে — prime attribute-এর জন্যও কোনো ছাড় নেই।

12PostgreSQL-এর ভেতরে — key মানেই index?

PK/UNIQUE → automatic index · FK → নিজে বানাতে হবে

Uniqueness check করতে PostgreSQL প্রতিটা PRIMARY KEY আর UNIQUE-এর জন্য নিজে একটা unique B-tree index বানায়। কিন্তু FOREIGN KEY-এর referencing (child) column-এ কোনো index বানায় না — parent-এর দিকে তো PK index আছেই, child-এর দিকটা তোমার দায়িত্ব।

-- কোন FK-এর child column-এ index নেই?
SELECT c.conrelid::regclass AS table_name, c.conname AS fk_name
FROM   pg_constraint c
WHERE  c.contype = 'f'
AND    NOT EXISTS (
         SELECT 1 FROM pg_index i
         WHERE  i.indrelid = c.conrelid
         AND    (i.indkey::int2[])[0:cardinality(c.conkey) - 1] @> c.conkey)
ORDER  BY 1, 2;

Index না থাকলে কী হয় — 10 লাখ row-এ মাপা

Parent row মুছলে (বা তার key বদলালে) PostgreSQL-কে child table-এ খুঁজতে হয় "কেউ কি এখনো একে দেখাচ্ছে?"। FK আসলে internal system trigger দিয়ে চলে — প্রতিটা মুছে ফেলা parent row-এর জন্য child-এ একটা query। Index না থাকলে প্রতিবার পুরো child table scan।

QInterview-এ যা আসে

Primary key আর Unique key-এর পার্থক্য কী?

PK = UNIQUE + NOT NULL, প্রতি table-এ একটাই, আর row-এর অফিসিয়াল পরিচয় (FK সাধারণত এটাকেই দেখায়)। UNIQUE key-তে NULL চলে (PostgreSQL-এ default-এ একাধিক NULL), আর যত খুশি থাকতে পারে। দুটোই PostgreSQL-এ unique B-tree index বানায়। (কিছু DB-তে — যেমন SQL Server, MySQL InnoDB — PK clustered index হয়; PostgreSQL-এ table সবসময় heap, PK আর দশটা unique index-এর মতোই।)

একটা table-এ কি একাধিক primary key থাকতে পারে?

না — multiple primary keys for table "students" are not allowed। তবে একটা PK-তে একাধিক column থাকতে পারে (composite), আর candidate key / UNIQUE constraint যত খুশি রাখা যায়।

Foreign key কি NULL হতে পারে? Duplicate?

দুটোই পারে। NULL মানে "এখনো কোনো parent নেই" — FK check হয় না। NOT NULL দিলে বাধ্যতামূলক সম্পর্ক। Duplicate তো স্বাভাবিক — অনেক enrollment একই course-কে দেখায় (one-to-many)। FK-তে UNIQUE দিলে সম্পর্কটা one-to-one হয়ে যায়।

Primary key কি composite হতে পারে? কখন ব্যবহার করবে?

হ্যাঁ — PRIMARY KEY (student_id, course_id, semester)। Junction table (many-to-many) আর weak entity-তে স্বাভাবিক। খারাপ দিক: যে table এটাকে FK দিয়ে দেখাবে তাকেও সব column রাখতে হয়। তখন অনেকে surrogate id PK নিয়ে composite-টাকে UNIQUE রাখে।

Super key আর candidate key-এর পার্থক্য কী?

প্রতিটা candidate key একটা super key, কিন্তু উল্টোটা না। Super key-তে বাড়তি attribute থাকতে পারে ({email, name}); candidate key minimal — কোনো attribute সরালেই uniqueness চলে যায় ({email})। n attribute-এর table-এ super key অনেক, candidate key হাতে গোনা।

Surrogate key না natural key — কোনটা ভালো?

সাধারণত surrogate PK (GENERATED ALWAYS AS IDENTITY, distributed হলে UUIDv7) — ছোট, কখনো বদলায় না, PII ছড়ায় না। কিন্তু natural key-কে UNIQUE NOT NULL হিসেবে রাখতেই হবে, নইলে একই মানুষ দুবার ঢুকবে। সত্যি স্থির ও ছোট natural key (country code, currency code) হলে সেটাই PK হতে পারে।

PostgreSQL কি foreign key-তে automatically index বানায়?

না। PK আর UNIQUE-এ বানায় (uniqueness check-এর জন্য লাগে), কিন্তু FK-র child column-এ না। Index না থাকলে parent delete/update-এ প্রতিটা row-এর জন্য child table-এ seq scan হয় — উপরের মাপে 52.6 s বনাম 18 ms। MySQL InnoDB নিজেই বানায়।

FK কি primary key ছাড়া অন্য column-কে দেখাতে পারে?

পারে, যদি সেই column-এ PK বা UNIQUE constraint থাকে (যেমন REFERENCES students(email))। না থাকলে: there is no unique constraint matching given keys for referenced table — কারণ parent-এ একাধিক match থাকলে "কোনটাকে দেখাচ্ছি" অর্থহীন।
