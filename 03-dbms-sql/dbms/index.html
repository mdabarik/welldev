Idempotency — একবার বা দশবার, ফল একই

bKash-এ "Pay" দুবার চাপা পড়ল, কিংবা network timeout হয়ে app নিজেই আবার request পাঠাল — টাকা কিন্তু কাটতে হবে একবারই। কোন SQL নিজে থেকেই idempotent, কোনটা না, আর PostgreSQL দিয়ে কীভাবে retry-কে নিরাপদ করা যায় — idempotency key, UNIQUE constraint, conditional update। প্রতিটা উদাহরণ PostgreSQL 18-এ চালিয়ে আসল output দেওয়া।

1Idempotency কী

একই কাজ একবার করো বা N বার — system-এর অবস্থা একই

কোনো operation idempotent হলে সেটা একবার চালানো আর পরপর অনেকবার চালানোর ফল (system-এর state) হুবহু এক। গণিতের ভাষায় f(f(x)) = f(x) — যেমন abs(abs(-5)) = abs(-5) = 5। লিফটের "5" button দশবার চাপলেও লিফট 5 তলাতেই যায়; কিন্তু "এক তলা উপরে" button দশবার চাপলে দশ তলা উঠে যাবে।

Double tap: bKash-এ ৳500 পাঠাতে "Pay" চাপলে, app এক সেকেন্ড ঝুলে থাকল — তুমি আবার চাপলে। Server-এ দুইটা request গেল। তোমার ইচ্ছা একটাই payment, তাই টাকা কাটতে হবে একবার।

Timeout → retry: Request server-এ পৌঁছেছে, টাকা কেটে COMMIT-ও হয়ে গেছে — কিন্তু response ফেরার পথে mobile network চলে গেল। App জানে না কাজ হয়েছে কি না, তাই আবার পাঠায়। Server-কে চিনতে হবে "এটা আগের সেই request"।

কেন retry এড়ানো যায় না:
  • Client কখনো আলাদা করতে পারে না — request হারিয়েছে, নাকি response হারিয়েছে। দুই ক্ষেত্রেই সে শুধু দেখে "timeout"।
  • তাই সব জায়গায় retry আছে: mobile app, HTTP client library (যেমন .NET-এ Polly), API gateway / load balancer, আর message queue (Kafka, RabbitMQ) — এরা at-least-once delivery দেয়, মানে একই message দুবারও আসতে পারে।
  • Retry থাকবেই — তাই server-কে এমনভাবে বানাতে হয় যে duplicate request এলে effect একবারই হয়। এটাই idempotency।

Same state বনাম same response

psql — একই DELETE দুবারstate একই
DELETE FROM orders WHERE id = 44;
DELETE 1
DELETE FROM orders WHERE id = 44;
DELETE 0          -- response আলাদা, কিন্তু row তো নেই-ই
HTTP — একই কথাresponse আলাদা
DELETE /orders/44   →  204 No Content
DELETE /orders/44   →  404 Not Found

Idempotency-র সংজ্ঞা state (side effect) নিয়ে, response নিয়ে না — দ্বিতীয় DELETE-এর উত্তর ভিন্ন হলেও সেটা idempotent। কিন্তু payment-এর মতো জায়গায় client-এর একই response-ও দরকার (payment id, নতুন balance) — তাই পরে আমরা response-টাও database-এ রেখে দেব (idempotency key pattern)।

3সমস্যা: timeout-এর পর retry = double charge

সাধারণ payment API — এক transaction-এ টাকা কাটো আর payment row লেখো। Atomicity ঠিক আছে, কিন্তু idempotency নেই। প্রথম request COMMIT হলো, response পথে হারাল, app একই request আবার পাঠাল:

কী ঘটল:

  2. Server টাকা কেটে COMMIT করল
  3. Response ফেরার পথে network drop → app দেখল timeout
  4. App একই request আবার পাঠাল
  5. Server জানে না এটা পুরনো request → আবার কাটল

Database-এর দোষ নেই — দুটোই বৈধ transaction। Server-কে "এই request আগে দেখেছি" চেনার উপায় দিতে হবে।

4সমাধান ১: Idempotency key

প্রতিটা user-intent-এর জন্য একটা unique key — server সেটা মনে রাখে

Client প্রতিটা payment-এর জন্য একটা random key (UUID) বানায় আর সব retry-তে একই key পাঠায় (Idempotency-Key header)। Server key-টা একটা table-এ লিখে রাখে, সাথে response। একই key আবার এলে কাজ না করে পুরনো response ফেরত দেয়।

schema
CREATE TABLE idempotency_keys (
  key          text        PRIMARY KEY,     -- client-এর পাঠানো UUID
  request_hash text        NOT NULL,        -- body-র sha256
  status       text        NOT NULL DEFAULT 'processing',
  response     jsonb,                       -- যা client-কে ফেরত দিয়েছিলাম
  created_at   timestamptz NOT NULL DEFAULT now()
);

Production-এ key সাধারণত user/merchant অনুযায়ী আলাদা: PRIMARY KEY (user_id, key) — এক user-এর key দিয়ে আরেকজনের response পাওয়া যাবে না।

Atomicity না থাকলে দুই রকম বিপদ:
  • Key আগে আলাদা commit, তারপর charge-এর আগে crash → key বলছে "দেখেছি", কিন্তু টাকা কাটা হয়নি। Retry এলে server ভুল করে "already done" বলবে — payment চিরতরে আটকে।
  • Charge commit, তারপর key লেখার আগে crash → key নেই, retry এলে আবার কাটবে — double charge ফিরে এল।
  • এক transaction-এ রাখলে দুটো হয় একসাথে টিকে, নয়তো একসাথে মুছে যায়। আর Durability-র কারণে COMMIT-এর পর crash হলেও key + payment দুটোই থাকে।
কিন্তু আসল charge যদি বাইরের API হয়? (যেমন bKash/SSLCommerz gateway call) — সেটা database transaction-এর ভেতরে rollback করা যায় না। তখন ধাপ ভাগ করো:
  1. Transaction ১: key insert, status = 'processing' → COMMIT।
  2. Gateway call — একই idempotency key gateway-কেও পাঠাও (ভালো gateway গুলো এটা support করে)।
  3. Transaction ২: payment row লেখো, key-কে completed + response করো।

এর মধ্যে একই key এলে status = 'processing' দেখে 409 Conflict দাও ("এখনো চলছে, পরে চেষ্টা করো")। Crash-এ আটকে থাকা processing row গুলো একটা background job gateway-র কাছে status জিজ্ঞেস করে ঠিক করে।

5সমাধান ২: Business key-তে UNIQUE constraint

Database-এর শেষ প্রতিরক্ষা — app-এ bug থাকলেও

একটা order-এর payment একবারই হয় — এই নিয়মটা সরাসরি database-কে বলে দাও। Client যদি ভুল করে প্রতিটা retry-তে নতুন idempotency key বানায়, কিংবা কোনো code path key check-ই না করে — তবুও দ্বিতীয় payment ঢুকতে পারবে না।

ব্যবহারের নিয়ম:
  • Constraint ভাঙলে PostgreSQL SQLSTATE 23505 (unique_violation) দেয়। App সেটা ধরে "আগেই paid" ধরে নিয়ে বিদ্যমান payment খুঁজে ফেরত দেয় — 500 error না।
  • Business key না থাকলে (যেমন একই order-এ কিস্তিতে একাধিক payment বৈধ) তখন UNIQUE (order_id, installment_no) বা idempotency key লাগবে।
  • Idempotency key = app-level সুরক্ষা ও response replay; UNIQUE = data-level গ্যারান্টি। Production-এ দুটোই রাখো।
  • UNIQUE constraint concurrent insert-এও কাজ করে — পরের অংশে দেখো।

6সমাধান ৩: Conditional update / state machine

"শুধু যদি এখনো pending থাকে, তবেই paid করো"

Order-এর একটা state machine আছে: pending → paid → shipped। Transition-টা WHERE-এ আগের state সহ লিখলে statement নিজেই idempotent হয় — দ্বিতীয়বার কোনো row মেলে না (compare-and-set)।

শুধু transition
UPDATE orders SET status = 'paid'
WHERE id = 42 AND status = 'pending';
UPDATE 1          ← transition হলো

UPDATE orders SET status = 'paid'
WHERE id = 42 AND status = 'pending';
UPDATE 0          ← আগেই paid, কিছু হলো না

App row count দেখে: 1 হলে এখন charge করো, 0 হলে আগেই হয়ে গেছে। Optimistic locking-ও একই ধারণা: … SET version = version + 1 WHERE id = 42 AND version = 7।

transition + charge — এক statement-এ (CTE)
WITH paid AS (
  UPDATE orders SET status = 'paid'
  WHERE id = 42 AND status = 'pending'
  RETURNING account_id, amount
)
UPDATE accounts a SET balance = a.balance - p.amount
FROM paid p WHERE a.id = p.account_id
RETURNING a.balance;

Concurrent হলেও নিরাপদ কেন: দুটো request একসাথে এই UPDATE চালালে দ্বিতীয়টা প্রথমটার row lock-এ অপেক্ষা করে। প্রথমটা commit করলে READ COMMITTED-এ PostgreSQL দ্বিতীয়টার WHERE শর্ত row-এর নতুন version-এর উপর আবার যাচাই করে — status এখন 'paid', তাই UPDATE 0 (দুই session চালিয়ে যাচাই করা)। সীমাবদ্ধতা: client-কে আগের response দেয় না, আর এমন কিছু লাগে যার state আছে (order)।

7Concurrency — দুইটা request একই মুহূর্তে

Double click-এ দুটো request প্রায় একসাথে আসে — দুইটা আলাদা connection, দুইটা transaction। এখানে সবচেয়ে প্রচলিত ভুল: "আগে SELECT করে দেখি আছে কি না, না থাকলে INSERT" (check-then-act)।

ভুল: SELECT করে দেখো, তারপর charge

কেন ভাঙল: দুজনেই t3–t4-এ check করেছে যখন কোনো payment ছিল না। accounts-এর row lock B-কে শুধু দেরি করিয়েছে, থামায়নি — কারণ "আছে কি না" সিদ্ধান্ত তো আগেই নেওয়া। Check আর insert-এর মাঝের ফাঁকটাই race condition।
  • idempotency_keys-এ PK থাকলে এই একই pattern-এ B পায় ERROR: duplicate key value violates unique constraint "idempotency_keys_pkey" — double charge হয় না, কিন্তু user দেখে 500 error (এটাও যাচাই করা)।

সঠিক: INSERT … ON CONFLICT দিয়ে key দাবি

কী ঘটল:
  • A-র insert করা key এখনো uncommitted। B একই key insert করতে গিয়ে unique index-এ সেটা দেখে — কিন্তু A commit করবে না rollback, জানে না। তাই B অপেক্ষা করে (t2)।
  • A COMMIT করতেই B জেগে উঠে conflict দেখে → INSERT 0 0, 0 row ফেরত → charge না করে stored response পড়ে।
  • যদি A ROLLBACK করত (ধরো balance কম ছিল), তাহলে B-এর insert সফল হতো (INSERT 0 1) আর B নিজেই কাজটা করত — ঠিক যেমন হওয়া উচিত (দুই session দিয়ে যাচাই করা)।
  • এই pattern READ COMMITTED-এর (default) জন্য। REPEATABLE READ-এ B-এর snapshot A-র row দেখতে পায় না, তাই PostgreSQL দেয় ERROR: could not serialize access due to concurrent update — তখন পুরো transaction retry করতে হবে (Isolation গাইড)।

8HTTP method আর idempotency

Safe = server-এর state বদলায় না (শুধু পড়ে)। Idempotent = বদলাতে পারে, কিন্তু N বার করলেও একবারের সমান। সব safe method idempotent, কিন্তু উল্টোটা না।

MethodSafeIdempotentউদাহরণ / কারণ
GET, HEAD, OPTIONS✓✓শুধু পড়া — SELECT-এর মতো।
PUT✗✓পুরো resource replace — PUT /orders/42 {"status":"paid"} ≈ UPDATE … SET status = 'paid'।
DELETE✗✓দ্বিতীয়বার 404 আসতে পারে, কিন্তু state একই — resource নেই।
POST✗✗নতুন কিছু তৈরি করে (নতুন payment, নতুন id) ≈ serial id দিয়ে INSERT। Idempotency-Key দিয়ে idempotent বানাতে হয়।
PATCH✗নির্ভর করে{"balance": 500} হলে idempotent; {"op":"increment","by":500} হলে না।
Idempotency-Key header convention
POST /v1/payments HTTP/1.1
Content-Type: application/json
Idempotency-Key: 7f3a9c1e-4b2d-4e8a-9c1f-2d3e4f5a6b7c

{"order_id": 42, "amount": 500}
যা প্রচলিত:
  • Stripe সহ অনেক payment API এই header নেয়; replay হলে আগের status code + body ফেরত দেয় (Stripe সাথে Idempotent-Replayed: true header দেয়), আর key অন্তত 24 ঘণ্টা রাখে।
  • IETF draft (The Idempotency-Key HTTP Header Field) অনুযায়ী: key না থাকলে 400, একই key-তে ভিন্ন body হলে 422, আগেরটা এখনো চললে 409।
  • HTTP-র idempotency শুধু একটা চুক্তি — PUT handler-এর ভেতরে balance = balance - 500 লিখলে সেটা আর idempotent থাকে না। আসল গ্যারান্টি আসে database-এর query থেকে।

9Application code — C# (Npgsql)

Server: key দাবি, charge, response save — সব এক transaction-এ। Client: একবার key বানাও, timeout হলে একই key দিয়ে exponential backoff-এ retry।

PaymentsEndpoint.cs — serverএক transaction
app.MapPost("/payments", async (HttpRequest http, PayRequest req, NpgsqlDataSource db) =>
{
    string? key = http.Headers["Idempotency-Key"];
    if (string.IsNullOrEmpty(key)) return Results.BadRequest("Idempotency-Key header লাগবে");
    string hash = Sha256(JsonSerializer.Serialize(req));

    await using var conn = await db.OpenConnectionAsync();
    await using var tx = await conn.BeginTransactionAsync();       // READ COMMITTED (default)

    NpgsqlCommand Cmd(string sql, params (string, object)[] ps)
    {
        var c = new NpgsqlCommand(sql, conn, tx);
        foreach (var (n, v) in ps) c.Parameters.AddWithValue(n, v);
        return c;
    }

    // ১) key দাবি — একই key-এর আরেকটা request চললে এখানে অপেক্ষা করবে
    var claimed = await Cmd("INSERT INTO idempotency_keys (key, request_hash) VALUES (@k, @h) " +
                            "ON CONFLICT (key) DO NOTHING RETURNING key",
                            ("k", key), ("h", hash)).ExecuteScalarAsync();

    if (claimed is null)                                             // ২) আগে দেখা request
    {
        await using var rd = await Cmd("SELECT request_hash, response::text FROM idempotency_keys WHERE key = @k",
                                       ("k", key)).ExecuteReaderAsync();
        await rd.ReadAsync();
        if (rd.GetString(0) != hash) return Results.UnprocessableEntity("একই key, ভিন্ন body");
        return Results.Content(rd.GetString(1), "application/json");  // replay — কিছু কাটা হয়নি
    }

    try                                                              // ৩) আসল কাজ
    {
        var balance = (int)(await Cmd("UPDATE accounts SET balance = balance - @amt WHERE id = @acc RETURNING balance",
                                      ("amt", req.Amount), ("acc", req.AccountId)).ExecuteScalarAsync())!;
        var paymentId = (long)(await Cmd("INSERT INTO payments (account_id, order_id, amount) " +
                                         "VALUES (@acc, @ord, @amt) RETURNING id",
                                         ("acc", req.AccountId), ("ord", req.OrderId), ("amt", req.Amount)).ExecuteScalarAsync())!;
        string body = JsonSerializer.Serialize(new { payment_id = paymentId, status = "paid", balance });

        await Cmd("UPDATE idempotency_keys SET status = 'completed', response = @r::jsonb WHERE key = @k",
                  ("r", body), ("k", key)).ExecuteNonQueryAsync();
        await tx.CommitAsync();                                      // key + টাকা + response একসাথে
        return Results.Content(body, "application/json");
    }
    catch (PostgresException e) when (e.SqlState is "23514" or "23505")
    {
        await tx.RollbackAsync();                                    // key-ও মুছে গেল → পরে retry সম্ভব
        return Results.UnprocessableEntity(e.SqlState == "23514" ? "balance যথেষ্ট না" : "এই order আগেই paid");
    }
});
PaymentClient.cs — retry + backoff
async Task<HttpResponseMessage> PayWithRetry(HttpClient http, PayRequest req)
{
    var key = Guid.NewGuid().ToString();     // একবারই — সব retry-তে একই key
    for (int attempt = 0; ; attempt++)
    {
        using var msg = new HttpRequestMessage(HttpMethod.Post, "/payments")
        {
            Content = JsonContent.Create(req)
        };
        msg.Headers.Add("Idempotency-Key", key);
        try
        {
            var res = await http.SendAsync(msg);
            int code = (int)res.StatusCode;
            if (code < 500 && code != 409 && code != 429) return res;   // সফল বা স্থায়ী 4xx
        }
        catch (Exception e) when (e is HttpRequestException or TaskCanceledException)
        {
            // timeout / network drop — কাজ হয়েছে কি না জানি না → retry নিরাপদ
        }
        if (attempt == 4) throw new Exception("৫ বার চেষ্টা করেও হয়নি");
        // 200ms, 400ms, 800ms, 1.6s … + jitter
        var delay = 200 * Math.Pow(2, attempt) + Random.Shared.Next(0, 100);
        await Task.Delay(TimeSpan.FromMilliseconds(delay));
    }
}
খেয়াল করার বিষয়:
  • Key loop-এর বাইরে বানানো — প্রতিটা attempt-এ নতুন key বানালে idempotency শেষ।
  • আসল app-এ key "Pay" screen খোলার সময় বানিয়ে local-এ রাখা ভালো — app restart হলেও একই key।
  • Exponential backoff: প্রতিবার অপেক্ষা দ্বিগুণ — server বিপদে থাকলে আরো চাপ না দেওয়া।
  • Jitter: হাজার client একসাথে retry করলে (thundering herd) সবাই একই মুহূর্তে আঘাত না করে।
  • 4xx (409/429 ছাড়া) retry করো না — একই ভুল request বারবার পাঠিয়ে লাভ নেই।
  • Server-এর Results.Content শুধু body replay করে; status code-ও replay করতে চাইলে সেটাও idempotency_keys-এ রাখো।

QInterview-এ যা আসে

Idempotent আর safe-এর পার্থক্য কী?

Safe operation server-এর state একদমই বদলায় না (GET, SELECT)। Idempotent operation বদলাতে পারে, কিন্তু একবার আর N বারের ফল একই (PUT, DELETE, SET balance = 500)। সব safe operation idempotent, কিন্তু সব idempotent operation safe না।

DELETE কি সত্যিই idempotent? দ্বিতীয়বার তো 404 আসে।

হ্যাঁ। Idempotency state নিয়ে — দুবার পরেও resource নেই, যেমন একবার পরেও নেই। Response ভিন্ন (DELETE 1 → DELETE 0, 204 → 404) হওয়া সংজ্ঞা ভাঙে না। তবে "সবচেয়ে পুরনো 10টা মুছো" ধরনের DELETE প্রতিবার আলাদা row মুছে — সেটা idempotent না।

POST কেন idempotent না? কীভাবে বানাবে?

POST মানে "নতুন কিছু তৈরি করো" — server প্রতিবার নতুন id দেয়, ঠিক serial id দিয়ে INSERT-এর মতো। Idempotent বানাতে client একটা Idempotency-Key পাঠায়; server key-টা unique table-এ INSERT … ON CONFLICT DO NOTHING দিয়ে আসল কাজের একই transaction-এ লেখে, আর response save করে replay করে। সাথে business key-তে UNIQUE constraint।

Idempotency key কতদিন রাখবে? Table তো বাড়তেই থাকবে।

Client যতক্ষণ retry করতে পারে তার চেয়ে বেশি সময় — সাধারণত 24 ঘণ্টা থেকে 7 দিন (Stripe অন্তত 24 ঘণ্টা)। একটা scheduled cleanup job চালাও: DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours' (বড় table-এ batch করে, created_at-এ index রেখে)। খুব বেশি traffic হলে দিন অনুযায়ী partition করে পুরনো partition DROP করা সবচেয়ে সস্তা। TTL-এর পরে একই key এলে সেটা নতুন request হিসেবে গণ্য হবে — তাই business key-তে UNIQUE constraint রাখা জরুরি।

Key কে বানাবে — client না server?

Client। Server বানালে timeout-এর পর client সেই key জানেই না, তাই retry-তে পাঠাতে পারবে না। Client প্রতিটা user intent-এর জন্য (প্রতিটা HTTP attempt-এর জন্য না) একটা random UUID v4 বানায় — যেমন checkout screen খোলার সময় — আর সব retry-তে সেটাই পাঠায়। Server key-কে user অনুযায়ী scope করে: PRIMARY KEY (user_id, key)।

Idempotency আর message queue-র "exactly-once delivery" — সম্পর্ক কী?

Network-এ সত্যিকারের exactly-once delivery প্রায় অসম্ভব; Kafka/RabbitMQ/SQS সাধারণত at-least-once দেয় — consumer crash করলে একই message আবার আসে। তাই "exactly-once processing" = at-least-once delivery + idempotent consumer। Consumer একটা dedup table রাখে আর message-এর side effect-এর একই transaction-এ id লেখে:

CREATE TABLE processed_messages (
  message_id   text PRIMARY KEY,
  processed_at timestamptz NOT NULL DEFAULT now()
);
BEGIN;
INSERT INTO processed_messages (message_id) VALUES ('evt-9f2c')
ON CONFLICT DO NOTHING RETURNING message_id;
-- 0 row → আগেই process হয়েছে, শুধু ack করো
-- 1 row → আসল কাজ এখানে, তারপর COMMIT, তারপর ack
COMMIT;
Upsert কী? ON CONFLICT DO NOTHING আর DO UPDATE-এর পার্থক্য?

Upsert = "থাকলে update, না থাকলে insert" — এক atomic statement-এ। DO NOTHING বিদ্যমান row ছুঁয়ে না, RETURNING-এ 0 row দেয় (idempotency key-র জন্য আদর্শ — "আমি প্রথম কি না" জানা যায়)। DO UPDATE SET col = EXCLUDED.col নতুন মান বসায়, RETURNING সবসময় row দেয়। এটা idempotent শুধু যদি SET-এ absolute মান থাকে। "SELECT করে দেখে INSERT/UPDATE" race-prone; PostgreSQL-এর MERGE-ও concurrent insert-এ unique violation দিতে পারে — তাই concurrent upsert-এ ON CONFLICT-ই নিরাপদ পছন্দ।

প্রথম request এখনো চলছে, তখন একই key আরেকটা এল — কী হবে?

Key insert আর কাজ এক transaction-এ থাকলে দ্বিতীয়টা unique index-এ অপেক্ষা করে, প্রথমটা commit করলে 0 row পেয়ে stored response ফেরত দেয়; প্রথমটা rollback করলে দ্বিতীয়টা নিজেই কাজটা করে (সেকশন ৭)। কাজের মাঝে বাইরের API call থাকলে key আগে processing হিসেবে commit হয় — তখন দ্বিতীয়টাকে 409 Conflict দাও, client পরে retry করবে।
