Optimistic বনাম Pessimistic Locking

দুজন customer একই মুহূর্তে শেষ কয়েকটা Laptop কিনছে। দুজনেই stock পড়ল 10, দুজনেই নিজের হিসাবে লিখল — একজনের বিক্রি হারিয়ে গেল। এই lost update ঠেকানোর দুই দর্শন: আগেই তালা দাও (pessimistic), নাকি লেখার সময় যাচাই করো (optimistic)। প্রতিটা output PostgreSQL 18-এ চালিয়ে নেওয়া।

!সমস্যা — Lost Update

Read → app-এ হিসাব → Write

App প্রথমে stock পড়ে, নিজের memory-তে 10 − 3 = 7 হিসাব করে, তারপর SET stock = 7 লেখে। মাঝখানে B-ও 10 পড়ে 8 লেখে। দুটো transaction-ই সফল, কোনো error নেই — কিন্তু A-র বিক্রি হারিয়ে গেল।

কেন হলো: PostgreSQL row lock নেয় শুধু লেখার সময়, পড়ার সময় না। B অপেক্ষা ঠিকই করল (t6), কিন্তু A commit করার পর B তার আগে হিসাব করা 8-ই লিখে দিল — কারণ মানটা app ঠিক করেছে, database না। Default READ COMMITTED এটা ধরে না। ৩টা ভুল জিনিস একসাথে: (১) read-এর পর lock নেই, (২) লেখার সময় যাচাই নেই, (৩) মান app-এ হিসাব করা।

▶Simulation — A আর B একসাথে

পদ্ধতি বেছে নাও, তারপর ▶ চালাও বা ⏭ এক ধাপ। মাঝখানে database-এর row, দুই পাশে দুই app server — কার memory-তে কী আছে, কে lock ধরে আছে, কে অপেক্ষা করছে, সব দেখা যাবে।

🔒সমাধান ১ — Pessimistic Locking

"কেউ না কেউ বদলাবেই" — তাই আগেই তালা

SELECT … FOR UPDATE পড়ার সাথে সাথে row-টা lock করে, transaction শেষ (COMMIT/ROLLBACK) না হওয়া পর্যন্ত। অন্য কেউ একই row FOR UPDATE বা UPDATE করতে চাইলে লাইনে দাঁড়ায়। সাধারণ SELECT (lock ছাড়া) কিন্তু আটকায় না — MVCC-তে পুরনো committed মান পড়তে পারে।

অপেক্ষা করতে না চাইলে — NOWAIT, SKIP LOCKED, lock_timeout

NOWAIT — সাথে সাথে errorfail fast
-- A আগে থেকেই FOR UPDATE ধরে আছে
SELECT stock FROM products WHERE id = 1 FOR UPDATE NOWAIT;
ERROR:  could not obtain lock on row in relation "products"
-- app: "এখন ব্যস্ত, একটু পরে চেষ্টা করুন"
lock_timeout — নির্দিষ্ট সময় পর্যন্তbounded wait
BEGIN;
SET LOCAL lock_timeout = '2s';
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
-- ২ সেকেন্ড অপেক্ষা…
ERROR:  canceling statement due to lock timeout
SKIP LOCKED — job queue-এর জন্যকেউ কাউকে আটকায় না
-- ১০টা worker একসাথে চালালেও প্রত্যেকে আলাদা job পায়
SELECT id FROM jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;     -- অন্য worker যেটা ধরে আছে সেটা বাদ

-- A যখন product row ধরে আছে, B চালালে:
SELECT * FROM products FOR UPDATE SKIP LOCKED;
(0 rows)
মনে রাখো:
  • Lock ধরে রেখে কখনো user-এর input, payment gateway বা HTTP call-এর জন্য অপেক্ষা করবে না — transaction যত ছোট, তত ভালো।
  • একাধিক row lock করলে সবসময় একই ক্রমে (যেমন ORDER BY id) — নাহলে deadlock।
  • Lock-এর ধরন: FOR UPDATE (সবচেয়ে কড়া), FOR NO KEY UPDATE (key না বদলালে, UPDATE নিজে এটাই নেয়), FOR SHARE (পড়তে দেয়, বদলাতে দেয় না), FOR KEY SHARE (foreign key check)।

vসমাধান ২ — Optimistic Locking

"সংঘর্ষ কদাচিৎ হয়" — তাই lock নয়, যাচাই

প্রতিটা row-এ একটা version। পড়ার সময় version মনে রাখো; লেখার সময় WHERE version = সেই_মান দিয়ে লেখো আর version বাড়াও। মাঝে কেউ বদলে থাকলে version মিলবে না — UPDATE 0। App তখন আবার পড়ে, আবার হিসাব করে, আবার চেষ্টা করে।

দুজনেই transaction-এর ভেতরে থাকলে?

কী হলো: A-র UPDATE row lock নিয়েছে, তাই B-এর UPDATE অপেক্ষা করল। A commit করার পর READ COMMITTED নতুন version-এর উপর WHERE আবার যাচাই করে — version এখন 2, শর্ত মেলে না, তাই 0 rows। Optimistic locking-এও database-এর row lock কাজ করে, শুধু app কোনো lock ধরে রাখে না পড়া থেকে লেখা পর্যন্ত।

Application code — retry loop (C#, Npgsql)

async Task BuyAsync(NpgsqlDataSource db, int productId, int qty)
{
    for (var attempt = 1; attempt <= 5; attempt++)
    {
        await using var read = db.CreateCommand("SELECT stock, version FROM products WHERE id = $1");
        read.Parameters.AddWithValue(productId);
        await using var r = await read.ExecuteReaderAsync();
        await r.ReadAsync();
        var (stock, version) = (r.GetInt32(0), r.GetInt32(1));
        await r.DisposeAsync();

        if (stock < qty) throw new InvalidOperationException("Out of stock");

        await using var write = db.CreateCommand(
            "UPDATE products SET stock = $1, version = version + 1 WHERE id = $2 AND version = $3");
        write.Parameters.AddWithValue(stock - qty);
        write.Parameters.AddWithValue(productId);
        write.Parameters.AddWithValue(version);

        if (await write.ExecuteNonQueryAsync() == 1) return;   // সফল
        // 0 rows → কেউ মাঝে বদলেছে, আবার পড়ো
    }
    throw new Exception("Too much contention, try later");
}

ORM-এ এটা built-in: EF Core-এ property-তে [ConcurrencyCheck] দিলে UPDATE-এর WHERE-এ সেটা যোগ হয়, 0 row হলে DbUpdateConcurrencyException; JPA/Hibernate-এ @Version। PostgreSQL-এ চাইলে আলাদা column ছাড়াই system column xmin-কে version হিসেবে ব্যবহার করা যায় (Npgsql EF Core provider এটা সমর্থন করে)।

=সবচেয়ে সহজ — হিসাবটা database-কেই করতে দাও

মান যদি app-এ হিসাব না করে SQL-এর ভেতরেই করো, read আর write একটাই statement — মাঝে কেউ ঢুকতে পারে না। শর্ত দিয়ে overselling-ও আটকানো যায়।

UPDATE products SET stock = stock - 3
WHERE id = 1 AND stock >= 3
RETURNING stock;
 stock
-------
     7     -- B একসাথে চালালে অপেক্ষা করে, তারপর 7 − 2 = 5
UPDATE products SET stock = stock - 30
WHERE id = 1 AND stock >= 30
RETURNING stock;
 stock
-------
(0 rows)  -- যথেষ্ট stock নেই, কিছুই বদলায়নি

যখন নিয়ম একটা row-এর ভেতরেই — এটাই প্রথম পছন্দ। নিয়ম যখন জটিল (একাধিক row, বাইরের API, user-এর হাতে form), তখন pessimistic বা optimistic লাগে। আরেক উপায়: REPEATABLE READ — একই row অন্য কেউ বদলালে "could not serialize access" error, তারপর retry।

Nঅনেকগুলো transaction একসাথে হলে

Pessimistic: ১০০ জন একই row-এ FOR UPDATE করলে একজন lock পায়, বাকি ৯৯ জন লাইনে (lock queue)। একে একে সবাই ঠিক মানই পায় — কেউ ব্যর্থ হয় না, কিন্তু সবাই সিরিয়ালি চলে। Throughput = ১ / (transaction-এর সময়)। Transaction লম্বা হলে connection pool ভরে যায়, timeout শুরু হয়।

Optimistic: ১০০ জন একসাথে পড়ে version 7; লেখার সময় একজন জেতে (version 8), বাকি ৯৯ জন UPDATE 0 পেয়ে আবার পড়ে — পরের রাউন্ডে আবার একজন জেতে। Conflict কম হলে কেউ অপেক্ষাই করে না (দ্রুত); conflict বেশি হলে retry-র ঝড়ে CPU আর DB round-trip নষ্ট হয়।

QInterview-এ যা আসে

Lost update কী, আর READ COMMITTED কেন এটা ধরে না?

দুজন একই মান পড়ে নিজের হিসাবে লিখলে প্রথমজনের লেখা দ্বিতীয়জন মুছে দেয়। READ COMMITTED শুধু uncommitted data দেখা আটকায়; app-এ হিসাব করা মান লেখার আগে যাচাই করে না। REPEATABLE READ বা উপরে PostgreSQL error দেয়।

Optimistic locking-এ কি আসলে কোনো lock নেই?

App-এর দিক থেকে নেই — পড়া থেকে লেখা পর্যন্ত কিছু ধরে রাখে না। কিন্তু UPDATE statement নিজে মুহূর্তের জন্য row lock নেয়, তাই দুটো UPDATE একসাথে এলে একটা অল্প সময় অপেক্ষা করে, তারপর version না মেলায় 0 rows পায়।

FOR UPDATE আর সাধারণ SELECT-এর পার্থক্য?

সাধারণ SELECT কোনো lock নেয় না, MVCC snapshot থেকে পড়ে — কাউকে আটকায় না, কারো জন্য আটকায় না। FOR UPDATE row-টা transaction শেষ পর্যন্ত lock করে; অন্য FOR UPDATE / UPDATE / DELETE অপেক্ষা করে।

SKIP LOCKED কোথায় কাজে লাগে?

Database-কে job queue হিসেবে ব্যবহার করলে — অনেক worker একসাথে "পরের pending job" চায়; SKIP LOCKED অন্যের ধরা row বাদ দিয়ে পরেরটা দেয়, ফলে কেউ কাউকে আটকায় না আর একই job দুজন পায় না।

Flash sale-এ ১০,০০০ জন একসাথে কিনলে কোনটা?

একটা hot row-এ optimistic দিলে প্রায় সবাই UPDATE 0 পেয়ে retry করবে। সবচেয়ে ভালো single-statement conditional update (stock = stock - 1 WHERE stock >= 1); জটিল হলে pessimistic, ছোট transaction, বা queue দিয়ে সিরিয়ালি।

REST API-তে optimistic locking কীভাবে?

GET-এর response-এ ETag (version) পাঠাও; client PUT/PATCH-এর সাথে If-Match: "7" পাঠায়; version না মিললে server 412 Precondition Failed দেয়।
