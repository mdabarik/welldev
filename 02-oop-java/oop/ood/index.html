Object-Oriented Design · UML · বাংলা

UML Class Diagram,
line by line.

UML (Unified Modeling Language) দিয়ে সফটওয়্যারের ডিজাইন ছবিতে দেখানো হয়। এই পাতায় আগে পুরো UML-এর ম্যাপ, তারপর সবচেয়ে বেশি ব্যবহৃত Class Diagram — ক্লাস বক্স, multiplicity আর ৬টি সম্পর্কের লাইন, তীর আর ডায়মন্ড কোন দিকে যায়।

ছবিগুলো আসল UML চিহ্নে আঁকা: সলিড বনাম ড্যাশড লাইন, ফাঁপা ত্রিভুজ, সাধারণ তীর, ফাঁপা ◇ আর ভরাট ◆ ডায়মন্ড।

অধ্যায় ১

UML ডায়াগ্রামের ১৪টি ধরন

UML 2.5 অনুযায়ী মোট ১৪ ধরনের ডায়াগ্রাম, দুই ভাগে: Structural — সিস্টেমের স্থির কাঠামো, আর Behavioral — সিস্টেমের গতিশীল আচরণ।

Structural Diagrams

৭টি · সিস্টেমের গঠন ও উপাদানের সম্পর্ক
  1. Class Diagramবেশি ব্যবহৃত

    সবচেয়ে বেশি ব্যবহৃত। ক্লাস, তাদের অ্যাট্রিবিউট, মেথড আর ক্লাসগুলোর সম্পর্ক (যেমন inheritance) দেখায়।

  2. Object Diagram

    Class diagram-এর একটা নির্দিষ্ট মুহূর্তের ছবি — তখন কোন অবজেক্ট কোন অবস্থায় আর কার সাথে যুক্ত।

  3. Component Diagram

    সিস্টেমের কম্পোনেন্ট (module বা library) কীভাবে একে অপরের সাথে যুক্ত হয়ে কাজ করে।

  4. Deployment Diagram

    হার্ডওয়্যার আর্কিটেকচার — কোন সার্ভার বা নোডে কোন সফটওয়্যার কম্পোনেন্ট চলবে।

  5. Package Diagram

    ক্লাস বা কম্পোনেন্টগুলো কীভাবে প্যাকেজ বা লজিক্যাল গ্রুপে ভাগ করা।

  6. Composite Structure Diagram

    একটা নির্দিষ্ট ক্লাসের ভেতরের গঠন আর তার অংশগুলো কীভাবে কাজ করে।

  7. Profile Diagram

    UML-কে নিজের ডোমেইনের জন্য কাস্টমাইজ করা (নিজস্ব stereotype ইত্যাদি)।

Behavioral Diagrams

৭টি · সিস্টেম কীভাবে কাজ করে, কে কার সাথে কথা বলে
  1. Use Case Diagramবেশি ব্যবহৃত

    ব্যবহারকারী (Actor) সিস্টেমের সাথে কীভাবে ইন্টারঅ্যাক্ট করে — সিস্টেমে কী কী ফিচার আছে তার হাই-লেভেল ছবি।

  2. Activity Diagramবেশি ব্যবহৃত

    ফ্লোচার্টের মতো — একটা কাজ শুরু থেকে শেষ পর্যন্ত কোন ধাপে হয়।

  3. State Machine Diagram

    ইভেন্টের কারণে একটা অবজেক্ট এক স্টেট থেকে আরেক স্টেটে কীভাবে যায়।

  4. Sequence Diagramবেশি ব্যবহৃত

    সময়ের ক্রমে অবজেক্টগুলোর মধ্যে মেসেজ আদান-প্রদান (Interaction diagram-এর অংশ)।

  5. Communication Diagram

    Sequence-এর মতোই, তবে সময়ের চেয়ে অবজেক্টগুলোর সম্পর্কে বেশি জোর।

  6. Interaction Overview Diagram

    Activity আর Sequence diagram-এর মিশ্রণ — পুরো ইন্টারঅ্যাকশনের ওভারভিউ।

  7. Timing Diagram

    সময়ের সাথে অবজেক্টের অবস্থার পরিবর্তন — যেখানে সময়ের হিসাব জরুরি (যেমন রিয়েল-টাইম সিস্টেম)।

সংক্ষেপে: বাস্তবে সবচেয়ে বেশি ব্যবহৃত হয় Class, Use Case, Sequence আর Activity ডায়াগ্রাম। নিচের বাকি পাতাটা Class Diagram নিয়ে।

অধ্যায় ৩

Multiplicity / Cardinality

দুই ক্লাসের মাঝের লাইনের দুই প্রান্তে লেখা সংখ্যা বা চিহ্ন। এটা বলে — একটা ক্লাসের একটা অবজেক্ট অন্য ক্লাসের কতগুলো অবজেক্টের সাথে যুক্ত থাকতে পারে। যে প্রান্তে সংখ্যা লেখা, সেটা ওই প্রান্তের ক্লাসের সংখ্যা।

1
ঠিক একটিExactly One

বাধ্যতামূলক — ঠিক ১টি, কম বা বেশি না।

উদাহরণ: একজন নাগরিকের (Citizen) ঠিক একটি ন্যাশনাল আইডি (NationalID) থাকে।

0..1
শূন্য অথবা একটিZero or One

ঐচ্ছিক — থাকতেও পারে, নাও থাকতে পারে; সর্বোচ্চ ১টি।

উদাহরণ: একজন চাকরিজীবীর (Employee) অফিস কার (OfficeCar) থাকতে পারে, নাও পারে।

* বা 0..*
শূন্য অথবা অনেকZero or Many

ঐচ্ছিক — একটাও না থাকতে পারে, আবার অনেকগুলোও।

উদাহরণ: একজন ক্রেতা (Customer) কোনো অর্ডার না-ও দিতে পারেন, আবার অনেক অর্ডারও দিতে পারেন।

1..*
কমপক্ষে একটিOne or Many

বাধ্যতামূলক — কমপক্ষে ১টি থাকতেই হবে, বেশিও হতে পারে।

উদাহরণ: একটা ডিপার্টমেন্টে (Department) কমপক্ষে ১ জন শিক্ষক (Teacher) থাকতেই হবে।

n..m
নির্দিষ্ট সীমাSpecific Range

সংখ্যা একটা নির্দিষ্ট সীমার ভেতরে (যেমন 2..4), বা নির্দিষ্ট একটা সংখ্যা।

উদাহরণ: একটা গাড়ির (Car) সাধারণত 4টা চাকা (Wheel); ফুটবল টিমে মাঠে 11 জন।

অধ্যায় ৪

৬টি Relationship

একটা সফটওয়্যারে কখনো এক ক্লাস দিয়ে সব কাজ হয় না। Relationship-এর লাইন দেখায় — একটা ক্লাস অন্য ক্লাসের সাথে কীভাবে আর কতটা গভীরভাবে যুক্ত। লাইন সলিড না ড্যাশড, আর মাথায় কোন চিহ্ন — এই দুটোতেই পুরো অর্থ।

Inheritanceউত্তরাধিকারRealizationচুক্তি বা বাস্তবায়নAssociationসাধারণ যোগাযোগAggregationশিথিল মালিকানাCompositionদৃঢ় মালিকানাDependencyসাময়িক নির্ভরশীলতা
“Has / Uses” সম্পর্কগুলোর শক্তি
Dependencyসাময়িক ব্যবহারAssociationচেনে, রেফারেন্স রাখেAggregationমালিক, কিন্তু আলাদা বাঁচেCompositionএকসাথে জন্ম, একসাথে শেষ

Inheritance আর Realization এই স্কেলের বাইরে — ওগুলো “Is-A” আর “চুক্তি” সম্পর্ক, মালিকানা না।

সহজ কথায়একটা ক্লাসের সব বৈশিষ্ট্য (ভেরিয়েবল ও মেথড) আরেকটা ক্লাসে স্বয়ংক্রিয়ভাবে চলে আসে। তীর সবসময় দেখায় — প্যারেন্ট কে।

বাস্তব উদাহরণগাড়ি (Car) এক ধরনের যানবাহন (Vehicle); বিড়াল (Cat) এক ধরনের প্রাণী (Animal)। এখানে Vehicle প্যারেন্ট, Car চাইল্ড।

কোডে কেমন দেখায়
Java
// পিতা (Superclass)
class Vehicle {
    String brand;
    void start() {
        System.out.println("Engine started");
    }
}

// সন্তান (Subclass) - extends ব্যবহারের মাধ্যমে Inheritance হয়
class Car extends Vehicle {
    int doors = 4;
}

শুরু

Interface

সহজ কথায়একটা Interface শুধু বলে দেয় কী কী কাজ করা যাবে (নিয়ম); আরেকটা ক্লাস কোড লিখে সেই নিয়মগুলো বাস্তবে কীভাবে কাজ করবে তা দেখায়।

বাস্তব উদাহরণরিমোট কন্ট্রোল (RemoteControl) একটা নিয়ম — এতে powerOn() বোতাম আছে। সনি টিভি (SonyTV) বা স্যামসাং টিভি (SamsungTV) ঠিক করে বোতাম চাপলে কী হবে।

কোডে কেমন দেখায়
Java
// নিয়ম বা চুক্তি (Interface)
interface RemoteControl {
    void powerOn();
}

// নিয়ম বাস্তবায়নকারী ক্লাস (Concrete Class) - implements ব্যবহার করা হয়
class SonyTV implements RemoteControl {
    public void powerOn() {
        System.out.println("Sony TV is now ON");
    }
}

সাধারণ তীর
শুরু

শেষ (তীর / ডায়মন্ড)
যে ক্লাস ব্যবহৃত হচ্ছে

সহজ কথায়দুটো ক্লাস একে অপরকে চেনে বা সরাসরি যোগাযোগ করে। একমুখী (Directed) হলে শুধু A, B-কে চেনে; উভমুখী (Bidirectional) হলে দুজনেই দুজনকে চেনে।

বাস্তব উদাহরণক্রেতা (Customer) আর অর্ডার (Order) — ক্রেতার কাছে তার অর্ডারের তথ্য থাকে।

কোডে কেমন দেখায়
Java
class Order {
    String orderId;
}

class Customer {
    String name;
    Order myOrder; // Customer ক্লাসের ভেতরে Order ক্লাসের অবজেক্ট ভেরিয়েবল হিসেবে রাখা হয়েছে
}

Whole / মূল (ডায়মন্ড এর গায়ে)

সহজ কথায়এক ধরনের association, তবে মালিকানা আছে। সবচেয়ে গুরুত্বপূর্ণ: মূল ক্লাস ধ্বংস হলেও ভেতরের অবজেক্টগুলো স্বাধীনভাবে বেঁচে থাকতে পারে।

বাস্তব উদাহরণলাইব্রেরি (Library) আর বই (Book) — লাইব্রেরি বন্ধ হয়ে গেলেও বই নষ্ট হয় না, অন্য লাইব্রেরিতে নেওয়া যায়। একইভাবে ডিপার্টমেন্ট বন্ধ হলেও শিক্ষকেরা থাকেন।

কোডে কেমন দেখায়
Java
class Book {
    String title;
}

class Library {
    String name;
    List<Book> books; // বইগুলো লাইব্রেরির বাইরে তৈরি হয়ে এখানে পাস করা হয়

    Library(List<Book> books) {
        this.books = books;
    }
}

সহজ কথায়সবচেয়ে শক্ত মালিকানা — মূল আর অংশের জীবনকাল একসাথে বাঁধা। মূল ক্লাস ধ্বংস হলে ভেতরের অবজেক্টও সাথে সাথে ধ্বংস হয়; আলাদা অস্তিত্ব নেই।

বাস্তব উদাহরণমানুষ (Human) আর হৃদপিণ্ড (Heart) — শরীর ছাড়া হৃদপিণ্ড বাঁচে না। একইভাবে বাড়ি (House) ভাঙলে রুম (Room)-ও থাকে না।

কোডে কেমন দেখায়
Java
class Heart {
    void beat() { }
}

class Human {
    Heart heart;

    Human() {
        // Human তৈরি হওয়ার সময় ভেতরেই Heart তৈরি হচ্ছে
        this.heart = new Heart();
    }
    // Human অবজেক্ট যখন মেমোরি থেকে ডিলিট হবে, heart-ও ডিলিট হয়ে যাবে
}

সহজ কথায়সবচেয়ে দুর্বল সম্পর্ক। একটা ক্লাস আরেকটাকে নিজের কাছে স্থায়ীভাবে রাখে না — শুধু সাময়িক কাজে ব্যবহার করে, যেমন মেথডের প্যারামিটার বা লোকাল ভেরিয়েবল হিসেবে।

বাস্তব উদাহরণড্রাইভার (Driver) আর গাড়ি (Car) — ড্রাইভার শুধু চালানোর সময় (drive(Car car)) গাড়িটা ব্যবহার করেন। একইভাবে Printer প্রিন্টের সময় Document ব্যবহার করে।

কোডে কেমন দেখায়
Java
class Car {
    void move() { }
}

class Driver {
    // Car কিন্তু ক্লাসের মেম্বার ভেরিয়েবল হিসেবে নেই।
    // এটি শুধু drive মেথডের ভেতর সাময়িক প্যারামিটার হিসেবে ব্যবহৃত হচ্ছে।
    void drive(Car car) {
        car.move();
    }
}
সব একসাথে: Relationship + Multiplicity
  • ১টা লাইব্রেরিতে কমপক্ষে ১টা বা তার বেশি বই — বইয়ের প্রান্তে 1..*।
  • ১টা বই একসাথে ১টার বেশি লাইব্রেরির অংশ হতে পারে না — লাইব্রেরির প্রান্তে 1।
  • লাইব্রেরি বন্ধ হলেও বই নষ্ট হয় না — তাই ফাঁপা ◇, অর্থাৎ Aggregation।

ডায়মন্ড

ফাঁপা হোক বা ভরাট, ডায়মন্ড সবসময় মূল / ধারক (Whole) ক্লাসের গায়ে লাগানো।

সলিড বনাম ড্যাশড

স্থায়ী, সরাসরি সম্পর্ক = সলিড। চুক্তি (interface) বা সাময়িক ব্যবহার = ড্যাশড।
