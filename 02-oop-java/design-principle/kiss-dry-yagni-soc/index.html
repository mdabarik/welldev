Design Principles · C# · বাংলা

DRY, KISS, YAGNI
& Separation of Concerns.

সফটওয়্যার ইঞ্জিনিয়ারিংয়ে Design Principles হলো কিছু সাধারণ নিয়ম বা গাইডলাইন, যা মেনে কোড লিখলে কোড অনেক বেশি ক্লিন, মেইনটেইনেবল এবং বাগ-ফ্রি হয়। এগুলো কোনো নির্দিষ্ট ল্যাঙ্গুয়েজের জন্য নয়, বরং সব ল্যাঙ্গুয়েজেই ব্যবহার করা যায়।

SOLID-এর পাশাপাশি এই ৪টি হলো সবচেয়ে বেসিক নীতি। প্রতিটির জন্য সহজ ব্যাখ্যা, একটা বাস্তব উদাহরণ, আর একই C# কোডের Bad বনাম Good ভার্সন।

D DRY Don't Repeat Yourself একই কোড বারবার লিখবেন না। K KISS Keep It Simple, Stupid কোড যতটা সম্ভব সহজ রাখুন। Y YAGNI You Aren't Gonna Need It ভবিষ্যতে লাগতে পারে ভেবে আজই কোনো কোড লিখবেন না। S SoC Separation of Concerns প্রতিটি অংশের কাজ আলাদা রাখুন।
D
Principle 01

DRY — Don't Repeat Yourself

একই কোড বারবার লিখবেন না।

DRY প্রিন্সিপালের মূল লক্ষ্য হলো কোডের ডুপ্লিকেশন কমানো। যদি আপনার প্রজেক্টের একাধিক জায়গায় একই লজিক বা কোড ব্লক ব্যবহার করা হয়, তবে কোনো পরিবর্তনের দরকার হলে আপনাকে সব জায়গায় পরিবর্তন করতে হবে, যা ভুল হওয়ার সম্ভাবনা বাড়িয়ে দেয়। তাই কমন কোডগুলোকে একটি আলাদা ফাংশন, মেথড বা ক্লাসে নিয়ে আসতে হয়। এতে কোড মেইনটেইন করা সহজ হয় এবং একবার পরিবর্তন করলেই সব জায়গায় আপডেট হয়ে যায়।

বাস্তব উদাহরণ

অফিসের ঠিকানা যদি ১০টা কাগজে হাতে লেখা থাকে, অফিস বদলালে ১০টাই খুঁজে ঠিক করতে হয় — একটা মিস হলেই ভুল ঠিকানা থেকে যায়। একটা সিল (stamp) বানিয়ে রাখলে শুধু সিলটা বদলালেই সব কাগজ ঠিক।

কোডে দেখি

ReportGeneratorBad-এ PDF আর Excel — দুই মেথডেই কোম্পানির header হুবহু কপি করা। Header-এর লেখা বদলাতে হলে দুই জায়গায় বদলাতে হবে; একটা ভুলে গেলে দুই রিপোর্ট দুই রকম দেখাবে।

DRY.cs · Bad
public class ReportGeneratorBad
{
    public void GeneratePDFReport()
    {
        // Adding Header
        Console.WriteLine("--- Company Header ---");
        Console.WriteLine("Date: " + DateTime.Now);
        
        // Generate PDF logic...
        Console.WriteLine("Generating PDF...");
    }

    public void GenerateExcelReport()
    {
        // Adding Header (Repeated Code)
        Console.WriteLine("--- Company Header ---");
        Console.WriteLine("Date: " + DateTime.Now);
        
        // Generate Excel logic...
        Console.WriteLine("Generating Excel...");
    }
}

Header-এর লজিক এক জায়গায় — PrintCompanyHeader()। PDF আর Excel দুজনেই সেটা call করে। বদলাতে হলে একবার বদলালেই সব রিপোর্টে আপডেট।

DRY.cs · Good
public class ReportGeneratorGood
{
    // Extracted common logic to a single place
    private void PrintCompanyHeader()
    {
        Console.WriteLine("--- Company Header ---");
        Console.WriteLine("Date: " + DateTime.Now);
    }

    public void GeneratePDFReport()
    {
        PrintCompanyHeader(); // Reused
        Console.WriteLine("Generating PDF...");
    }

    public void GenerateExcelReport()
    {
        PrintCompanyHeader(); // Reused
        Console.WriteLine("Generating Excel...");

মনে রাখো

একটা লজিক (বা জ্ঞান) পুরো সিস্টেমে একটাই জায়গায় থাকবে।

সাবধান

দেখতে এক রকম হলেই এক করা ঠিক না। দুটো কোড যদি আলাদা কারণে বদলায়, জোর করে এক করলে ভুল abstraction তৈরি হয়। প্রচলিত নিয়ম: একই জিনিস তিনবার লিখতে হলে তখন আলাদা করো (Rule of Three)।

K
Principle 02

KISS — Keep It Simple, Stupid

কোড যতটা সম্ভব সহজ রাখুন।

সফটওয়্যার ডেভেলপমেন্টে সব সময় চেষ্টা করা উচিত যেন সিস্টেম ডিজাইন এবং কোড যতটা সম্ভব সহজ থাকে। অযথাই জটিল লজিক বা ওভার-ইঞ্জিনিয়ারিং করার কোনো মানে নেই। কোড এমন হওয়া উচিত যেন অন্য কোনো ডেভেলপার বা ভবিষ্যতে আপনি নিজে দেখলে খুব সহজেই বুঝতে পারেন যে কোডটি কী কাজ করছে।

বাস্তব উদাহরণ

ঘরের দরজা খুলতে একটা চাবিই যথেষ্ট। তার জায়গায় ফিঙ্গারপ্রিন্ট + পাসওয়ার্ড + ফেস স্ক্যান লাগালে দরজা খোলা কঠিন হয়, নষ্ট হওয়ার জায়গাও বাড়ে — অথচ কাজ একই।

কোডে দেখি

GetMonthNameBad() নিজেই ১২ মাসের array বানায়, তারপর invalid হলে try-এর ভেতরে exception থ্রো করে সাথে সাথে catch করে message রিটার্ন করে। Exception দিয়ে সাধারণ if/else-এর কাজ করানো — পড়তে কঠিন, আর অকারণে ধীর।

KISS.cs · Bad
public string GetMonthNameBad(int monthNumber)
{
    // Unnecessarily complex way to return a month name
    string[] months = { "January", "February", "March", "April", "May", "June", "July", "August", "September", "October", "November", "December" };
    
    try
    {
        if (monthNumber >= 1 && monthNumber <= 12)
        {
            return months[monthNumber - 1];
        }
        else
        {
            throw new Exception("Invalid month");
        }
    }
    catch (Exception ex)
    {
        return ex.Message;
    }
}

GetMonthNameGood() শুরুতেই invalid ইনপুট আটকে দেয় (guard clause), তারপর built-in DateTime-কে দিয়ে মাসের নাম নেয়। ৩ লাইন, এক নজরে বোঝা যায়।

KISS.cs · Good
public string GetMonthNameGood(int monthNumber)
{
    // Simple, built-in, easy to read
    if (monthNumber < 1 || monthNumber > 12)
        return "Invalid month";

    return new DateTime(2000, monthNumber, 1).ToString("MMMM");
পুরো ফাইল দেখুন — KISS.cs

using System;

namespace DesignPrinciples
{
    public class DateHelper
    {
        // ==========================================

        // ==========================================
        public string GetMonthNameBad(int monthNumber)
        {
            // Unnecessarily complex way to return a month name
            string[] months = { "January", "February", "March", "April", "May", "June", "July", "August", "September", "October", "November", "December" };
            
            try
            {
                if (monthNumber >= 1 && monthNumber <= 12)
                {
                    return months[monthNumber - 1];
                }
                else
                {
                    throw new Exception("Invalid month");
                }
            }
            catch (Exception ex)
            {
                return ex.Message;
            }
        }

        // ==========================================
        // ✅ GOOD: Simple and readable (KISS Principle)
        // ==========================================

                return "Invalid month";

            return new DateTime(2000, monthNumber, 1).ToString("MMMM");
        }
    }
}
মনে রাখো

কোড একবার লেখা হয়, কিন্তু পড়া হয় বহুবার — পড়তে সহজ কোডই ভালো কোড।

সাবধান

সহজ মানে অসম্পূর্ণ না — দরকারি validation বা error handling বাদ দেওয়া KISS না। আর ToString("MMMM") চলতি culture অনুযায়ী মাসের নাম দেয়; সবসময় ইংরেজি নাম চাইলে CultureInfo.InvariantCulture দিতে হয়।

Y
Principle 03

YAGNI — You Aren't Gonna Need It

ভবিষ্যতে লাগতে পারে ভেবে আজই কোনো কোড লিখবেন না।

আমরা অনেক সময় ভাবি, "ভবিষ্যতে হয়তো এই ফিচারটি লাগতে পারে, তাই আজকেই এর জন্য কিছু এক্সট্রা ক্লাস বা মেথড লিখে রাখি।" কিন্তু বেশির ভাগ সময়ই সেই ফিচারগুলোর আর দরকার হয় না, ফলে কোডবেস অযথাই বড় এবং জটিল হয়ে যায়। YAGNI প্রিন্সিপাল বলে, বর্তমানে আপনার যে রিকোয়ারমেন্ট আছে, ঠিক ততটুকুই কোড লিখুন।

বাস্তব উদাহরণ

এখনো গাড়ি কেনেননি, কিন্তু বাড়িতে আগেই গ্যারেজ বানিয়ে রাখলেন। জায়গা আর টাকা আটকে থাকল — আর পরে যে গাড়ি কিনবেন, সেটা হয়তো ওই গ্যারেজে ঢুকবেই না।

কোডে দেখি

এখনো কোনো mobile app নেই, তবু RegisterUserFromMobileApp(deviceId) লিখে রাখা হয়েছে। এই কোড এখন কেউ ব্যবহার করে না, কিন্তু maintain আর test করতে হয় — আর আসল requirement এলে সেটা হয়তো সম্পূর্ণ আলাদা হবে।

YAGNI.cs · Bad
public class UserRegistrationBad
{
    public void RegisterUser(string username, string password)
    {
        Console.WriteLine($"User {username} registered.");
    }

    // We don't have a mobile app yet, but we wrote this just in case.
    // This is a waste of time and adds unnecessary code to maintain.
    public void RegisterUserFromMobileApp(string username, string password, string deviceId)
    {
        Console.WriteLine($"User {username} registered from device {deviceId}.");
    }
}

আজকের requirement শুধু সাধারণ registration — তাই শুধু RegisterUser()। Mobile registration তখনই লেখা হবে, যখন সত্যিই দরকার আসবে।

YAGNI.cs · Good
public class UserRegistrationGood
{
    // The current requirement is only simple registration.
    public void RegisterUser(string username, string password)
    {
        Console.WriteLine($"User {username} registered.");
    }

    // We will add mobile registration later ONLY IF the requirement actually comes.

মনে রাখো

আজকের requirement-এর জন্য কোড লেখো, কালকের অনুমানের জন্য না।

সাবধান

YAGNI মানে design খারাপ রাখা না। কোড এমনভাবে লেখো যেন পরে নতুন ফিচার যোগ করা সহজ হয় (clean, OCP মেনে) — শুধু ফিচারটা আগেভাগে বানিয়ো না।

S
Principle 04

SoC — Separation of Concerns

প্রতিটি অংশের কাজ আলাদা রাখুন।

একটি প্রোগ্রামের বিভিন্ন কাজ বা দায়িত্বকে আলাদা আলাদা অংশে ভাগ করাকে Separation of Concerns বলে। যেমন: ডাটাবেস থেকে ডেটা আনার কাজ, ইউজার ইন্টারফেসে ডেটা দেখানোর কাজ এবং বিজনেস লজিক—এগুলো সব আলাদা আলাদা ক্লাস বা মডিউলে থাকা উচিত। এতে একটি অংশে পরিবর্তন আনলে অন্য অংশগুলোর ওপর কোনো প্রভাব পড়ে না।

বাস্তব উদাহরণ

হাসপাতালে রিসেপশন, ডাক্তার আর ফার্মেসি আলাদা। ফার্মেসি নতুন সিস্টেমে গেলে ডাক্তারকে নতুন কিছু শিখতে হয় না — কারণ প্রত্যেকের কাজ নিজের জায়গায়।

কোডে দেখি

OrderProcessorBad.ProcessOrder() একাই validation, database-এ save আর email পাঠানো — তিনটা আলাদা কাজ একসাথে করে। Database বদলালে বা email-এর নিয়ম বদলালে এই একটা মেথডই বারবার এডিট করতে হয়।

SoC.cs · Bad
public class OrderProcessorBad
{
    public void ProcessOrder()
    {
        // 1. Validation Logic
        Console.WriteLine("Validating order...");
        
        // 2. Database Logic
        Console.WriteLine("Saving order to database...");

        // 3. Email Notification Logic
        Console.WriteLine("Sending confirmation email...");
    }
}

OrderValidator, OrderRepository, EmailService — প্রত্যেকে একটা কাজ করে। OrderProcessorGood শুধু তাদের সমন্বয় (coordinate) করে।

SoC.cs · Good
public class OrderValidator
{
    public void Validate() => Console.WriteLine("Validating order...");
}

public class OrderRepository
{
    public void Save() => Console.WriteLine("Saving order to database...");
}

public class EmailService
{
    public void SendEmail() => Console.WriteLine("Sending confirmation email...");
}

public class OrderProcessorGood
{
    private OrderValidator _validator = new OrderValidator();
    private OrderRepository _repository = new OrderRepository();
    private EmailService _emailService = new EmailService();

    public void ProcessOrder()
    {
        // The processor now only coordinates, each class does its own specific job.
        _validator.Validate();
        _repository.Save();
        _emailService.SendEmail();
পুরো ফাইল দেখুন — SoC.cs
SoC.cs
using System;

namespace DesignPrinciples
{
    // ==========================================
    // ❌ BAD: Mixing everything together (SoC Violation)
    // ==========================================
    public class OrderProcessorBad
    {
        public void ProcessOrder()
        {
            // 1. Validation Logic
            Console.WriteLine("Validating order...");
            
            // 2. Database Logic
            Console.WriteLine("Saving order to database...");

            // 3. Email Notification Logic
            Console.WriteLine("Sending confirmation email...");
        }
    }

    // ==========================================
    // ✅ GOOD: Separating the concerns (SoC Principle)
    // ==========================================
    
    public class OrderValidator
    {
        public void Validate() => Console.WriteLine("Validating order...");
    }

    public class OrderRepository
    {
        public void Save() => Console.WriteLine("Saving order to database...");
    }

    public class EmailService
    {
        public void SendEmail() => Console.WriteLine("Sending confirmation email...");
    }

    public class OrderProcessorGood
    {
        private OrderValidator _validator = new OrderValidator();
        private OrderRepository _repository = new OrderRepository();
        private EmailService _emailService = new EmailService();

        public void ProcessOrder()
        {
            // The processor now only coordinates, each class does its own specific job.
            _validator.Validate();
            _repository.Save();
            _emailService.SendEmail();
        }
    }
}
মনে রাখো

প্রতিটা অংশ একটা concern দেখবে — UI, business logic, data আলাদা।

সাবধান

Good ভার্সনেও ক্লাসগুলো ভেতরে new দিয়ে তৈরি হচ্ছে। আরও ভালো হলো constructor দিয়ে inject করা — সেটা SOLID-এর Dependency Inversion। বাস্তব উদাহরণ: MVC, layered architecture (UI → Business → Data), HTML / CSS / JS আলাদা রাখা।

তুলনা — কখন কোনটা

কোড লেখার সময় নিজেকে এই প্রশ্নগুলো করুন।

নীতিনিজেকে প্রশ্ন করোভাঙার লক্ষণসমাধান
DRYএই লজিক কি আর কোথাও আছে?একই কোড কপি-পেস্ট; এক জায়গা বদলালে আরেক জায়গাও বদলাতে হয়কমন অংশ একটা মেথড / ক্লাসে নিয়ে যাও
KISSএর চেয়ে সহজভাবে কি লেখা যায়?অকারণ nested logic, exception দিয়ে flow control, built-in থাকতে নিজে বানানোGuard clause, built-in ফাংশন, ছোট মেথড
YAGNIএটা কি আজই লাগবে?"পরে লাগতে পারে" ভেবে লেখা কোড, যা কেউ call করে নামুছে দাও; দরকার হলে তখন লেখো
SoCএই ক্লাস কি একাধিক ধরনের কাজ করছে?এক মেথডে validation + database + emailপ্রতিটা concern আলাদা ক্লাস / layer-এ
DRY ↔ KISS: অতিরিক্ত DRY করতে গিয়ে সবকিছু এক জেনেরিক abstraction-এ ঢোকালে কোড জটিল হয়ে KISS ভাঙে। একটু repetition অনেক সময় ভুল abstraction-এর চেয়ে ভালো।
KISS ↔ YAGNI: দুটো একই পরিবারের — দুটোই over-engineering থামায়। KISS বলে যা লিখছ সহজ রাখো, YAGNI বলে যা দরকার নেই লিখো না।
SoC ↔ SRP: একই ধারণা, ভিন্ন স্কেলে। SoC বড় স্কেলে (layer, module — UI / business / data), SOLID-এর SRP ক্লাস লেভেলে (একটা ক্লাস, বদলানোর একটা কারণ)।
ইন্টারভিউর জন্য এক লাইনে
  • DRY — Every piece of knowledge should have a single source of truth.
  • KISS — Prefer the simplest solution that works; code is read more than written.
  • YAGNI — Build for today's requirement, not for guesses about tomorrow.
  • SoC — Each part of the system handles one concern, so changes stay local.
