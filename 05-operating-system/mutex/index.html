1Race condition কী

shared data + একাধিক thread + অন্তত একটা write + কোনো সমন্বয় নেই

Program-এর ফল যখন thread গুলোর কে কখন চলল তার ওপর নির্ভর করে — তখন সেটা race condition। সবচেয়ে সাধারণ চেহারা: দুই thread একই variable পড়ে-বদলে-লেখে, আর মাঝখানে কেউ কাউকে আটকায় না। ফলে একটার লেখা আরেকটা মুছে দেয় — lost update।

শেয়ার করা খাতা: দুজন একই খাতায় "মোট = 5" দেখে নিজের মাথায় +1 করে 6 লিখল। দুজনই 5 দেখেছিল, তাই খাতায় শেষে 6 — অথচ দুটো +1 হলে 7 হওয়ার কথা। কেউ ভুল করেনি; ভুলটা হলো পড়া আর লেখার মাঝে অন্যজন ঢুকে যাওয়া।

Race condition-এর চারটা উপাদান (সবগুলো লাগে):
  1. Shared mutable data — একাধিক thread-এর কাছে একই memory।
  2. Concurrent access — thread গুলো একই সময়ে (multi-core) বা পালা করে (context switch) চলছে।
  3. অন্তত একটা write — সবাই শুধু পড়লে সমস্যা নেই।
  4. কোনো synchronisation নেই — lock, atomic, বা অন্য ব্যবস্থা।

counter++ একটা step না — তিনটা

C-তে এক লাইন, কিন্তু CPU-র কাছে তিনটা আলাদা instruction: memory থেকে register-এ LOAD, register-এ ADD, আবার memory-তে STORE। Context switch (বা অন্য core) এই তিনটার যেকোনো দুইটার মাঝে ঘটতে পারে।

x86-64 styleillustrative
mov  eax, [counter]    ; LOAD   memory → register
add  eax, 1            ; ADD    register-এ +1
mov  [counter], eax    ; STORE  register → memory

সাধারণ x86-64 compiler output-এর ধাঁচ — এই পাতার জন্য লেখা, নির্দিষ্ট কোনো build থেকে নেওয়া না।

এই Mac-এ (Apple M1, arm64) — clang -O0 -Sreal output
ldr  w8, [x9, _counter@PAGEOFF]   ; LOAD
add  w8, w8, #1                   ; ADD
str  w8, [x9, _counter@PAGEOFF]   ; STORE

compiler-এর আসল output থেকে নেওয়া (ঠিকানা আনার adrp লাইন আর ; comment বাদে/যোগে)। Instruction-এর নাম আলাদা, কিন্তু তিনটা ধাপ একই।

দুই thread interleave করলে — lost update

counter = 5, T1 আর T2 প্রত্যেকে একবার counter++ চালায়। সঠিক ফল 5 + 1 + 1 = 7। নিচের schedule-এ দুজনই 5 পড়ে ফেলেছে, তাই দুজনই 6 লেখে:

#কে · কী করলT1 regT2 regcounter
1T1 LOAD — counter পড়ল5—5
2T2 LOAD — এখনো 5, কারণ T1 কিছু লেখেনি555
3T1 ADD655
4T2 ADD665
5T1 STORE666
6T2 STORE — T1-এর লেখা মুছে দিল666 ✗ (হওয়ার কথা 7)

Single core-এ এটা context switch থেকে হয়; multi-core-এ দুই core সত্যিই একই সময়ে চলে বলে আরও সহজে হয়। দুই ক্ষেত্রেই ফল এক। নিচের animation-এ এই schedule নিজে চালাতে পারবে।

প্রমাণ — আসল C program, আসল output

দুইটা thread, প্রত্যেকে shared int এক মিলিয়ন বার বাড়ায়; সঠিক ফল 2,000,000। নিচের সবকিছু এই Mac-এ (Apple M1, macOS, Apple clang 15) clang -O0 -pthread দিয়ে compile করে চালানো — প্রতিটা output আসল।

race.c — কোনো lock নেইভুল ফল
#include <pthread.h>
#include <stdio.h>

#define N 1000000
int counter = 0;                       // shared, কোনো সুরক্ষা নেই

void *work(void *arg) {
    for (int i = 0; i < N; i++)
        counter++;                     // load, add, store
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, work, NULL);
    pthread_create(&t2, NULL, work, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d (expected %d)\n", counter, 2 * N);
    return 0;
}

সময় কত লাগল — সৎ ব্যাখ্যা

প্রতিটা version ৫ বার চালিয়ে wall-clock সময় (process শুরু থেকে শেষ, shell থেকে মাপা, তাই ছোট একটা fixed overhead আছে):

এই সংখ্যা কী বলে, কী বলে না:
  • No-lock version প্রায় ৮–১০ গুণ দ্রুত — কিন্তু ভুল। "Fast but wrong" কোনো optimisation না, bug। Correctness আগে, speed পরে।
  • এটা একটা worst-case micro-benchmark: দুই thread শুধু ওই একটা variable নিয়েই লড়ছে, অন্য কোনো কাজ নেই। বাস্তব program-এ lock ধরা সময়ের তুলনায় বাকি কাজ অনেক বেশি, তাই এত বড় ব্যবধান দেখা যায় না।
  • এখানে atomic, mutex-এর চেয়ে ধীর এসেছে — এটা সাধারণ নিয়ম না। এই ঘটনা এই machine, এই workload আর দুই thread-এর পুরো-contention-এর ফল; আনুমানিক কারণ, দুই core একই cache line বারবার কেড়ে নিচ্ছে। Contention কম হলে uncontended atomic সাধারণত mutex-এর চেয়ে অনেক সস্তা। অন্য hardware-এ আলাদা ফল আসতে পারে — আমি শুধু এই machine-এর সংখ্যা দেখিয়েছি।
  • -O2-তে একই unlocked program কখনো 2,000,000, কখনো 1,000,000 দিয়েছে (আমার দুই run-এ) — optimiser loop-এর ভেতর counter-কে register-এ রেখে একবারে লিখে দেয়। Data race-এ C-এর behaviour undefined, তাই compiler যা খুশি করতে পারে; "আমার machine-এ ঠিক চলছে" কোনো প্রমাণ না।

2Critical section আর তার ৩টা শর্ত

যে code shared data ছোঁয়, সেটাকে "একবারে একজন" করে দাও

Critical section = code-এর সেই অংশ যা shared resource পড়ে-বদলায় এবং যেটা একসাথে একাধিক thread চালালে ভুল হয়। Mutex-এর কাজ হলো এই অংশের চারপাশে দরজা বসানো।

while (true) {
    lock(&m);          // entry section   — ঢোকার অনুমতি চাও
        counter++;     // CRITICAL SECTION — shared data ছোঁয়া
    unlock(&m);        // exit section    — অন্যকে ঢুকতে দাও
    do_other_work();   // remainder section — shared data নেই
}

সমাধানকে যে ৩টা শর্ত মানতে হয়

1. Mutual Exclusion

একসময়ে critical section-এ সর্বোচ্চ একটা thread। এটাই মূল শর্ত — এটা ভাঙলে race ফিরে আসে।

2. Progress

Section ফাঁকা থাকলে আর কেউ ঢুকতে চাইলে, বাইরের কেউ (যে ঢুকতে চায় না) তাকে আটকাতে পারবে না; কে ঢুকবে সেই সিদ্ধান্ত অনির্দিষ্টকাল ঝুলে থাকবে না।

3. Bounded Waiting

কেউ ঢোকার অনুরোধ করার পর, অন্যরা কতবার তার আগে ঢুকতে পারবে তার একটা সীমা আছে — নইলে কেউ starve করে।

Interview-এ যেভাবে বলবে: "Mutual exclusion = safety, progress আর bounded waiting = liveness।" একটা lock যদি সবাইকে চিরকাল আটকে রাখে, সেটা mutual exclusion মানে — কিন্তু progress মানে না। আর যদি lock unfair হয় (কোনো thread বারবার হেরে যেতে পারে) তাহলে bounded waiting ভাঙে — সব practical mutex এটা কঠোরভাবে দেয় না; FIFO queue বা ticket lock দিলে দেয়। Peterson's algorithm software দিয়ে এই তিনটাই দেয় (শুধু দুই thread), কিন্তু আধুনিক CPU-র reordering-এ memory barrier ছাড়া ভাঙে — তাই বাস্তবে hardware atomic instruction ব্যবহার হয়।

3Mutex কীভাবে কাজ করে

lock / unlock · owner আছে · ভেতরে একটা atomic instruction

Mutex (mutual exclusion lock) একটা object যার দুইটা অবস্থা: unlocked বা locked। lock() ফাঁকা পেলে নিয়ে নেয়; আগে থেকে locked থাকলে অপেক্ষা করে। unlock() ছেড়ে দেয় এবং (দরকারে) একজন অপেক্ষাকারীকে সুযোগ দেয়।

Mutex-এর ভেতরের state (ধারণাগত)illustrative
struct mutex {
    int     locked;      // 0 = ফাঁকা, 1 = কারো হাতে
    thread *owner;       // কে ধরে আছে
    queue   waiters;     // sleep করা thread-এর লাইন
};

Ownership: যে thread lock() করেছে শুধু সেই-ই unlock() করতে পারে। অন্য thread unlock করতে গেলে error (error-checking mutex EPERM দেয়) বা undefined behaviour।

Semaphore-এর সাথে পার্থক্য: semaphore-এর কোনো owner নেই — এক thread wait() করে, অন্য thread post() করতে পারে। তাই semaphore "ইঙ্গিত দেওয়ার" (signalling), mutex "দরজায় তালা"-র (locking) জন্য। বিস্তারিত নিচের তুলনায়।

"Check, তারপর set" — এই দুই ধাপেও race আছে

Mutex বানানোর সবচেয়ে সরল চেষ্টা: if (!locked) locked = true;। কিন্তু এটাও দুইটা ধাপ — flag পড়া, তারপর flag লেখা। মাঝে অন্য thread ঢুকলে দুজনই "ফাঁকা" দেখে দুজনই ঢুকে পড়ে। সমস্যাটা counter++-এর সমস্যারই হুবহু একই — lock নিজেই একটা shared variable! নিচে Step চাপো:

সমাধান — hardware-এর atomic instruction

"পড়ো আর লেখো" যদি একটাই অবিভাজ্য instruction হয়, মাঝে কেউ ঢুকতে পারে না। CPU এটা দেয়:

Test-and-Set (TAS) আর Compare-and-Swap (CAS):
  • TAS: একই step-এ পুরোনো মান ফেরত দেয় এবং flag = 1 করে দেয়। পুরোনো মান 0 পেলে তুমিই lock পেয়েছ; 1 পেলে অন্য কারো হাতে।
  • CAS(addr, expected, new): *addr == expected হলেই শুধু new লেখে, আর সফল হলো কি না জানায়। Mutex-এর lock = CAS(&state, 0, 1)।
  • x86-এ: lock cmpxchg, xchg [mem], reg (memory operand থাকলে implicit lock), lock xadd। lock prefix মানে ওই memory-তে read-modify-write কোনো core-এর মাঝখানে ঢোকার সুযোগ ছাড়া শেষ হয়।
  • ARM-এ: load-exclusive / store-exclusive জোড়া (ldxr/stxr), বা নতুন version-এ single-instruction atomics (যেমন cas, ldadd)।

Cache-এর দিক থেকে (সরলীকৃত): core ওই cache line-এর exclusive মালিকানা নিয়ে read-modify-write শেষ করে; অন্য core-কে অপেক্ষা করতে হয়। তাই contended atomic ব্যয়বহুল — line দুই core-এর মধ্যে ঘুরতে থাকে।

Linux-এ sleeping mutex — futex

Linux-এ pthread mutex futex (fast userspace mutex) দিয়ে বানানো। মূল ধারণা: contention না থাকলে kernel-এ যাওয়াই লাগে না।

দুটো পথ:
  • Fast path (uncontended): lock() = user space-এ একটা atomic CAS (0 → 1)। unlock() = একটা atomic লেখা। কোনো system call নেই — তাই মাত্র কয়েক nanosecond।
  • Slow path (contended): CAS ব্যর্থ হলে thread futex(FUTEX_WAIT) system call করে — kernel দেখে "ওই ঠিকানার মান এখনো আমি যা ভেবেছিলাম?", হ্যাঁ হলে thread-কে sleep করিয়ে ওই ঠিকানার wait queue-তে রাখে।
  • Unlock-এ: যদি কেউ অপেক্ষা করে (state ≠ "locked, no waiters"), futex(FUTEX_WAKE, 1) একজনকে জাগায়। জেগে সে আবার lock নেওয়ার চেষ্টা করে — ইতিমধ্যে আরেকজন নিয়ে নিলে আবার sleep।

macOS-এ futex নেই; সেখানে আলাদা kernel API একই কাজ করে। উপরের real run-গুলো macOS-এ, futex ধারণাটা Linux-এর।

সরলীকৃত futex mutex (Drepper-এর ধাঁচ)illustrative — not run
// state: 0 = unlocked | 1 = locked, কেউ অপেক্ষায় নেই | 2 = locked, অপেক্ষাকারী আছে
void lock(int *s) {
    int c = cmpxchg(s, 0, 1);          // fast path: একটা atomic op, syscall নেই
    if (c != 0) {                       // কারো হাতে
        do {
            if (c == 2 || cmpxchg(s, 1, 2) != 0)
                futex_wait(s, 2);       // *s == 2 থাকলে kernel-এ sleep
        } while ((c = cmpxchg(s, 0, 2)) != 0);
    }
}
void unlock(int *s) {
    if (atomic_dec(s) != 1) {           // পুরোনো মান 1 না হলে কেউ অপেক্ষায়
        *s = 0;
        futex_wake(s, 1);               // একজনকে জাগাও
    }
}

Memory visibility — lock শুধু "একজন" না, "দেখতে পাওয়া"-ও

CPU আর compiler performance-এর জন্য instruction reorder করে, আর প্রতিটা core-এর নিজের cache/store buffer থাকে। তাই এক thread-এর লেখা অন্য thread সঙ্গে সঙ্গে দেখবে — এর নিশ্চয়তা নেই। Mutex এই নিশ্চয়তাও দেয়:

  • unlock() = release: critical section-এর সব write unlock-এর আগে সম্পূর্ণ হয়েছে বলে ধরা হয়, কোনো লেখা unlock-এর পরে সরে যেতে পারে না।
  • lock() = acquire: lock পাওয়ার পরের সব read আর write lock-এর পরেই হয়; আগে সরে যেতে পারে না।
  • একই mutex-এ T1-এর unlock এবং T2-এর পরের lock-এর মধ্যে তৈরি হয় happens-before সম্পর্ক — তাই T1 critical section-এ যা লিখেছে T2 ঢুকে তা নিশ্চিতভাবে দেখবে।
  • এই কারণেই "সব thread-এ একই mutex" নিয়ম জরুরি: আলাদা mutex দিয়ে বা lock ছাড়া পড়লে এই গ্যারান্টি পাও না। (x86 তুলনামূলক শক্ত ordering দেয়, ARM — এই Mac-এর M1 — দুর্বল; তাই ARM-এ memory-order ভুল আগে ধরা পড়ে।)

    5Common ভুল

    Mutex নিজে সহজ — ভুল হয় ব্যবহারে

    1. Unlock ভুলে যাওয়া

    Early return বা exception-এ unlock() বাদ পড়লে lock চিরকাল locked, বাকি সবাই ঝুলে। সমাধান: scope-ভিত্তিক release — C++ std::lock_guard (RAII), C# lock, Java try/finally (বা synchronized), Go defer mu.Unlock()।

    2. Lock-এর scope বেশি বড় (coarse)

    সব কিছুর ওপর একটা বড় lock = সবাই লাইনে দাঁড়ায়, multi-core-এর সুবিধা শেষ (contention)। উল্টোদিকে খুব ছোট/ভুল জায়গায় lock = race ফিরে আসে। লক্ষ্য: যতটুকু shared data ছোঁয়, ঠিক ততটুকু।

    3. Lock ধরে I/O বা ধীর কাজ

    Lock ধরে network call, disk, sleep বা অজানা callback চালালে সেই সময় সবাই আটকে। হিসাব/I/O lock-এর বাইরে করো, শুধু shared state-এর update ভেতরে।

    4. Deadlock — উল্টো ক্রমে lock

    T1: A তারপর B; T2: B তারপর A → দুজন চিরকাল অপেক্ষা। সমাধান: সব জায়গায় একই lock order। পুরো গল্প, Coffman-এর ৪ শর্ত: Deadlock গাইড →

    5. Non-recursive mutex-এ আবার lock (self-deadlock)

    Thread নিজের ধরা mutex আবার চাইলে নিজেই নিজের জন্য অপেক্ষা (default pthread mutex-এ undefined/hang)। Recursive (reentrant) mutex — pthread PTHREAD_MUTEX_RECURSIVE, Java synchronized/ReentrantLock, C# lock — একই thread-কে আবার ঢুকতে দেয় ও hold count রাখে। তবে এটা design-এর গন্ধ ঢেকে রাখতে পারে।

    6. অন্য thread থেকে unlock

    Mutex-এর owner আছে: যে lock করেছে সেই unlock করবে। অন্যজন করলে error বা undefined behaviour। "এক thread আটকাবে, অন্য thread ছাড়বে" দরকার হলে সেটা semaphore-এর কাজ।

    7. Priority inversion

    Low-priority L mutex ধরে আছে; High-priority H সেটা চায় → H ঘুমায়। এরপর Medium M এসে L-কে preempt করে চলতে থাকে → L unlock করতে পারে না → H অনির্দিষ্টকাল আটকে, যদিও H-ই সবচেয়ে জরুরি। বিখ্যাত ঘটনা: Mars Pathfinder (1997) — মহাকাশযানে বারবার system reset; কারণ ছিল এই inversion। সমাধান: priority inheritance (L সাময়িকভাবে H-এর priority পায়) বা priority ceiling।

    8. Lock convoy

    অনেক thread একই hot lock চায়, প্রতিটা handoff-এ sleep/wake context switch লাগে — throughput ধসে যায়, যদিও কেউ deadlock-এ নেই। প্রতিকার: critical section ছোট করা, lock ভাগ করা (sharding), read-mostly হলে read-write lock বা atomic।

    প্রতিটা operation আলাদা lock-এ — তবু race

    Mutex শুধু একটা critical section-এর ভেতরটা রক্ষা করে। দুটো ধাপ (check, তারপর act) যদি আলাদা আলাদা lock নেয়, মাঝখানে ফাঁক থেকে যায়। এটা check-then-act race:

    ভুল — প্রতিটা method নিজে thread-safeillustrative — not run
    // balance = 600; T1 আর T2 দুজনই 500 তুলতে চায়
if (account.getBalance() >= 500) {   // synchronized — lock নিয়ে পড়ে ছেড়ে দিল
    account.withdraw(500);            // synchronized — আবার আলাদা lock
}
// দুজনই 600 দেখল → দুজনই withdraw → balance = -400
    ঠিক — check + act একই lock-এillustrative — not run
    synchronized (account) {              // একটাই critical section
    if (account.getBalance() >= 500) {
        account.withdraw(500);        // reentrant, তাই ভেতরে আবার ঢুকতে পারে
    }
}
// অথবা একটা atomic operation: account.tryWithdraw(500)

    QInterview-এ যা আসে

    Race condition আর data race — একই জিনিস?
    • Data race: দুই thread একই memory location-এ একই সময়ে access করে, অন্তত একটা write, আর কোনো synchronisation নেই। এটা একটা সংকীর্ণ, যান্ত্রিক সংজ্ঞা; C/C++/Java-র memory model-এ এর আলাদা নিয়ম আছে (C/C++-এ undefined behaviour)।
    • Race condition: ফল timing / ক্রমের ওপর নির্ভর করে — বড় ধারণা, logic-এর সমস্যা।
    • Data race ছাড়াও race condition হয়: প্রতিটা access আলাদা lock-এ, তাই data race নেই — কিন্তু check-then-act-এর মাঝে ফাঁক (ওপরের balance উদাহরণ)। আবার data race সাধারণত race condition-এর কারণ, আর "benign data race" ভেবে ছেড়ে দেওয়া C/C++-এ ঝুঁকিপূর্ণ।
    Mutex আর semaphore-এর পার্থক্য? Binary semaphore কি mutex?
    • Ownership: mutex-এর owner আছে, শুধু সে-ই unlock করে। Semaphore-এ নেই — এক thread wait, অন্য thread post করতে পারে।
    • Purpose: mutex = mutual exclusion (locking); semaphore = signalling আর resource গোনা।
    • Binary semaphore ≠ mutex: মান দুটো (0/1) বলেই একই না। Binary semaphore-এ ownership নেই, তাই priority inheritance দেওয়া যায় না (কাকে boost করবে?), ভুল thread-এর post-ও আটকানো যায় না; recursive locking-ও হয় না। Mutex চাইলে mutex-ই নাও।
    Single core-এ spinlock খারাপ কেন?

    কারণ spinner যতক্ষণ CPU-তে ঘুরছে, lock-holder চলতেই পারছে না (core মাত্র একটা, সে preempted)। Spinner তার পুরো time slice শুধু ঘুরে নষ্ট করে, তারপর scheduler holder-কে চালায় — spin পুরোটাই বৃথা। Multi-core-এ holder অন্য core-এ চলতে থাকে, তাই অল্প spin কাজে আসে। Kernel spinlock ধরা অবস্থায় preemption বন্ধ রাখে যাতে holder মাঝপথে preempt না হয় (মনে থাকা তথ্য, এখানে যাচাই করিনি: uniprocessor kernel build-এ spinlock প্রায় শুধু preemption বন্ধ করাতেই নেমে আসে)।

    Mutex কীভাবে thread-কে block করে?
    • lock() প্রথমে user space-এ atomic CAS করে (fast path)। সফল হলে কোনো kernel call নেই।
    • ব্যর্থ হলে (কেউ ধরে আছে) thread system call করে kernel-কে বলে "এই ঠিকানা বদলালে আমাকে ডেকো" — Linux-এ futex(FUTEX_WAIT)। Kernel thread-কে sleeping/blocked করে wait queue-তে রাখে, CPU অন্য runnable thread-কে দেয়।
    • unlock() flag ছেড়ে, কেউ অপেক্ষায় থাকলে futex(FUTEX_WAKE) দিয়ে একজনকে runnable করে। সে CPU পেলে আবার lock নেওয়ার চেষ্টা করে।
    • তাই block হওয়া মানে busy-wait না; thread scheduler-এর run queue থেকে সরে যায়।
    i++ কি atomic?

    না। এটা load → add → store, আর মাঝে অন্য thread ঢুকতে পারে — ওপরের real run-এ প্রায় অর্ধেক increment হারিয়েছে। এমনকি x86-এ add [mem], 1 এক instruction হলেও, lock prefix ছাড়া multi-core-এ সেটা atomic না (ভেতরে read-modify-write আলাদা ধাপ)। Java-তে volatile int-এর i++-ও atomic না — AtomicInteger.incrementAndGet() বা synchronized। C#-এ Interlocked.Increment, C11-এ atomic_fetch_add। (Java-তে 32-bit int একটা read বা write atomic, কিন্তু ++ যৌগিক।)

    Mutex ধরা thread crash করলে কী হয়?
    • পুরো process ভেঙে গেলে মেমরিসহ mutex-ও শেষ — সমস্যা নেই। সমস্যা: thread শেষ হয়ে গেল lock ধরা অবস্থায় (বা process-shared mutex-এ অন্য process মরল) — lock চিরকাল locked থাকে, বাকিরা ঝুলে।
    • POSIX robust mutex (PTHREAD_MUTEX_ROBUST): owner মরলে পরের lock() EOWNERDEAD ফেরত দেয়; নতুন owner shared data মেরামত করে pthread_mutex_consistent() ডাকে, তারপর স্বাভাবিক চলে। মেরামত না করে unlock করলে mutex অব্যবহারযোগ্য (ENOTRECOVERABLE)।
    • Java/C#-এ synchronized/lock exception হলেও release হয়; তবে data অর্ধেক-বদলানো থেকে যেতে পারে — lock ছাড়া ≠ state ঠিক।
    Priority inversion কী? কীভাবে ঠেকায়?

    High-priority task এমন mutex চাইছে যেটা low-priority task ধরে আছে; Medium-priority task low-কে preempt করে চলতে থাকায় low unlock করতে পারে না, ফলে High আটকে থাকে Medium-এর কারণে — priority উল্টে গেছে। Mars Pathfinder-এ এটাই ঘটেছিল (পরে priority inheritance চালু করে সারানো হয়)। সমাধান: priority inheritance (holder সাময়িক waiter-এর priority পায়, POSIX PTHREAD_PRIO_INHERIT), priority ceiling, বা critical section ছোট রাখা / lock-free।

    Reentrant (recursive) lock কী? কখন সমস্যা?

    একই thread বারবার একই lock নিতে পারে; lock একটা hold count রাখে, যতবার নিয়েছে ততবার unlock করলে তবেই অন্যরা পায়। Java synchronized আর ReentrantLock, C# lock reentrant; Go-র sync.Mutex আর default pthread mutex না (আবার lock = self-deadlock)। সমস্যা: reentrancy-তে ঢোকা method দেখতে পারে অর্ধেক-বদলানো state (invariant সাময়িক ভাঙা), আর design-এর ভুল (কে কোন lock ধরে আছে) চাপা পড়ে যায়।

    কখন mutex না লাগিয়ে atomic-ই যথেষ্ট?
    • যখন সুরক্ষা দিতে হবে একটা মাত্র variable (counter, flag, pointer, reference count) আর operation-টা এক atomic ধাপে হয় (fetch-add, CAS, exchange)।
    • একাধিক variable নিয়ে invariant থাকলে (যেমন "balance আর history একসাথে বদলাবে") atomic যথেষ্ট না — mutex লাগে, নইলে মাঝের অবস্থা দেখা যায়।
    • Lock-free code লেখা কঠিন (ABA সমস্যা, memory ordering); সাধারণ ক্ষেত্রে mutex-ই সহজ ও নিরাপদ, আর uncontended mutex ইতিমধ্যে সস্তা (user-space fast path)।
    Race কীভাবে ধরবে? (ThreadSanitizer)

    Race ধরা কঠিন কারণ ফল অনির্দিষ্ট; run-এ ধরা পড়লেও না-ও পড়তে পারে। তাই dynamic race detector: C/C++ (clang/gcc) -fsanitize=thread (ThreadSanitizer), Go -race, Valgrind-এর Helgrind/DRD (আমার জানা মতে, এগুলো চালাইনি)। TSan-এর মূল সুবিধা: race বাস্তবে ফল ভুল না করলেও দুই access-এর মাঝে happens-before নেই দেখলেই রিপোর্ট করে। এই পাতার race.c এই Mac-এ clang -O0 -g -pthread -fsanitize=thread দিয়ে চালিয়ে পাওয়া আসল report:

    #0 work race.c:9 (race_tsan:arm64+0x100003d40)

    Spinlock বনাম sleeping mutex — কোনটা কখন?

    অপেক্ষা context switch-এর খরচের চেয়ে কম হবে মনে হলে spin (ছোট section, multi-core, holder এখন চলছে)। অপেক্ষা লম্বা বা অনিশ্চিত হলে sleep। বাস্তবে hybrid — আগে অল্প spin, তারপর sleep (adaptive mutex)। User-space application-এ সাধারণত library-র mutex নাও (সে এটা জানে); নিজে spinlock লিখো না — holder preempt হলে spinner CPU পোড়াবে। Kernel-এর interrupt context-এ sleep নিষিদ্ধ, তাই সেখানে spinlock-ই একমাত্র উপায়।
