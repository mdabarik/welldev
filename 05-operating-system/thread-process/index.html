1Process কে তৈরি করে?

Kernel বানায় — তবে প্রায় সবসময় আরেকটা process-এর অনুরোধে

Process বানাতে পারে শুধু kernel। কারণ এর জন্য kernel memory-তে নতুন data structure আর নতুন page table লাগে, আর user mode-এর code সেগুলো ছুঁতেই পারে না। তবে kernel নিজে থেকে কোনো app চালায় না। একটা চলমান process (parent) system call করে চায়, তখন kernel বানায়। ব্যতিক্রম একটাই: boot-এর শেষে kernel নিজেই PID 1 চালায়, আর পরের সব process তার বংশধর।

Linux: fork() + exec(), দুই ধাপে। fork() parent-এর একটা copy বানায়, নতুন PID সহ। তারপর child execve() করে সেই copy-র ভেতরে নতুন program load করে, PID একই থাকে। Shell এভাবেই ls চালায়।

glibc-এর fork() ভেতরে clone() system call ব্যবহার করে। posix_spawn() আর vfork() copy এড়িয়ে আরও দ্রুত নতুন program চালানোর পথ।

Windows: CreateProcess(), এক ধাপে। একটা call-এই নতুন process বানায় আর নতুন .exe load করে। ভেতরে যায় NtCreateUserProcess-এ। Windows-এ fork-এর মতো "নিজের copy বানাও" ধরনের সাধারণ API নেই।

দুই OS-এই কাজটা শেষ পর্যন্ত kernel করে। User-space library শুধু অনুরোধটা পৌঁছে দেয়।

spawn.c — shell যা করে, ছোট করে
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();          // kernel: নতুন task_struct, mm copy (COW)
    if (pid < 0) { perror("fork"); return 1; }

    if (pid == 0) {              // child: এখানে fork() 0 ফেরত দেয়
        char *argv[] = {"ls", "-l", NULL};
        execvp("ls", argv);      // সফল হলে আর ফেরে না, memory পুরো বদলে যায়
        perror("exec");          // এখানে আসা মানে exec fail
        _exit(127);
    }

    int status;                  // parent: fork() child-এর PID ফেরত দেয়
    waitpid(pid, &status, 0);    // child শেষ হওয়া পর্যন্ত ঘুম, zombie-ও পরিষ্কার
    printf("child %d exited: %d\n", pid, WEXITSTATUS(status));
    return 0;
}

মনে রাখার মতো
  • fork() একবার call হয়, কিন্তু দুইবার ফেরে: parent-এ child-এর PID, child-এ 0।
  • exec() নতুন process বানায় না। একই PID রেখে program বদলায়, আর সফল হলে ফেরে না।
  • Child শেষ হলে parent wait() না করা পর্যন্ত সে zombie থাকে, exit status রাখার জন্য। Parent আগে মারা গেলে orphan child-কে PID 1 (বা subreaper) নিজের করে নেয়।
  • Multi-threaded process fork করলে child-এ শুধু calling thread থাকে। তাই fork-এর পর সাধারণত সাথে সাথেই exec করা হয়।

2Thread কে তৈরি করে?

Process-এর একটা thread চায়, kernel বানায়, একই address space-এর ভেতরে

Thread-ও বানায় kernel। Process-এর যেকোনো চলমান thread (শুধু main thread না) একটা library function ডাকে, library system call করে। Linux kernel-এর চোখে thread আর process-এর মধ্যে মৌলিক কোনো পার্থক্য নেই: দুটোই clone() দিয়ে বানানো task। পার্থক্য শুধু flag-এ, মানে নতুন task parent-এর কোন জিনিসগুলো share করবে।

pthread_create() ভেতরে কী করে (glibc NPTL, Linux)
  1. mmap() দিয়ে নতুন stack নেয়। আকার default-এ সাধারণত 8 MB, তবে সেটা virtual, RAM তখনই লাগে না। নিচে একটা guard page থাকে। Stack-এর মাথায় glibc নিজের user-space TCB (struct pthread) আর TLS রাখে।
  2. clone() ডাকে (নতুন glibc-এ clone3()), এই flag-গুলো দিয়ে: CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID।
  3. Kernel নতুন task_struct আর 16 KB kernel stack বানায়, mm/files/sighand share করে, নতুন TID দেয়। TGID হয় process-এর PID। তারপর task-টা run queue-তে যায়।
  4. নতুন thread নিজের stack-এ শুরু হয় আর তোমার function চালায়।
threads.c · gcc threads.c -pthread
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

void *worker(void *arg) {
    printf("worker: pid=%d tid=%ld\n", getpid(), syscall(SYS_gettid));
    return NULL;
}

int main(void) {
    pthread_t t;
    printf("main:   pid=%d tid=%ld\n", getpid(), syscall(SYS_gettid));
    pthread_create(&t, NULL, worker, NULL);  // mmap stack + clone()
    pthread_join(t, NULL);
    return 0;
}

3Main thread কী, কে তৈরি করে?

Process তৈরির সাথে সাথেই kernel প্রথম thread-টাও বানিয়ে দেয়

Main thread বানানোর জন্য কেউ আলাদা করে "create thread" ডাকে না। fork()-এ kernel যে নতুন task বানায়, সেটাই নতুন process-এর একমাত্র thread। এরপর execve() সেই thread-কে নতুন program-এর শুরুতে বসিয়ে দেয়। এজন্য main thread-এর TID আর process-এর PID একই, তাকে বলে thread group leader। Windows-এ CreateProcess-এর ভেতরেই kernel প্রথম thread-টা বানায়।

execve() ভেতরে কী করে (kernel)
  1. File-এর ELF header পড়ে। পুরনো address space ফেলে দেয়। Process-এ অন্য thread থাকলে সেগুলোও শেষ হয়ে যায়।
  2. নতুন mm_struct আর page table বানায়। text, data, bss segment map করে, তবে RAM-এ তখনই load করে না (demand paging, অংশ ৮)।
  3. Binary dynamic হলে PT_INTERP দেখে ld-linux-x86-64.so.2-ও map করে।
  4. Stack VMA বানিয়ে argv, envp, auxv সাজায় (পাশের ছবি)।
  5. Thread-এর saved register-এ RIP = entry point (ld.so-র, বা static হলে ELF-এর e_entry) আর RSP = argc-এর ঠিকানা বসায়। System call থেকে "ফেরার" সময় thread সরাসরি নতুন program-এ পৌঁছে যায়।

এরপর ld.so shared library load আর relocation করে, তারপর AT_ENTRY-তে থাকা _start-এ যায়। _start → __libc_start_main() → main()। main return করলে সেই মান দিয়ে exit() হয়, আর exit_group সব thread শেষ করে দেয়।

Main thread নিয়ে যা জানা দরকার
  • main() return করলে পুরো process শেষ হয়ে যায়, worker thread-এর কাজ বাকি থাকলেও। Main-এ pthread_exit() দিলে শুধু main thread থামে, বাকিরা চলতে থাকে।
  • UI framework-এ main thread মানেই UI thread। Android (Looper; input প্রায় 5 সেকেন্ড আটকে থাকলে ANR, main thread থেকে network call করলে NetworkOnMainThreadException), WPF/WinForms (Dispatcher, STA), iOS UIKit, browser-এর JS main thread — সবখানে UI শুধু main thread থেকে বদলানো যায়। ভারী কাজ worker-এ চালাতে হয়, আর ফল main thread-এ post করতে হয়।
  • Windows-এ kernel প্রথম thread বানায়। সেই thread প্রথমে ntdll-এর loader (LdrInitializeThunk) চালায়, তারপর CRT-এর mainCRTStartup হয়ে main-এ পৌঁছায়।

4Worker thread কী, কে তৈরি করে?

পরে আসা thread — program বা runtime চায়, বানায় সেই kernel-ই

Main thread-এর পরে যত thread তৈরি হয়, সাধারণভাবে সেগুলোকে worker thread বলে। OS-এর কাছে এরা main thread-এর মতোই সাধারণ task, আলাদা কোনো flag নেই। "Worker" শুধু ভূমিকার নাম: main বা UI thread-এর হয়ে এরা ভারী বা blocking কাজ করে। নতুন thread বানাতে খরচ আছে (clone, stack mmap, kernel struct — সব মিলে কয়েক থেকে কয়েক দশ µs, আনুমানিক)। তাই বেশিরভাগ runtime একটা thread pool রাখে: কয়েকটা worker আগেই বানিয়ে রাখে, তারপর বারবার reuse করে।

5Thread-এ কী কী থাকে?

নিজের: চলার অবস্থা। Shared: বাকি প্রায় সব কিছু।

একটা thread-এর নিজের জিনিস খুব কম, শুধু যা দিয়ে "কোন instruction-এ আছি, কোন function-এর ভেতরে আছি" বোঝা যায়: register set (PC/RIP, SP), দুইটা stack, TLS, signal mask, scheduling state। Memory, file, socket — এগুলো process-এর, তাই একই process-এর সব thread share করে। এজন্যই thread বানানো আর thread-এর মধ্যে switch করা process-এর চেয়ে সস্তা। আবার এজন্যই shared data-তে lock লাগে।

6User space কী? Kernel space কী?

একই CPU, দুই ক্ষমতা — পাহারা দেয় hardware নিজে

"User space / kernel space" দিয়ে দুইটা জিনিস একসাথে বোঝায়। (১) CPU-র privilege level: এই মুহূর্তে যে code চলছে, তার ক্ষমতা কতটা। (২) Virtual address space-এর দুই ভাগ: কোন memory কে ছুঁতে পারবে। দুটোই hardware enforce করে, software-এর ভালো ব্যবহারের উপর ভরসা করে না।

Privilege level, আসলে কী
  • x86-64: এখন কোন level চলছে, সেটা থাকে CS register-এর নিচের 2 bit-এ (CPL)। Kernel = 0, user = 3।
  • ARM64: EL0 = user app, EL1 = kernel, EL2 = hypervisor, EL3 = secure monitor/firmware।
  • শুধু ring 0 যা পারে: CR3 লেখা (page table বদল), interrupt বন্ধ করা (cli), hlt, MSR লেখা (wrmsr), I/O port, IDT/GDT load। Ring 3 থেকে এগুলোর চেষ্টা করলে #GP exception হয়, আর Linux সেই process-কে SIGSEGV পাঠায়।
  • Memory: প্রতিটা PTE-তে একটা U/S bit থাকে। Kernel page-এ U/S = 0, তাই ring 3 থেকে সেখানে পড়তে গেলেই page fault।
  • কোন code কোথায় চলে: ring 3-এ চলে তোমার app, libc, JVM, browser। ring 0-তে চলে kernel core, scheduler, memory manager, file system, network stack আর বেশিরভাগ device driver।

Kernel-এ ঢোকার তিনটা দরজা

দরজাকে ঘটায়উদাহরণ
System callprogram নিজেই চায় (syscall instruction)read, write, mmap, clone, futex
Exception (trap / fault)চলতি instruction-এর কারণে, synchronouspage fault, divide by zero, int3 breakpoint, invalid opcode
Hardware interruptবাইরের device, যেকোনো মুহূর্তে (asynchronous)timer, network card, disk, keyboard (অংশ ২০)

একটা system call-এর পথ — printf("hi\n")

hello.asm — libc ছাড়া সরাসরি system call (NASM, x86-64 Linux)
section .data
msg db "hello", 10
section .text
global _start
_start:
    mov rax, 1          ; syscall number: 1 = write
    mov rdi, 1          ; arg1: fd 1 = stdout
    lea rsi, [rel msg]  ; arg2: buffer
    mov rdx, 6          ; arg3: length
    syscall             ; ring 0-তে যায়, RIP = LSTAR
    mov rax, 60         ; 60 = exit
    xor rdi, rdi        ; status 0
    syscall
System call-এর ধাপ (x86-64 Linux)
  • RAX-এ syscall number থাকে (write = 1)। Argument যায় RDI, RSI, RDX, R10, R8, R9-এ। সাধারণ function call-এ চতুর্থ argument যায় RCX-এ, কিন্তু এখানে R10, কারণ syscall instruction RCX নষ্ট করে।
  • syscall instruction RIP-কে RCX-এ আর RFLAGS-কে R11-এ রাখে, ring 0-তে যায়, তারপর RIP = MSR_LSTAR (Linux-এর entry_SYSCALL_64)। Stack কিন্তু নিজে থেকে বদলায় না। Kernel entry code swapgs করে per-CPU data থেকে এই thread-এর kernel stack load করে, তারপর user register-গুলো pt_regs হিসেবে save করে।
  • sys_call_table[RAX] আসল handler চালায়। ফল যায় RAX-এ। Error হলে kernel -errno দেয়, আর libc সেটাকে -1 আর errno-তে বদলে দেয়।
  • sysretq আবার ring 3-এ ফেরায়, RIP = RCX।

Virtual address space-এর ভাগ (x86-64 Linux, 4-level paging)

ছবিটা পড়ার নিয়ম
  • 48-bit address দিয়ে মোট 256 TiB ঠিকানা হয়। নিচের 128 TiB user-এর, উপরের 128 TiB kernel-এর, মাঝে বিশাল একটা non-canonical ফাঁক। 5-level paging (57-bit) চালু থাকলে user space 64 PiB পর্যন্ত যেতে পারে।
  • Kernel-এর অর্ধেক প্রতিটা process-এর page table-এ হুবহু একই। তাই syscall-এর সময় page table বদলাতে হয় না, kernel সরাসরি নিজের code আর data পায়।
  • Meltdown-এর পর KPTI চালু থাকলে user mode-এর page table-এ kernel-এর শুধু ছোট entry অংশটুকু থাকে, আর kernel-এ ঢুকলে CR3 বদলায়। PCID থাকার কারণে এতে পুরো TLB flush লাগে না।
  • 32-bit Linux-এ default ভাগ ছিল 3 GB user আর 1 GB kernel।
  • "Kernel space" মানে আলাদা কোনো RAM chip না। একই physical RAM, শুধু page table-এ সেই অংশ kernel-only হিসেবে চিহ্নিত।

7Page table কোথায় থাকে?

RAM-এ থাকে — kernel বানায়, MMU পড়ে, CR3 তার ঠিকানা ধরে রাখে

Page table কোনো বিশেষ hardware memory না। এটা physical RAM-এর সাধারণ 4 KB page-এ রাখা একটা data structure। Kernel সেগুলো allocate করে আর লেখে, আর CPU-র MMU address translation-এর সময় সেগুলো পড়ে। প্রতিটা process-এর একটা করে page table থাকে (mm_struct → pgd)। একই process-এর সব thread সেই একটাই share করে।

কেPage table নিয়ে কী করে
Kernelpage table page allocate করে। PTE লেখে আর মোছে (mmap, page fault, munmap, fork-এর COW)। Context switch-এ CR3 লেখে।
CR3 (x86)এখন যে process চলছে, তার top-level table (PML4)-এর physical address রাখে। PCID চালু থাকলে নিচের 12 bit-এ PCID থাকে। প্রতিটা core-এর নিজের CR3, তাই দুই core-এ দুই আলাদা process চলতে পারে।
TTBR0 / TTBR1 (ARM64)TTBR0_EL1 user অর্ধেকের table দেখায়, TTBR1_EL1 kernel অর্ধেকের। ASID থাকে TTBR-এর ভেতরে।
MMU (page walker)TLB miss হলে CR3 থেকে শুরু করে চার ধাপ নিচে নামে। x86-এ এটা hardware নিজেই করে, kernel-কে ডাকে না।
User programকিছুই না। Page table দেখতেই পায় না, কারণ page table-এর page kernel-only।
একটা PTE (8 byte)-তে কী থাকে
  • P (Present): page RAM-এ আছে কিনা। 0 হলে page fault।
  • R/W: লেখা যাবে কিনা। COW page-এ এটা 0 রাখা হয়।
  • U/S: user mode থেকে access করা যাবে কিনা।
  • A / D (Accessed / Dirty): page পড়া হয়েছে / লেখা হয়েছে কিনা। CPU নিজে বসায়, আর kernel এটা দেখে ঠিক করে কোন page swap-এ পাঠাবে।
  • G (Global): CR3 বদলালেও এই entry TLB-তে থেকে যায় (kernel page-এর জন্য)।
  • NX (bit 63): এই page থেকে code চালানো যাবে না। Stack/heap-এ inject করা code এভাবে আটকায়।
  • PFN (bit 12–51): physical frame number।
Multi-level কেন?

এক স্তরের table হলে 48-bit address আর 4 KB page-এ লাগত 236 entry × 8 B = 512 GB, প্রতিটা process-এর জন্য! Multi-level-এ শুধু ব্যবহৃত অংশের table বানাতে হয়, তাই ছোট একটা process-এর page table মাত্র কয়েক দশ KB।

Huge page: PD level-এ থেমে গেলে একটা entry পুরো 2 MB page দেখায়, PDPT level-এ থামলে 1 GB। এতে TLB entry কম লাগে, database আর VM-এ এটা খুব কাজে লাগে।

Context switch-এ: P1 থেকে P2-তে গেলে kernel শুধু CR3-এ P2-এর PML4-এর ঠিকানা লেখে, page table copy করে না। একই process-এর thread-এর মধ্যে switch-এ CR3 লেখার দরকারই নেই।

$ grep -E 'VmRSS|VmPTE' /proc/self/status
VmRSS:      1920 kB
VmPTE:        48 kB    ← এই process-এর page table নিজেই 48 KB RAM নিচ্ছে

8Virtual address কী, কেন লাগে?

প্রতিটা process ভাবে পুরো memory শুধু তার

Program যত pointer দেখে — &x, malloc-এর return, function-এর address — সবই virtual address। আসল RAM chip-এর ঠিকানা (physical address) program কখনো দেখে না। প্রতিটা memory access-এ MMU virtual address-কে physical-এ বদলে নেয়। এতে দুই process একই virtual address ব্যবহার করলেও আসলে আলাদা RAM-এ পৌঁছায়।

কেন এই ব্যবস্থা

IsolationP1 P2-এর memory দেখতেই পায় না, কারণ P1-এর page table-এ P2-এর frame নেই। এক process-এর bug বা attack সেখানেই আটকে থাকে।
সবার একই layoutপ্রতিটা process ভাবে তার memory 0 থেকে শুরু, code একই ঠিকানায়। এতে linker আর loader-এর কাজ সহজ হয়। (নিরাপত্তার জন্য ASLR আবার ঠিকানাগুলো random করে।)
Demand paging / lazy allocationmalloc(1 GB) সাথে সাথে 1 GB RAM নেয় না। কোনো page প্রথমবার ছোঁয়ার সময় page fault হয়, আর kernel তখন frame দেয়।
Swapকম ব্যবহৃত page disk-এ সরিয়ে রাখা যায়। তাতে মোট memory RAM-এর চেয়ে বেশি মনে হয়।
Shared librarylibc-এর code RAM-এ একবারই থাকে, অথচ শত শত process-এর page table সেই একই frame-এ map করা।
Copy-on-writefork()-এর পর parent আর child একই frame read-only অবস্থায় share করে। কেউ লিখতে গেলে তখন শুধু সেই একটা page copy হয়।
mmap করা fileFile-কে memory-র মতো পড়া যায়। Kernel-এর page cache-এর page সরাসরি process-এ map হয়।
Guard আর permissionStack overflow, NULL pointer dereference, code-এ লেখার চেষ্টা — সবই hardware page fault দিয়ে ধরা পড়ে।

Translation হাতে-কলমে: virtual → page number + offset → frame

Page 4 KB = 212 byte, তাই address-এর নিচের 12 bit হলো offset (page-এর ভেতরে কোথায়), আর উপরের bit-গুলো virtual page number (VPN)। x86-64-এ VPN-এর 36 bit আবার চারটা 9-bit index-এ ভাগ হয়, প্রতিটা page table level-এর জন্য একটা। নিচে যেকোনো hex address দিয়ে দেখো।

PFN (frame number) এই demo-তে বানানো। আসল মান kernel ঠিক করে, আর user space সেটা দেখতে পায় না (/proc/<pid>/pagemap-এ PFN পড়তে root লাগে)।

9MMU কী? TLB কী?

MMU অনুবাদ করে, TLB মনে রাখে

MMU (Memory Management Unit) প্রতিটা CPU core-এর ভেতরের একটা hardware। প্রতিটা instruction fetch, load আর store-এ এটা virtual address-কে physical address-এ বদলায় আর permission check করে। প্রতিবার চার ধাপ page table পড়তে হলে প্রতিটা memory access অনেক ধীর হয়ে যেত। তাই MMU-র সাথে থাকে TLB (Translation Lookaside Buffer): সম্প্রতি ব্যবহার হওয়া translation-এর একটা ছোট আর খুব দ্রুত cache। নিচে mode বেছে Next চাপো।

এই ধাপে কাজ হচ্ছেসফলmiss / fault
TLBসাধারণ মান (আনুমানিক)
L1 dTLB (data)~64–96 entry (4 KB page), প্রতি core
L1 iTLB (instruction)~64–256 entry
L2 TLB (STLB)~1.5K–3K entry, instruction আর data দুইটার জন্যই
TLB hit~0–1 cycle, L1 cache খোঁজার সাথে একই সময়ে
Miss + page walkকয়েক দশ cycle। Entry cache-এ না থাকলে কয়েকশো cycle

CPU model অনুযায়ী মান বদলায়। cpuid বা vendor-এর manual-এ আসল মান পাওয়া যায়।

Page fault তিন রকম
  • Minor (soft): page আসলে RAM-এ আছে, শুধু এই process-এর page table-এ map করা নেই। অথবা এটা প্রথম touch, তাই নতুন zero page দিলেই হয়। এক µs-এর কম লাগে।
  • Major (hard): page disk থেকে আনতে হবে (swap বা mmap করা file)। SSD-তে ~100 µs, HDD-তে কয়েক ms। ততক্ষণ thread ঘুমায়, আর অন্য thread চলে।
  • Invalid: address-টা কোনো VMA-তে পড়ে না, অথবা permission নেই (যেমন read-only page-এ লেখা)। ফলাফল SIGSEGV, মানে "Segmentation fault"।
  • COW fault: fork-এর পর shared page-এ লেখা। Kernel তখন page copy করে আর PTE-তে R/W = 1 করে দেয়।
TLB flush কখন হয় — context switch-এর জন্য এটাই আসল কথা
  • CR3-এ নতুন মান লিখলে (process switch-এ), global (G bit দেওয়া) entry ছাড়া TLB-র সব entry বাতিল হয়ে যায়।
  • PCID (x86) / ASID (ARM): প্রতিটা TLB entry-তে process-এর একটা tag থাকে। Switch-এর সময় tag বদলায়। পুরনো entry থেকে যায়, কিন্তু নতুন tag-এর সাথে মেলে না। পরে সেই process-এ ফিরে এলে আবার কাজে লাগে। Linux x86-এ 4.14 থেকে PCID ব্যবহার করে, প্রতিটা CPU-তে অল্প কয়েকটা PCID ঘুরিয়ে।
  • TLB shootdown: munmap/mprotect-এ page table বদলালে invlpg দিয়ে নির্দিষ্ট entry মুছতে হয়। একই process-এর thread অন্য core-এ চললে সেই core-গুলোকেও IPI (inter-processor interrupt) পাঠিয়ে flush করাতে হয়, যেটা বেশ দামি।
  • একই process-এর thread-এর মধ্যে switch: কোনো flush নেই, কারণ page table একই।

10L1, L2, L3 cache কী?

RAM অনেক ধীর, তাই CPU-র ভেতরে ছোট কিন্তু দ্রুত memory রাখা হয়

CPU প্রতি ns-এ কয়েকটা instruction চালাতে পারে, অথচ RAM থেকে একটা data আনতে ~100 ns লাগে। এই ফাঁক ভরাতে core আর RAM-এর মাঝে কয়েক স্তরের SRAM cache থাকে। L1 সবচেয়ে ছোট আর সবচেয়ে দ্রুত, L3 বড় কিন্তু ধীর। Cache-এ data আসে-যায় cache line ধরে, x86-এ যার আকার 64 byte। একটা byte দরকার হলেও পুরো 64 byte আসে।

খুঁটিনাটি
  • L1 দুই ভাগে (L1i + L1d): instruction fetch আর data load/store একই cycle-এ ঘটে, আলাদা cache থাকায় একে অপরের পথ আটকায় না। L2 আর L3 unified, মানে দুই ধরনের data-ই রাখে।
  • Locality: temporal (যা এইমাত্র ব্যবহার হলো, সেটা আবার লাগবে) আর spatial (পাশের byte-ও লাগবে)। এজন্য array ক্রমানুসারে পড়া linked list-এর চেয়ে অনেক দ্রুত।
  • Cache coherence (MESI ধরনের protocol): এক core কোনো line-এ লিখলে অন্য core-এর copy invalid হয়ে যায়। Hardware নিজেই এটা করে, software-কে কিছু করতে হয় না।
  • Process switch-এ cache flush হয় না। Cache physical address দিয়ে কাজ করে (L1 VIPT হলেও কার্যত তাই)। কিন্তু নতুন process-এর data cache-এ থাকে না, ধীরে ধীরে ভরে। একে বলে cold cache।

11Register কী? Register-এ কী কী থাকে?

Register set = এই মুহূর্তে thread-এর পুরো CPU state

Register হলো core-এর ভেতরের সবচেয়ে ছোট আর সবচেয়ে দ্রুত storage। Instruction সরাসরি এগুলোর উপর কাজ করে (add rax, rbx)। x86-64-এ register-গুলো কয়েকটা দলে ভাগ করা। Context switch মানে মূলত এটাই: চলমান thread-এর register-গুলো save করা আর পরের thread-এর register load করা। এই register set-ই একটা thread-এর CPU state।

12Core-এ কী কী থাকে?

Core হলো instruction চালানোর একটা পুরো যন্ত্র, আর chip-এ থাকে এমন কয়েকটা

আধুনিক core একটার পর একটা করে instruction চালায় না। প্রতি cycle-এ সে কয়েকটা instruction fetch আর decode করে, যেটা আগে তৈরি হয় সেটা আগে চালায় (out-of-order), তারপর ফলগুলো আবার program-এর ক্রমে commit করে। নিচের ছবি সরলীকৃত; Intel, AMD আর ARM-এর খুঁটিনাটি আলাদা।

  • এক core-এ দুইটা hardware thread (logical CPU) থাকে। প্রতিটার নিজের architectural register set (RIP, RSP, RFLAGS, CR3…) আর interrupt state। তাই OS দুইটাকে আলাদা CPU হিসেবে দেখে, আর দুইটাতে দুই আলাদা software thread চালাতে পারে, এমনকি দুই আলাদা process-এর thread-ও।
  • Execution unit, cache আর TLB দুজনে ভাগ করে। একটা thread memory-র জন্য অপেক্ষা করার সময় আরেকটা খালি unit ব্যবহার করে। তবে লাভ 2× না, সাধারণত ~10–30% (workload অনুযায়ী, আনুমানিক)।
  • Software thread আর hardware thread এক জিনিস না। 8-core/16-thread CPU মানে একসাথে 16টা software thread চলতে পারে। বাকি শত শত thread run queue-তে অপেক্ষা করে, আর context switch দিয়ে পালা পায়।
  • Chip-এ shared: L3, interconnect, memory controller (IMC), PCIe/I/O, আর কিছু chip-এ integrated GPU।

13IMC কী?

Integrated Memory Controller — CPU আর RAM-এর মধ্যে অনুবাদক

L3-তেও data না পেলে request যায় IMC (Integrated Memory Controller)-এ। IMC হলো CPU chip-এর ভেতরের একটা circuit, যেটা DRAM-এর সাথে DDR4/DDR5 protocol-এ কথা বলে। Physical address-কে channel, rank, bank, row আর column-এ ভাগ করে, DRAM-কে command পাঠায় (ACTIVATE, READ/WRITE, PRECHARGE, আর নিয়মিত REFRESH), অনেকগুলো request একসাথে সাজিয়ে চালায়, আর server-এ ECC check করে। Core থেকে ক্রম: L1 → L2 → L3 → interconnect → IMC → memory channel → DIMM।

IMC কেন CPU-র ভেতরে আনা হলো
  • Latency: আগে request যেত CPU → FSB → northbridge → RAM। IMC chip-এর ভেতরে আসায় একটা পুরো chip আর bus-এর hop বাদ পড়ল, RAM access কয়েক দশ ns কমল (আনুমানিক)।
  • Bandwidth: একটা shared FSB-তে সব core-এর ভিড় হতো। এখন প্রতিটা CPU-র নিজের memory channel। Desktop-এ সাধারণত 2 channel, server-এ প্রতি socket-এ 8–12 channel। একটা DDR5-5600 channel ≈ 5600 MT/s × 8 byte ≈ 44.8 GB/s।
  • Chiplet CPU-তে (AMD Zen 2 থেকে) IMC থাকে আলাদা I/O die-তে, core-গুলোর die-তে না। তবু সেটা CPU package-এর ভেতরেই।
  • OS-এর ভূমিকা কম: Boot-এর সময় firmware (UEFI) memory training করে IMC configure করে। Kernel শুধু physical memory-র map দেখে (e820/UEFI memory map)। ECC error হলে kernel-এর EDAC driver সেটা জানায়।
NUMA (Non-Uniform Memory Access)

Multi-socket server-এ প্রতিটা socket-এর নিজের IMC আর নিজের RAM থাকে। Linux সাধারণত page দেয় যে node-এর CPU প্রথমবার page-টা ছোঁয় (first-touch), আর scheduler thread-কে তার memory-র কাছাকাছি রাখার চেষ্টা করে। Database বা JVM-এর মতো বড় process-এ numactl দিয়ে এটা নিয়ন্ত্রণ করা যায়।

14Thread-এর user space stack কী?

প্রতিটা thread-এর নিজের stack, একই address space-এর ভেতরে পাশাপাশি

Stack overflow
  • অসীম বা খুব গভীর recursion, অথবা বিশাল local array (char buf[16 << 20]) হলে stack guard page পর্যন্ত পৌঁছায়। তখন page fault হয়, kernel দেখে সেখানে কোনো valid mapping নেই, আর SIGSEGV পাঠায়।
  • Java-য় এটা StackOverflowError হয়ে আসে, কারণ JVM নিজের guard zone দিয়ে ধরে exception বানায়। .NET-এ stack overflow ধরা যায় না, process crash করে।
  • Worker thread-এর stack ছোট রাখলে (যেমন 256 KB) অনেক thread চালানো যায়। তবে গভীর recursion তখন বিপজ্জনক।

15Thread-এর kernel space stack কী?

প্রতিটা thread-এর kernel-এ ঢোকার জন্য আলাদা একটা ছোট stack

Thread যখন syscall করে, অথবা চলার সময় interrupt বা exception আসে, CPU তখন kernel-এর code চালায়, কিন্তু সেই thread-এর হয়ে। Kernel code-এরও function call আর local variable আছে, তাই তারও stack লাগে। সেই stack user stack না। প্রতিটা thread-এর kernel space-এ একটা আলাদা kernel stack থাকে। x86-64 Linux-এ এর আকার 16 KB (Linux 3.15 থেকে, তার আগে 8 KB)।

User stack কেন ব্যবহার করা যায় না
  • বিশ্বাস করা যায় না: RSP-তে user যা ইচ্ছা রাখতে পারে — invalid address, kernel-এর address, অথবা এমন memory যেটা আরেক thread ঠিক সেই সময় বদলাচ্ছে। Kernel সেখানে return address রাখলে attacker সেটা বদলে kernel-এর নিয়ন্ত্রণ নিয়ে নিতে পারত।
  • Leak: Kernel-এর local variable (key, pointer) user memory-তে পড়ে থাকত, user সেগুলো পড়ে ফেলত।
  • Crash: User stack ভর্তি বা unmapped থাকলে kernel নিজেই fault করত।
  • এজন্য hardware সাহায্য করে। User mode-এ interrupt এলে CPU নিজে TSS থেকে kernel-এর stack pointer নিয়ে stack বদলায়। Syscall-এ entry code প্রথম কয়েকটা instruction-এর মধ্যেই stack বদলায়।
প্রতি thread-এ একটা কেন (প্রতি CPU-তে একটা না)
  • Syscall-এর মাঝখানে thread ঘুমাতে পারে (disk read, lock)। তার kernel call chain (vfs_read → … → schedule()) পুরোটা তখন ওই kernel stack-এ জমা থাকে। অন্য thread চলে নিজের kernel stack-এ। ঘুম ভাঙলে আগেরটা ঠিক যেখানে থেমেছিল সেখান থেকে চলে।
  • Context switch আসলে kernel stack বদলানো। switch_to-তে RSP এক thread-এর kernel stack থেকে আরেক thread-এর kernel stack-এ যায় (অংশ ১৮)।
  • Stack ছোট (16 KB), কারণ thread হাজার হাজার হতে পারে। তাই kernel code-এ বড় local array বা গভীর recursion নিষেধ। CONFIG_VMAP_STACK (Linux 4.9+) চালু থাকলে stack-এর নিচে guard page থাকে, overflow হলে সাথে সাথে ধরা পড়ে।
  • x86-64 Linux-এ hardware interrupt, NMI আর double fault-এর জন্য আলাদা per-CPU stack-ও আছে (IRQ stack, IST)। তবে user register (pt_regs) save হয় thread-এর kernel stack-এই।

16Thread-এর PCB/TCB কী, kernel-এর জন্য কোথায় থাকে?

Linux-এ সবার জন্য একটাই struct — task_struct

Textbook-এ দুইটা আলাদা struct: PCB (Process Control Block) রাখে process-এর তথ্য (address space, open file, PID…), আর TCB (Thread Control Block) রাখে thread-এর নিজের তথ্য (saved register, stack pointer, state, priority)। Linux এভাবে আলাদা করে না। প্রতিটা thread-এর একটা করে task_struct, আর "process" মানে একই tgid আর একই mm/files share করা কয়েকটা task-এর দল। Shared অংশগুলো আলাদা struct-এ থাকে (mm_struct, files_struct…), আর task_struct-এ থাকে শুধু সেগুলোর pointer।

Kernel-এর কাছে কোথায় থাকে
  • Kernel memory-তে (address space-এর kernel অর্ধেকে), slab allocator-এর task_struct cache (kmem_cache) থেকে নেওয়া। আকার kernel config অনুযায়ী কয়েক KB।
  • User program সরাসরি দেখতে পারে না। /proc/<pid>/task/<tid>/ দিয়ে কিছু অংশ পড়া যায়।
  • সব task একটা list-এ যুক্ত থাকে, আর PID hash table দিয়ে খোঁজা যায়। Task runnable হলে per-CPU run queue (struct rq)-তে যায়। Fair class-এ সেটা একটা red-black tree (Linux 6.6 থেকে EEVDF scheduler)।

User space-এও TCB থাকে
  • glibc প্রতিটা thread-এর জন্য একটা struct pthread রাখে (user-space TCB), thread stack-এর মাথায়। FS base সেটার দিকে দেখায়। TLS, errno, cancel state আর thread-এর return value এখানে থাকে।
  • N:1 বা M:N runtime নিজের TCB রাখে, যেমন Go runtime-এর g struct বা Java virtual thread-এর continuation। Kernel এগুলো চেনে না।
  • Windows: kernel-এ EPROCESS/KPROCESS (process) আর ETHREAD/KTHREAD (thread)। User mode-এ PEB আর TEB (TEB পাওয়া যায় GS register দিয়ে)।

17PCB-তে data রাখে নাকি TCB-তে?

Process-এর জিনিস process-এর block-এ, thread-এর চলার অবস্থা thread-এর নিজের block-এ

উত্তর নির্ভর করে কোন data, তার উপর। PCB = পুরো process-এর তথ্য, সব thread-এর জন্য একটাই: address space (mm), open file, PID, credential। TCB = প্রতিটা thread-এর নিজের তথ্য: saved register, stack pointer, state, priority। Context switch-এ thread-এর CPU context সবসময় তার নিজের TCB-তে যায়, shared PCB-তে না। না হলে দুই thread একে অপরের saved register overwrite করে ফেলত।

18Context switch — ধাপে ধাপে

কে করছে, kernel-এ ঢুকতে হচ্ছে কিনা, address space বদলাচ্ছে কিনা — খরচ ঠিক হয় এই তিনটা দিয়ে

Context switch মানে একটা core-এ চলমান thread থামানো, তার CPU state save করা, আর আরেক thread-এর state load করে তাকে চালানো। Intro গাইডের মূল কথা ছিল "register RAM-এ save হয়"। এখানে দেখব ঠিক কোন register কোথায় যায়, আর তিন ধরনের switch-এ কী কী বদলায়। নিচে mode বেছে Next চাপো, অথবা Play।

Context switch কখন হয়
  • Preemption: timer interrupt আসে। Kernel দেখে time slice শেষ, অথবা বেশি priority-র thread ready, তখন need_resched flag বসায়। Interrupt থেকে ফেরার পথে schedule() ডাকা হয়।
  • Voluntary: thread নিজেই block করে — read()-এ data-র অপেক্ষা, mutex (futex) না পাওয়া, sleep()। Kernel ভেতর থেকেই schedule() ডাকে।
  • Thread শেষ হলে (exit), বা sched_yield() ডাকলে।
  • User-level thread: library-র yield() বা library-র নিজের mutex, kernel ছাড়াই।
এই ধাপে বদলাল / কাজ হলোবদলায়নি, এটাই লাভখরচ বা সমস্যাঝাপসা = এই mode-এ নেই

19তোমার বোঝা — কোনটা ঠিক, কোনটা ঠিক না

User-level, kernel-level আর ভিন্ন process — তিনটা আলাদা রাখলেই ছবিটা পরিষ্কার

প্রশ্নটা ছিল মোটামুটি এরকম: "context switching-এ library থেকে data রাখে process-এর TCB-তে, যেহেতু kernel ছাড়া access করা যায় না — এটা user mode-এই thread switch হয়, right? user space-এর thread t1, t2 context switch হলে library থেকে data তার register-এ save করে আর বাকি flush করে, অন্য p2 process-এর user thread t2 আর p1-এর t1…"

✓ (১) একই process-এর user-level (N:1) thread: হ্যাঁ, পুরোটা user mode-এLibrary T1-এর register save করে user space-এ library-র নিজের TCB-তে (বা T1-এর stack-এ), তারপর T2-এর register load করে। Kernel জড়িত না, mode switch নেই, কোনো flush নেই। একটা ছোট সংশোধন: এই TCB user memory-তে থাকে, তাই kernel ছাড়াই access করা যায়, আর এটাই এর মূল সুবিধা। Kernel ছাড়া যেটা ছোঁয়া যায় না, সেটা kernel-এর নিজের task_struct।
✗ (২) Library কখনো অন্য process-এর thread-এ যেতে পারে নাP1-এর T1 থেকে P2-এর T2-তে যেতে হলে CR3-এ P2-এর page table বসাতে হয়, আর CR3 লেখা যায় শুধু ring 0 থেকে। তাছাড়া P1-এর page table-এ P2-এর memory map করাই নেই, তাই library P2-এর TCB বা stack পড়তেই পারবে না। দুই process-এর মধ্যে switch সবসময় kernel করে।
! (৩) সাধারণ thread kernel thread (1:1), তাই switch kernel-এ হয়Linux, Windows আর macOS-এ pthread, Java platform thread, .NET thread, C++ std::thread — সব 1:1। এদের প্রতিটা switch, একই process-এর ভেতরে হলেও, kernel দিয়ে হয়। Context save হয় kernel-এর task_struct আর ওই thread-এর kernel stack-এ। "library user mode-এ switch করে" কথাটা খাটে শুধু green thread, goroutine বা virtual thread-এর ক্ষেত্রে।
~ (৪) "Register-এ save করে আর বাকি flush করে" — দুইটাই একটু ঘোরানোSave হয় register থেকে memory-তে (TCB বা stack-এ), আর load হয় memory থেকে register-এ। Flush: একই process হলে CR3 বদলায় না, তাই TLB flush নেই। ভিন্ন process হলে CR3 বদলায়, আর TLB flush হয় (বা PCID/ASID tag বদলায়)। Cache কোনো ক্ষেত্রেই flush হয় না, শুধু নতুন process-এর data না থাকায় cache ঠান্ডা থাকে।

20Driver কীভাবে কাজ করে? Keyboard, mouse, monitor — kernel mode-এ যায়, নাকি user mode-এ?

Hardware-এর সাথে কথা বলে kernel-এর driver, আর event-টা শেষ পর্যন্ত পৌঁছায় user space-এর app-এ

Driver হলো এমন code যেটা একটা নির্দিষ্ট device-এর register আর protocol চেনে, আর kernel-এর একটা standard interface (input, block, network, display) দিয়ে সেটা বাকি system-এর কাছে পৌঁছে দেয়। Keyboard, mouse, GPU, network card, disk — এদের মূল driver সাধারণত kernel mode-এ চলে, kernel-এর অংশ হিসেবে বা loadable module হিসেবে (Linux-এ .ko, Windows-এ .sys)। কারণ device register, interrupt আর DMA শুধু ring 0 থেকে নিরাপদে সামলানো যায়। তবে event-এর শেষ অংশটা চলে user space-এ: display server বা compositor, তারপর app-এর event loop।

CPU device-এর সাথে কথা বলে চারভাবে
  • MMIO (memory-mapped I/O): device-এর register physical address space-এর একটা অংশে বসানো থাকে। Driver সেটা map করে (ioremap) সাধারণ load/store দিয়ে পড়ে আর লেখে। আধুনিক device এভাবেই কাজ করে।
  • Port I/O: x86-এর in/out instruction। পুরনো device (PS/2, serial port) এটা ব্যবহার করত।
  • DMA: device নিজেই RAM-এ পড়ে বা লেখে, CPU-কে প্রতিটা byte copy করতে হয় না। IOMMU ঠিক করে দেয় কোন device কোন RAM ছুঁতে পারবে।
  • Interrupt: কাজ শেষ হলে device CPU-কে জানায়। পুরনো IRQ line IOAPIC হয়ে আসে। আধুনিক PCIe device MSI/MSI-X ব্যবহার করে: একটা বিশেষ address-এ memory write পাঠায়, আর সেটা একটা নির্দিষ্ট core-এর local APIC-এ interrupt হয়ে পৌঁছায়।
Driver-এর দুই অর্ধেক
  • Top half (interrupt handler): যে thread চলছিল তাকে থামিয়ে, interrupt disable অবস্থায় খুব কম কাজ করে। শুধু device-কে "পেয়েছি" জানায় আর data তুলে রাখে।
  • Bottom half (softirq, tasklet, workqueue, threaded IRQ): বাকি ভারী কাজটা পরে করে, interrupt চালু রেখে। Network-এর NAPI এরই উদাহরণ।
  • Interrupt কোনো process-এর অনুরোধে আসে না, তাই handler-এর জন্য নতুন thread তৈরি হয় না। যে thread চলছিল তার kernel stack-এ register save হয়, আর handler চলে সেই core-এর IRQ stack-এ (অংশ ১৫)।
  • User space device-কে দেখে file হিসেবে: /dev/input/event3, /dev/dri/card0, /dev/nvme0n1। সেখানে read, write, ioctl, mmap করা যায়, আর kernel সেটা driver-এর function-এ পাঠিয়ে দেয়।

21Network card কীভাবে কাজ করে? OSI কি network card-এর ভেতরে থাকে?

NIC করে L1–L2, kernel করে L3–L4, আর L5–L7 থাকে তোমার app-এ

পুরো OSI model network card-এর ভেতরে থাকে না। NIC (Network Interface Card) করে শুধু নিচের দুইটা layer: L1 Physical (PHY: electrical বা radio signal থেকে bit) আর L2 Data link-এর hardware অংশ (MAC: frame চেনা, MAC address দিয়ে filter, FCS/CRC check)। IP আর TCP/UDP (L3–L4) চলে kernel-এর network stack-এ। TLS আর HTTP (L5–L7) চলে user space-এ, তোমার app বা তার library-তে। OSI নিয়ে বিস্তারিত আছে OSI গাইডে, আর server-এর দিকটা web server গাইডে।

একটা packet আসার পথ (receive)

ধাপগুলোর খুঁটিনাটি
  • MAC filter: destination MAC নিজের, broadcast, অথবা subscribe করা multicast না হলে NIC frame-টা ফেলে দেয়, CPU জানতেও পারে না। Promiscuous mode-এ (Wireshark) সব frame নেয়।
  • FCS/CRC ভুল হলে frame সেখানেই বাদ পড়ে, আর NIC-এর error counter বাড়ে (ethtool -S)।
  • RX ring: driver আগে থেকেই RAM-এ buffer বরাদ্দ করে descriptor ring-এ রাখে। NIC সেখানে DMA দিয়ে packet লেখে, CPU কোনো copy করে না।
  • NAPI: প্রতিটা packet-এ একটা করে interrupt হলে CPU ডুবে যেত। তাই প্রথম interrupt-এর পর driver interrupt বন্ধ রেখে softirq-তে একসাথে অনেক packet poll করে, ring খালি হলে interrupt আবার চালু করে।
  • Socket buffer থেকে app: recv()-এ blocked থাকা thread (বা epoll-এ অপেক্ষা করা event loop) জেগে ওঠে। Kernel data user buffer-এ copy করে দেয়।
Offload — NIC যখন kernel-এর কিছু কাজ নিজেই করে
  • Checksum offload: IP/TCP/UDP checksum NIC নিজে হিসাব আর যাচাই করে।
  • TSO/GSO (send): kernel 64 KB-র একটা বড় segment দেয়, আর NIC (বা driver-এর ঠিক আগে kernel) সেটা MTU মাপের packet-এ ভাঙে।
  • LRO/GRO (receive): পাশাপাশি আসা packet জুড়ে একটা বড় packet বানিয়ে stack-এ পাঠায়।
  • RSS (multi-queue): connection-এর hash দেখে packet আলাদা RX queue-তে যায়, আর প্রতিটা queue-র interrupt আলাদা core-এ। ফলে অনেক core একসাথে network সামলাতে পারে।
  • kTLS / TLS offload, VLAN tag, timestamp: কিছু NIC-এ থাকে। SmartNIC/DPU এর চেয়েও বেশি করে: পুরো TCP, firewall, এমনকি virtual switch।
  • এক লাইনে: offload থাকলেও TCP-র মূল state আর logic সাধারণ NIC-এ না, kernel-এ থাকে। দেখতে: ethtool -k eth0।

QInterview-এ যা আসে

Process আর thread-এর পার্থক্য কী?

Process হলো resource-এর container: নিজের address space (page table), open file, PID, credential। Thread হলো execution-এর unit: নিজের register set, stack আর scheduling state, কিন্তু process-এর memory আর file অন্য thread-এর সাথে share করে। Linux kernel-এ দুটোই task_struct, পার্থক্য শুধু clone()-এর flag-এ, মানে কোনটা share হবে।

একই process-এর thread-এর মধ্যে context switch কেন process switch-এর চেয়ে সস্তা?

Address space একই, তাই CR3 লিখতে হয় না, TLB flush হয় না। Code, heap আর page table entry cache-এ গরম থাকে। কাজ শুধু register save/restore আর kernel stack বদলানো। Process switch-এ এর সাথে CR3 বদলাতে হয়, TLB-র entry অচল হয়ে যায় (বা PCID tag বদলায়), আর নতুন working set cache-এ আনতে হয়, যেটাই আসল খরচ।

Thread-গুলো কী share করে, কী করে না?

Share করে: code, global/static data, heap, open file descriptor, socket, signal handler, cwd, PID। নিজের: TID, register (PC, SP সহ), user stack, kernel stack, TLS (errno সহ), signal mask, scheduling state আর priority।

দুইটা process কি memory share করতে পারে?

পারে, তবে kernel-এর মাধ্যমে। shm_open + mmap(MAP_SHARED), System V shared memory, বা একই file mmap করলে দুই process-এর page table একই physical frame দেখায়। Shared library-র code আর fork-এর পরের COW page-ও এভাবে share হয়। Kernel ছাড়া এক process আরেক process-এর memory ছুঁতে পারে না।

Page fault হলে কী হয়?

MMU PTE-তে Present = 0 পায় বা permission মেলে না, তখন #PF exception তোলে, আর faulting address CR2-তে রাখে। Kernel-এর handler দেখে address-টা কোনো valid VMA-তে পড়ে কিনা। Minor fault হলে frame দিয়ে বা map করে দেয়। Major fault হলে disk থেকে পড়ে, thread ততক্ষণ ঘুমায়। Invalid হলে SIGSEGV। এরপর PTE update করে instruction-টা আবার চালানো হয়।

Kernel stack আলাদা কেন? User stack ব্যবহার করলে কী সমস্যা?

User stack-এর RSP user-এর নিয়ন্ত্রণে, তাই invalid বা ক্ষতিকর হতে পারে। আরেক thread একই সময়ে সেটা বদলাতেও পারে, আর kernel-এর data user memory-তে leak হতো। এছাড়া প্রতিটা thread syscall-এর মাঝখানে ঘুমাতে পারে, তাই প্রতি thread-এ নিজের একটা kernel stack লাগে (x86-64 Linux-এ 16 KB)।

System call কি context switch?

না, এটা mode switch। একই thread ring 3 থেকে ring 0-তে যায় আর ফিরে আসে, CR3 বা thread বদলায় না। Syscall-এর ভেতরে thread block করলে (যেমন disk-এর অপেক্ষায়) বা preempt হলে তখন context switch হয়।

fork() কি পুরো memory copy করে?

না। Child-এর জন্য নতুন page table বানানো হয়, কিন্তু সেটা parent-এর একই physical frame দেখায়, দুই দিকেই read-only করে। কেউ লিখতে গেলে page fault হয়, আর kernel শুধু সেই একটা page copy করে (copy-on-write)। তাই fork-এর পর সাথে সাথে exec করলে প্রায় কিছুই copy হয় না।

TLB কী, flush কখন হয়, PCID কী?

TLB হলো virtual → physical translation-এর per-core cache। CR3 বদলালে (process switch) non-global entry flush হয়। PCID/ASID থাকলে প্রতিটা entry process-এর tag নিয়ে থাকে, তাই পুরো flush লাগে না। munmap/mprotect-এ নির্দিষ্ট entry invalidate হয়, আর অন্য core-এ একই process চললে IPI দিয়ে TLB shootdown করতে হয়।

1:1 আর M:N threading-এর পার্থক্য কী? Goroutine কেন হালকা?

1:1-এ প্রতিটা thread একটা kernel task, আর switch হয় kernel-এ (pthread, Java platform thread)। M:N-এ অনেক user-level task কয়েকটা OS thread-এর উপর runtime-এর scheduler দিয়ে চলে। Goroutine-এর stack শুরু হয় কয়েক KB দিয়ে, switch হয় user space-এ (কোনো syscall নেই), আর blocking syscall-এর সময় runtime অন্য OS thread-এ বাকিদের চালিয়ে নেয়।

Kernel thread-এর তো নিজের user address space নেই — তাতে switch করলে CR3 কী হয়?

Kernel thread-এর mm = NULL। Linux তখন আগের task-এর page table ধার করে চালায় (active_mm, "lazy TLB" mode)। Kernel-এর অর্ধেক সব page table-এ একই, তাই CR3 লেখারও দরকার পড়ে না। এতে user process → kernel thread → সেই একই user process — এই পথে TLB গরম থাকে।

IMC কী, আর NUMA-র সাথে এর সম্পর্ক কী?

IMC (Integrated Memory Controller) CPU chip-এর ভেতরে থেকে DDR channel দিয়ে RAM-এর সাথে কথা বলে। আগে এটা northbridge chip-এ থাকত (AMD K8 আর Intel Nehalem থেকে CPU-তে এসেছে), তাই এখন latency কম। Multi-socket-এ প্রতিটা socket-এর নিজের IMC আর RAM। নিজের RAM পড়া দ্রুত, অন্য socket-এর RAM পড়া ধীর — এটাই NUMA।

Keyboard-এর driver কি user mode-এ চলে?

না, মূল অংশটা kernel-এ। USB host controller interrupt দেয়, kernel-এর xhci আর usbhid driver report পড়ে, input subsystem সেটা /dev/input/eventX-এ দেয়। তারপর user-space display server বা compositor সেটা পড়ে app-কে পাঠায়। Interrupt আর DMA সামলানোর ক্ষমতা শুধু ring 0-এর আছে। User-mode driver (UMDF, libusb, FUSE) সম্ভব, তবে তাদের নিচেও একটা kernel stub থাকে।

OSI-এর কোন layer network card-এ, কোনটা kernel-এ?

NIC করে L1 (PHY) আর L2-এর hardware অংশ (frame, MAC filter, CRC)। সাথে কিছু offload থাকে (checksum, TSO, GRO, RSS)। L3 (IP) আর L4 (TCP/UDP) চলে kernel-এর network stack-এ। L5–L7 (TLS, HTTP) চলে user space-এ app বা library-তে। Packet NIC থেকে DMA দিয়ে RAM-এর RX ring-এ যায়, তারপর interrupt আর NAPI poll হয়ে kernel stack-এ, শেষে socket buffer থেকে recv() দিয়ে app-এ।
