1Deadlock কী, কীভাবে হয়

সবাই অপেক্ষা করছে এমন কিছুর জন্য, যেটা শুধু অপেক্ষারত অন্য কেউ দিতে পারে

একদল process (বা thread, বা transaction) এমন অবস্থায় আটকে গেছে যেখানে প্রত্যেকে একটা resource ধরে রেখেছে এবং দলের অন্য কারো হাতে থাকা resource-এর জন্য অপেক্ষা করছে। কেউ নিজের resource ছাড়বে না যতক্ষণ না কাজ শেষ হয়, আর কাজ শেষ হবে না যতক্ষণ না অন্যেরটা পায় — তাই কেউ কখনো এগোয় না। বাইরে থেকে কেউ হস্তক্ষেপ না করলে এই অবস্থা চিরকাল থাকে।

সরু ব্রিজে দুই গাড়ি: একটা মাত্র lane-এর ব্রিজে দুই দিক থেকে দুইটা গাড়ি ঢুকে মাঝখানে মুখোমুখি। প্রত্যেকে ব্রিজের অর্ধেক দখল করে আছে (resource ধরে আছে), আর বাকি অর্ধেক চাইছে — যেটা অন্য গাড়ির দখলে। কেউ পিছু না হটলে (preemption / rollback) দুজনই সারাদিন দাঁড়িয়ে থাকবে।

এক জোড়া chopstick: টেবিলে দুইজন, মাঝে মাত্র দুইটা chopstick। খেতে লাগে দুইটাই। রহিম বাঁ পাশেরটা তুলল, করিম ডান পাশেরটা। এখন দুজনই অন্যটার জন্য হাত বাড়িয়ে বসে আছে — কেউ নিজেরটা নামাচ্ছে না। এটাই বিখ্যাত Dining Philosophers সমস্যার ছোট রূপ।

Computer-এ resource মানে কী?
  • Software resource: mutex / lock, semaphore, database-এর row বা table lock, file lock।
  • Hardware resource: printer, tape drive, নির্দিষ্ট পরিমাণ memory buffer।
  • প্রতিটা resource ব্যবহারের ছন্দ একই: request → use → release। Request পূরণ না হলে process blocked হয়ে অপেক্ষা করে — deadlock এই অপেক্ষারই একটা চক্র।

Process আর thread কী, block হওয়া মানে কী — ঝালিয়ে নিতে: OS, Kernel, Process ও Thread গাইড →

2Database-এ deadlock — PostgreSQL

দুই transaction, দুই row, উল্টো ক্রমে lock

PostgreSQL-এ UPDATE যে row বদলায় সেটায় row lock নেয়, আর lock ধরে রাখে transaction শেষ (COMMIT / ROLLBACK) হওয়া পর্যন্ত। দুইটা transaction যদি একই দুইটা row উল্টো ক্রমে lock করতে যায় — deadlock। নিচের সব output PostgreSQL 18-এ দুইটা psql session পাশাপাশি চালিয়ে নেওয়া।

setup.sql
CREATE TABLE accounts (
  id      int  PRIMARY KEY,
  name    text NOT NULL,
  balance int  NOT NULL CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Rahim', 1000), (2, 'Karim', 500);
accounts — শুরুতে
idnamebalance
1Rahim1000
2Karim500

দুই session, উল্টো ক্রম

Transaction A (Rahim → Karim transfer) আগে row 1 (Rahim) ধরে, তারপর row 2 (Karim)। Transaction B (Karim → Rahim transfer) ঠিক উল্টো — আগে row 2, তারপর row 1। (টাকার অঙ্কগুলো শুধু demo-র জন্য; আসল বিষয় হলো কোন row আগে lock হচ্ছে।)

Session B — t6-এর পুরো errorSQLSTATE 40P01
ERROR:  deadlock detected
DETAIL:  Process 32816 waits for ShareLock on transaction 801; blocked by process 32817.
Process 32817 waits for ShareLock on transaction 802; blocked by process 32816.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,1) in relation "accounts"
শেষে — SELECT * FROM accounts ORDER BY id;
idnamebalance
1Rahim1100

শুধু A-এর দুইটা UPDATE টিকেছে (row 1 +100, row 2 −500)। B-এর সব কাজ rollback হয়ে গেছে।

Error-টা পড়তে শেখো:
  • প্রতিটা psql session server-এ একটা আলাদা backend process (PID 32816 = B, 32817 = A)। প্রথম write-এর সময় প্রতিটা transaction একটা ID (xid) পায় — A পেয়েছে 801, B পেয়েছে 802।
  • Row lock-এর জন্য অপেক্ষা আসলে হয় "যে transaction row-টা ধরে আছে, সে শেষ হোক" — তাই লেখা waits for ShareLock on transaction 801।
  • দুই লাইন মিলিয়ে: B (32816) অপেক্ষা করছে A-এর (801) জন্য, আর A (32817) অপেক্ষা করছে B-এর (802) জন্য — চক্র।
  • tuple (0,1) = page 0-এর ১ নম্বর row — অর্থাৎ B যে row 1 (Rahim) update করতে চাইছিল।
PostgreSQL কীভাবে deadlock ধরে:
  1. কোনো transaction lock-এর জন্য অপেক্ষা শুরু করলে PostgreSQL সাথে সাথে কিছু করে না — বেশিরভাগ অপেক্ষা এমনিই শেষ হয়, প্রতিবার check করা ব্যয়বহুল।
  2. deadlock_timeout (default 1s) পরেও অপেক্ষা চললে ওই backend deadlock detector চালায়: কে কার জন্য অপেক্ষা করছে তা দিয়ে একটা wait-for graph বানিয়ে cycle খোঁজে।
  3. Cycle পেলে যে detector চালিয়েছে, তার নিজের transaction-টাই abort করে (40P01) — তাতে তার সব lock ছেড়ে যায়, আর অন্যজন সঙ্গে সঙ্গে এগিয়ে যায় (t6-এ A-এর UPDATE শেষ হলো)।
  4. মানুষের গতিতে টাইপ করলে A-এর timer (t5 + 1s) বাজার সময় B তখনো অপেক্ষা শুরু করেনি — cycle নেই, A আর check করে না। B অপেক্ষা শুরু করে পরে, তার timer-এ cycle ধরা পড়ে — তাই শেষে যে অপেক্ষা শুরু করেছে সে-ই বাতিল হয়। দুজন ১ সেকেন্ডের ভেতরে অপেক্ষা শুরু করলে আগেরজনের timer আগে বাজে, তখন সে-ই victim হতে পারে।

সমাধান — একই ক্রমে lock নাও

Deadlock-এর মূলে উল্টো ক্রম। নিয়ম করে দাও: সবসময় ছোট id আগে lock হবে। তাহলে দুইটা transfer একই row (id 1) দিয়ে শুরু করবে — দ্বিতীয়জন শুরুতেই অপেক্ষা করবে, কিন্তু তার হাতে তখন কিছুই নেই, তাই cycle হওয়া অসম্ভব।

fixed transfer (SQL)no deadlock
BEGIN;
-- দুইটা row শুরুতেই, id-এর ক্রমে lock
SELECT id, balance
FROM accounts
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;

UPDATE accounts SET balance = balance - 100 WHERE id = 2;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
COMMIT;

PostgreSQL FOR UPDATE-এর row গুলো sort হওয়ার পরে lock করে, তাই ORDER BY id দিলে lock-এর ক্রমও id-এর ক্রম। এরপরের UPDATE গুলো যেকোনো ক্রমে চলুক — lock তো আগেই হাতে।

C# (Npgsql) — ক্রম + retry
async Task TransferAsync(int from, int to, int amount)
{
    // সবসময় ছোট id আগে — দুই দিকের transfer একই ক্রমে lock নেয়
    var (first, second) = from < to ? (from, to) : (to, from);

    for (int attempt = 1; ; attempt++)
    {
        await using var tx = await conn.BeginTransactionAsync();
        try
        {
            await LockRow(first, tx);   // SELECT ... FOR UPDATE
            await LockRow(second, tx);
            await AddBalance(from, -amount, tx);
            await AddBalance(to, amount, tx);
            await tx.CommitAsync();
            return;
        }
        catch (PostgresException ex) when (ex.SqlState == "40P01" && attempt < 3)
        {
            await tx.RollbackAsync();   // victim হলে আবার পুরোটা
            await Task.Delay(50 * attempt);
        }
    }
}
Production-এ deadlock কমানোর checklist:
  • Consistent order: সব code path-এ row / table একই ক্রমে lock (ORDER BY id, বা app-এ id sort করে)। এটাই আসল সমাধান।
  • Transaction ছোট রাখো: transaction-এর ভেতরে HTTP call, user input বা লম্বা হিসাব না — lock যত কম সময় ধরা, সংঘর্ষ তত কম।
  • Retry: deadlock পুরোপুরি শূন্য করা কঠিন; SQLSTATE 40P01 (আর SERIALIZABLE-এ 40001) পেলে পুরো transaction আবার চালাও।
  • lock_timeout: SET lock_timeout = '2s'; দিলে বেশিক্ষণ অপেক্ষা না করে ERROR: canceling statement due to lock timeout (55P03) দেয় — চিরকাল ঝুলে থাকার বদলে দ্রুত fail।
  • খুঁজে বের করা: log_lock_waits = on, server log-এ দুই query-ই লেখা থাকে (HINT সেটাই বলছে); চলমান অবস্থায় pg_locks আর pg_stat_activity।

3CPU / OS-এ deadlock — ২ thread, ২ mutex

Thread 1: A তারপর B · Thread 2: B তারপর A

একই ঘটনা OS-এর ভেতরে। দুইটা thread দুইটা shared data রক্ষা করতে দুইটা mutex ব্যবহার করে। Thread 1 আগে Mutex A নেয়, তারপর B চায়; Thread 2 আগে B নেয়, তারপর A চায়। Scheduler যদি ঠিক মাঝখানে context switch করে — deadlock। Play বা Step চাপো, তারপর "lock ordering ON" করে আবার দেখো।

Bug-টা code-এ

ভুল — উল্টো ক্রমমাঝে মাঝে ঝুলে যায়
static readonly object A = new object();
static readonly object B = new object();

void Thread1()
{
    lock (A)               // A পেলাম
    {
        Thread.Sleep(10);  // ← এখানে context switch হলে…
        lock (B) { Work(); }   // B চাই — T2-এর হাতে
    }
}

void Thread2()
{
    lock (B)               // B পেলাম
    {
        Thread.Sleep(10);
        lock (A) { Work(); }   // A চাই — T1-এর হাতে
    }
}
ঠিক — সবাই A তারপর Bcycle অসম্ভব
void Thread1()
{
    lock (A) { lock (B) { Work(); } }
}

void Thread2()
{
    lock (A) { lock (B) { Work(); } }   // একই ক্রম
}

// বিকল্প: timeout দিয়ে চেষ্টা, না পেলে হাতেরটা ছেড়ে দাও
if (Monitor.TryEnter(B, TimeSpan.FromMilliseconds(100)))
{
    try { Work(); } finally { Monitor.Exit(B); }
}
else { /* A ছেড়ে দিয়ে একটু পরে আবার চেষ্টা */ }

// Thread 1

Bug-টা প্রতিবার হয় না — দুই thread-এর প্রথম lock-এর পরে ঠিক সময়ে context switch হলেই হয়। তাই test-এ ধরা পড়ে না, production-এ load বাড়লে হঠাৎ app "freeze"। Thread.Sleep শুধু সম্ভাবনা বাড়াতে দেওয়া।

Resource-Allocation Graph আর Wait-for Graph

Resource-Allocation Graph (RAG)

○ = process / thread, ▭ = resource, ভেতরের ● = একটা instance। Resource → Process (solid) = assignment edge, "ধরে আছে"। Process → Resource (dashed) = request edge, "চাইছে"। লাল পথটা একটা cycle।

Wait-for Graph — শুধু process

RAG থেকে resource node সরিয়ে দিলে: "Ti → Tj" মানে Ti যে resource চায় সেটা Tj-এর হাতে। PostgreSQL ঠিক এই graph বানিয়েই cycle খোঁজে (A → B → A)।

Cycle থাকলেই কি deadlock?
  • প্রতিটা resource-এর একটাই instance হলে (mutex, row lock) — হ্যাঁ, cycle মানেই deadlock।
  • কোনো resource-এর একাধিক instance হলে (যেমন ৩টা printer) — cycle থাকা প্রয়োজনীয় কিন্তু যথেষ্ট না; cycle-এর বাইরের কেউ একটা instance ছেড়ে দিলে চক্র ভেঙে যেতে পারে। এই ক্ষেত্রেই Banker's-এর মতো হিসাব লাগে।
  • Cycle-ই না থাকলে deadlock অসম্ভব — দুই ক্ষেত্রেই।

4Deadlock-এর ৪টি শর্ত (Coffman conditions)

চারটাই একসাথে সত্য হলে তবেই deadlock — যেকোনো একটা ভাঙো, deadlock অসম্ভব

1971-এ E. G. Coffman ও সহকর্মীরা দেখান, deadlock হতে হলে নিচের চারটা শর্তই একই সময়ে পূরণ হতে হবে। এগুলো necessary শর্ত — তাই deadlock prevention মানে হলো design করে অন্তত একটাকে কখনো সত্য হতে না দেওয়া।

1Mutual Exclusion

Resource-টা একসময় একজনই ব্যবহার করতে পারে; অন্যজন চাইলে অপেক্ষা করতে হয়।

DB
একটা row-তে একসাথে একটাই transaction write lock রাখতে পারে।
Thread
Mutex A একবারে একটা thread-এর হাতে।
ভাঙলে
Resource share-যোগ্য করো — read-only data, MVCC (PostgreSQL-এ reader writer-কে block করে না), lock-free / atomic operation (Interlocked, CAS)। কিন্তু write-এর জন্য প্রায়ই সম্ভব না, তাই এটা ভাঙা সবচেয়ে কঠিন।

2Hold and Wait

একটা resource হাতে রেখে আরেকটার জন্য অপেক্ষা করা।

DB
A row 1-এর lock ধরে রেখেই row 2 চাইছে (t5)।
Thread
Thread 1 Mutex A ছাড়েনি, অথচ B-র জন্য blocked।
ভাঙলে
শুরুতেই সব একসাথে নাও (সব পেলে চলো, নয়তো কিছুই না), অথবা নতুন কিছু চাওয়ার আগে হাতের সব ছেড়ে দাও (try-lock ব্যর্থ হলে release + back-off)। খরচ: resource অকারণে আটকে থাকে, কেউ কেউ starve করতে পারে।

3No Preemption

কারো হাত থেকে resource জোর করে কেড়ে নেওয়া যায় না; holder নিজে না ছাড়লে মুক্ত হয় না।

DB
B-এর row lock অন্য কেউ কেড়ে নিতে পারে না — B commit / rollback করলেই শুধু ছাড়ে।
Thread
OS অন্য thread-এর mutex কেড়ে নিয়ে কাউকে দেয় না।
ভাঙলে
কেড়ে নেওয়ার ব্যবস্থা রাখো — DB-র deadlock detector victim-কে abort করে তার lock ছাড়িয়ে দেয়; Monitor.TryEnter(timeout) বা lock_timeout ব্যর্থ হলে নিজের lock ছেড়ে দেয়। CPU / memory-র মতো resource-এ সহজ (state save করা যায়), mutex বা printer-এ মাঝপথে কেড়ে নিলে data নষ্ট হতে পারে।

4Circular Wait

অপেক্ষার একটা চক্র: P1 → P2 → … → Pn → P1, প্রত্যেকে পরেরজনের হাতের resource চায়।

DB
A অপেক্ষা করছে B-এর জন্য, B অপেক্ষা করছে A-এর জন্য (error-এর DETAIL-এর দুই লাইন)।
Thread
T1 → Mutex B → T2 → Mutex A → T1।
ভাঙলে
সব resource-কে একটা global order দাও, সবাই ছোট থেকে বড় ক্রমে নেবে (ORDER BY id, আগে A পরে B)। যে Ri ধরে আছে সে শুধু j > i এমন Rj চাইতে পারে — চক্রে ফিরে আসতে হলে কোথাও ছোট নম্বর চাইতে হতো, তাই চক্র অসম্ভব। বাস্তবে সবচেয়ে প্রচলিত উপায়; Linux kernel-এর lockdep এই নিয়ম ভাঙলে warning দেয়।
মনে রাখার কৌশল: প্রথম তিনটা হলো system-এর নীতি (resource কেমন আচরণ করে), চতুর্থটা হলো একটা নির্দিষ্ট মুহূর্তের অবস্থা। প্রথম তিনটা সত্য থাকলে deadlock সম্ভব; চতুর্থটা ঘটলে deadlock হয়ে গেছে। Interview-এ প্রায়ই জিজ্ঞেস করে "কোনটা ভাঙা সবচেয়ে সহজ?" — উত্তর: Circular Wait (lock ordering)।

5Deadlock সামলানোর ৪টি কৌশল

আগে ঠেকাও, পাশ কাটাও, ধরে সারাও — নয়তো উপেক্ষা করো

OS (বা database) deadlock নিয়ে চারভাবে চিন্তা করতে পারে। প্রথম দুইটা deadlock ঘটতেই দেয় না, তৃতীয়টা ঘটতে দিয়ে পরে সারায়, চতুর্থটা ধরে নেয় এটা এত বিরল যে খরচ করার মানে নেই।

কৌশলমূল ideaউদাহরণখরচ / সমস্যা
1PreventionDesign করেই ৪ শর্তের অন্তত একটা অসম্ভব করাLock ordering, সব lock একসাথে নেওয়া, try-lock + back-offResource utilisation কমে; নিয়ম মানা developer-এর দায়িত্ব
2Avoidanceপ্রতিটা request-এ দেখা — দিলে system safe state-এ থাকবে কি না; না থাকলে অপেক্ষাBanker's Algorithm (নিচে)প্রত্যেক process-এর Max আগে জানতে হয়; প্রতিটা request-এ হিসাব
3Detection & RecoveryDeadlock হতে দাও, মাঝে মাঝে wait-for graph-এ cycle খোঁজো, পেলে victim বেছে abort / rollbackPostgreSQL, MySQL InnoDB, SQL ServerVictim-এর কাজ নষ্ট, retry লাগে; একই victim বারবার হলে starvation
4Ignorance (Ostrich)উটপাখির মতো বালিতে মাথা গুঁজে থাকা — ধরে নাও হবে না; হলে user process kill / reboot করবেWindows, Linux, macOS — user program-এর mutex deadlockখরচ শূন্য, কিন্তু হলে app ঝুলে থাকে
বাস্তবে কে কোনটা করে:
  • সাধারণ OS (Linux, Windows) তোমার program-এর দুই thread deadlock করলে কিছুই করে না — process ঝুলে থাকে, তুমি kill করো। Detection-এর খরচ আর ভুল abort-এর ঝুঁকির চেয়ে এটা সস্তা। তবে kernel নিজের ভেতরের lock-এর জন্য prevention (lock ordering) মেনে চলে।
  • Database detection & recovery করে, কারণ transaction rollback করা নিরাপদ — ACID-এর কারণে victim-এর অর্ধেক কাজ কোথাও থেকে যায় না।
  • Recovery-র উপায়: (ক) cycle-এর সব process abort, (খ) একটা একটা করে abort যতক্ষণ না cycle ভাঙে, (গ) resource preempt করে victim-কে আগের অবস্থায় rollback। Victim বাছাইয়ে দেখা হয় কতটা কাজ নষ্ট হবে, কতগুলো resource ধরে আছে, আগে কতবার victim হয়েছে।

6Banker's Algorithm — deadlock avoidance

ঋণ দেওয়ার আগে ব্যাংক দেখে — সবাইকে শেষ পর্যন্ত মেটানো যাবে তো?

Dijkstra-র algorithm। নামটা এসেছে ব্যাংক থেকে: ব্যাংক কখনো এমনভাবে টাকা ধার দেয় না যাতে সব গ্রাহকের সর্বোচ্চ চাহিদা আর মেটানো না যায়। প্রতিটা process শুরুতেই ঘোষণা করে প্রতিটা resource-এর সর্বোচ্চ কতগুলো instance তার লাগতে পারে। এরপর প্রতিটা request-এ OS হিসাব করে — দিলে system কি safe state-এ থাকবে? থাকলে দেয়, না থাকলে process-কে অপেক্ষা করায় (যদিও resource এই মুহূর্তে খালি আছে)।

Available[j]resource j-এর এখন কতগুলো instance খালি।
Max[i][j]process i সর্বোচ্চ কতগুলো j চাইতে পারে (আগে থেকে ঘোষিত)।
Allocation[i][j]process i-এর হাতে এখন কতগুলো j।
Need = Max − Allocationকাজ শেষ করতে i-এর আরও কতগুলো j লাগতে পারে।
Safe state কী? এমন একটা ক্রম <Pa, Pb, …> (safe sequence) আছে যেখানে প্রত্যেক process-এর বাকি Need = এখনকার Available + তার আগে শেষ হওয়া সবার ফেরত দেওয়া resource দিয়ে মেটানো যায়। অর্থাৎ সবচেয়ে খারাপ ক্ষেত্রেও (সবাই একসাথে Max চাইলেও) সবাইকে একে একে শেষ করানো সম্ভব।
  • Safe ⇒ deadlock হবে না (OS নিশ্চিত করতে পারে)।
  • Unsafe ⇒ deadlock হতে পারে — নিশ্চিত না, কিন্তু OS আর গ্যারান্টি দিতে পারে না। Deadlocked state সবসময় unsafe, কিন্তু সব unsafe state deadlocked না।

Classic উদাহরণ — ৫টা process, ৩ ধরনের resource

Resource A, B, C-এর মোট instance যথাক্রমে 10, 5, 7। এখনকার অবস্থা (Silberschatz-এর textbook উদাহরণ):

যাচাই: ΣAllocation = (7, 2, 5), সাথে Available (3, 3, 2) যোগ করলে (10, 5, 7) = মোট instance ✓। Need = Max − Allocation, যেমন P0: (7,5,3) − (0,1,0) = (7,4,3)।

Safety algorithm — ধাপে ধাপে

Work   = Available           // হাতে যা খালি
Finish = [false] * n

// নিয়ম: P0 → Pn-1 ক্রমে বারবার pass দাও;
// যার Need ≤ Work, সে "শেষ করতে পারবে"
repeat until কোনো pass-এ কেউ শেষ হয় না:
  for i in 0 .. n-1:
    if !Finish[i] and Need[i] ≤ Work:
      Work = Work + Allocation[i]   // শেষে ফেরত দেবে
      Finish[i] = true
      sequence.add(Pi)

safe  ⇔  সবার Finish == true

Need ≤ Work মানে vector-এর প্রতিটা উপাদান ≤ (A, B, C তিনটাতেই)।

কেন Work + Allocation? Pi-এর বাকি Need মেটানো গেলে সে শেষ করবে আর হাতের সব resource (Allocation) ফেরত দেবে — তাই পরেরজনের জন্য Work বাড়ে।

Scan rule: এখানে প্রতিটা pass P0 থেকে P4 পর্যন্ত চলে, pass-এর মাঝে কেউ শেষ হলেও pass চলতে থাকে। অন্য rule (যেমন প্রতিবার P0 থেকে নতুন করে খোঁজা) দিলে অন্য একটা safe sequence আসতে পারে — একাধিক safe sequence থাকা স্বাভাবিক, সবই সঠিক।

খরচ: O(m × n²) — n process, m resource type।

Resource-request algorithm

Process Pi যখন Request vector চায়, OS তিনটা ধাপে সিদ্ধান্ত নেয়:

1. if Request > Need[i]:    error  // ঘোষিত Max-এর বেশি চাইছে
2. if Request > Available:  wait   // এখন যথেষ্ট খালি নেই
3. ধরে নাও দিয়ে দিলাম (pretend):
     Available     -= Request
     Allocation[i] += Request
     Need[i]       -= Request
   if safety(নতুন state) == safe:  grant  ✓
   else: পুরনো state ফেরত, Pi wait

খেয়াল করো ধাপ ৩: resource খালি থাকলেও OS দিতে অস্বীকার করতে পারে — কারণ দিলে system unsafe state-এ চলে যাবে। এটাই avoidance-এর মূল কথা: শুধু "এখন আছে কি না" না, "দিলে ভবিষ্যতে সবাই শেষ করতে পারবে কি না"।

তিনটা request — পরপর (একই state-এর ওপর)

নিজে চালিয়ে দেখো — Banker's simulator

সংখ্যা বদলাও (Allocation, Max, Available), Check safe state চাপলে safety algorithm row ধরে ধরে চলবে — Work vector কীভাবে বাড়ে আর Finish flag কীভাবে বসে দেখবে। নিচের form-এ request দিয়ে দেখো OS grant করে নাকি অপেক্ষা করায়।

Preset:
Work = — Safe sequence:

    "Unsafe state" preset = textbook state-এ P1 (1,0,2) আর তারপর P0 (0,2,0) safety check ছাড়া দিয়ে দিলে যা হতো। Grant হলে নতুন state টেবিলে বসে যায় — পরপর একাধিক request দিয়ে দেখতে পারো (যেমন উপরের তিনটা: P1 (1,0,2), তারপর P4 (3,3,0), তারপর P0 (0,2,0))।

    Banker's-এর সীমাবদ্ধতা:
    • প্রত্যেক process-কে শুরুতেই প্রতিটা resource-এর Max জানাতে হয় — বাস্তব program আগে থেকে জানে না কতগুলো lock / file / memory লাগবে।
    • Process আর resource-এর সংখ্যা স্থির ধরে নেয় — বাস্তবে process আসে-যায়, device যোগ হয় বা নষ্ট হয়।
    • প্রতিটা request-এ O(m × n²) হিসাব — হাজার হাজার thread আর lock থাকলে খুব ব্যয়বহুল।
    • অতি সতর্ক: unsafe মানেই deadlock না, তবু request আটকে রাখে — resource খালি পড়ে থাকে, utilisation কমে।
    • ধরে নেয় process সীমিত সময়ে resource ফেরত দেবে। তাই বাস্তব general-purpose OS এটা ব্যবহার করে না; ধারণাটা interview আর কিছু বিশেষ system (যেমন নির্দিষ্ট resource-এর embedded / batch system)-এর জন্য।

    QInterview-এ যা আসে

    Deadlock, Starvation আর Livelock — পার্থক্য কী?
    • Deadlock: একদল process একে অপরের জন্য অপেক্ষায় blocked — কেউ কিছু করছে না, কেউ এগোচ্ছে না।
    • Livelock: process গুলো blocked না, অনবরত state বদলাচ্ছে (যেমন lock না পেয়ে ছেড়ে দিয়ে আবার চেষ্টা), কিন্তু কাজ এগোচ্ছে না — সরু করিডোরে দুইজন একসাথে বারবার একই দিকে সরে যাওয়া। সমাধান: random back-off।
    • Starvation: system এগোচ্ছে, কিন্তু একটা নির্দিষ্ট process অনির্দিষ্টকাল resource পাচ্ছে না (কম priority, বা প্রতিবার deadlock victim)। সমাধান: aging, fair queue।
    একটা মাত্র thread দিয়ে কি deadlock হতে পারে?

    হ্যাঁ — non-reentrant lock হলে। Thread একটা mutex ধরে আবার একই mutex চাইলে নিজেই নিজের জন্য চিরকাল অপেক্ষা করে (self-deadlock)। pthread-এর PTHREAD_MUTEX_NORMAL এভাবে আটকে যায়, C#-এর SemaphoreSlim(1,1)-এ দুবার WaitAsync করলেও তাই। অন্যদিকে C#-এর lock (Monitor), Java-র synchronized আর ReentrantLock reentrant — একই thread আবার নিলে শুধু একটা counter বাড়ে, deadlock হয় না।

    Database কীভাবে deadlock ধরে আর কাকে বাতিল করে?
    • সবাই wait-for graph-এ cycle খোঁজে, পার্থক্য কখন আর কাকে বাতিল করে তাতে।
    • PostgreSQL: lock-এর জন্য deadlock_timeout (1s) অপেক্ষার পর check; যে check করে সে-ই victim; error 40P01।
    • MySQL InnoDB: lock wait শুরু হওয়ার সঙ্গে সঙ্গে detect করে (innodb_deadlock_detect), সাধারণত "ছোট" transaction-টা (কম row বদলেছে) rollback করে; error 1213।
    • SQL Server: lock monitor thread নির্দিষ্ট সময় পরপর খোঁজে, DEADLOCK_PRIORITY আর rollback-এর খরচ দেখে victim বাছে; error 1205।
    Banker's Algorithm বাস্তব OS-এ প্রায় ব্যবহার হয় না কেন?

    কারণ এর অনুমানগুলো বাস্তবে মেলে না: process-এর Max আগে জানা থাকে না, process আর resource-এর সংখ্যা সবসময় বদলায়, প্রতিটা request-এ O(m × n²) হিসাব অনেক ব্যয়বহুল, আর unsafe দেখলেই আটকে রাখায় resource খালি পড়ে থাকে। তাই সাধারণ OS ostrich পদ্ধতি নেয়, database detection & recovery, আর application code prevention (lock ordering)।

    নিজের code-এ deadlock কীভাবে ঠেকাবে?
    • সব lock-এর একটা নির্দিষ্ট ক্রম ঠিক করো, সব জায়গায় সেই ক্রমে নাও (দরকার হলে object id / hash দিয়ে sort)।
    • Lock ধরে রেখে বাইরের code (callback, event, virtual method, network call) ডেকো না — সে কোন lock নেবে তুমি জানো না।
    • Lock-এর scope যত ছোট সম্ভব; একসাথে অনেক lock লাগলে design আবার ভাবো (একটা coarse lock, বা immutable data)।
    • Timeout-ওয়ালা চেষ্টা (Monitor.TryEnter, tryLock(timeout), lock_timeout) — না পেলে হাতের সব ছেড়ে retry।
    • C#-এ async code-এ .Result / .Wait() দিয়ে block কোরো না — UI বা পুরনো ASP.NET-এর SynchronizationContext-এ এটা ক্লাসিক deadlock।
    Unsafe state মানেই কি deadlock?

    না। Safe state ⊂ deadlock-free; unsafe state মানে শুধু OS আর গ্যারান্টি দিতে পারছে না — process গুলো যদি পুরো Max না চেয়েই resource ছেড়ে দেয়, তাহলে কখনো deadlock হবে না। কিন্তু প্রতিটা deadlocked state অবশ্যই unsafe।

    Resource-Allocation Graph-এ cycle থাকলেই কি deadlock?

    প্রতিটা resource-এর একটা করে instance হলে হ্যাঁ। কোনো resource-এর একাধিক instance থাকলে cycle থাকা জরুরি কিন্তু যথেষ্ট না — cycle-এর বাইরের কোনো process একটা instance ছাড়লে cycle-এর কেউ সেটা পেয়ে এগোতে পারে। আর cycle না থাকলে কখনোই deadlock নেই।

    Production-এ app ঝুলে গেছে — deadlock কি না কীভাবে বুঝবে?

    সব thread-এর stack দেখো: Java-তে jstack (নিজেই "Found one Java-level deadlock" লেখে), .NET-এ dotnet-dump / dotnet-stack, native-এ gdb দিয়ে thread apply all bt। দুই thread একে অপরের ধরা lock-এ আটকে থাকলে সেটাই deadlock। Database-এ log_lock_waits = on, server log-এর deadlock report, আর pg_locks join pg_stat_activity দেখো।

    7Short note — Multiprogramming vs Multitasking

    দুইটাই "একসাথে অনেক program" — পার্থক্য কখন আর কেন CPU বদলায়

    Multiprogramming: একাধিক program একসাথে memory-তে রাখা হয়। চলমান program যখন I/O-র জন্য (disk, printer) অপেক্ষা করে, CPU বসে না থেকে আরেকটা program চালায়। Switch হয় শুধু তখনই যখন চলমানটা নিজে থামে — non-preemptive। লক্ষ্য: CPU utilisation। পুরনো batch system।

    Multitasking (time-sharing): CPU প্রতিটা task-কে ছোট time slice (কয়েক millisecond) দেয়; timer interrupt এলে OS জোর করে পরেরটায় যায় — preemptive। এত দ্রুত ঘোরে যে মনে হয় সব একসাথে চলছে। লক্ষ্য: response time / interactivity। আজকের Windows, Linux, macOS।

    • Multithreading: একটা process-এর ভেতরে একাধিক thread, একই memory share করে — আর এখান থেকেই mutex আর deadlock-এর গল্প শুরু।
