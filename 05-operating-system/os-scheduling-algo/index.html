0Basics — scheduler, ready queue, dispatcher

Process কীভাবে তৈরি হয় আর ready queue-তে ঢোকে, সেটা OS, Kernel, Process ও Thread গাইডে আছে। এখানে প্রশ্ন একটাই: ready queue থেকে পরের process কে CPU পাবে, আর কতক্ষণের জন্য?

CPU scheduler (short-term)

Ready queue-এর process গুলোর মধ্যে থেকে একজনকে বেছে নেয়। এটাই "scheduling algorithm"। খুব ঘন ঘন চলে (প্রতি কয়েক millisecond), তাই নিজে দ্রুত হতে হয়।

Ready queue

যারা চলার জন্য পুরো প্রস্তুত, শুধু CPU পাচ্ছে না। নামে queue, কিন্তু সবসময় FIFO না — algorithm অনুযায়ী এটা priority queue, sorted list বা red-black tree-ও হতে পারে।

Dispatcher

Scheduler যাকে বাছল, তাকে আসলে CPU-তে বসায়: আগেরজনের register/PC সেভ করে (PCB-তে), নতুনজনেরটা load করে, user mode-এ ফিরে তার PC-তে jump। এই সময়টুকু dispatch latency।

যে শব্দ আর formula গুলো সবখানে লাগবে

Arrival Time (AT)

Process কখন ready queue-তে এল।

Burst Time (BT)

একটানা কতক্ষণ CPU লাগবে (CPU burst)। বাস্তবে process CPU burst আর I/O burst পালা করে চালায়; এখানে প্রতিটা process-এর একটাই CPU burst ধরে হিসাব।

Completion Time (CT)

Process কখন পুরো শেষ হলো (Gantt chart-এ তার শেষ block-এর ডান দিক)।

Turnaround TimeTAT = CT − AT

আসা থেকে শেষ হওয়া পর্যন্ত মোট সময় — অপেক্ষা + চলা।

Waiting TimeWT = TAT − BT

Ready queue-তে বসে থাকার মোট সময় (মাঝে মাঝে কয়েকবার অপেক্ষা করলে সব যোগ)। Algorithm তুলনায় সবচেয়ে বেশি ব্যবহৃত মাপকাঠি: average WT।

Response TimeRT = প্রথমবার CPU পাওয়া − AT

প্রথম সাড়া পেতে কত দেরি। Interactive system-এ (UI, terminal) এটাই আসল। Non-preemptive algorithm-এ process একবারেই শেষ করে, তাই সেখানে RT = WT।

Throughput

প্রতি একক সময়ে কয়টা process শেষ হয়। যেমন 16 unit-এ 4টা process শেষ → 4/16 = 0.25 process/unit।

CPU utilisationbusy time ÷ মোট সময়

CPU কত শতাংশ সময় কাজে ছিল। ready queue ফাঁকা থাকলে CPU idle — Gantt chart-এ ডোরাকাটা ঘর।

Context switch cost

এক process থেকে আরেক process-এ যাওয়ার খরচ — register save/restore, kernel-এ ঢোকা-বের হওয়া, আর পরে cache/TLB আবার গরম হওয়া। সরাসরি খরচ কয়েক microsecond, কিন্তু এই সময় কোনো "কাজের কাজ" হয় না। এই পেজের হিসাবে context switch-এর সময় 0 ধরা হয়েছে, শুধু কয়বার হলো সেটা গোনা হয়েছে।

লক্ষ্য: CPU utilisation আর throughput বাড়ানো; turnaround, waiting আর response time কমানো। সবগুলো একসাথে সেরা করা যায় না — প্রতিটা algorithm কোনো একটা দিকে ছাড় দেয়। উদাহরণ: P1 AT=0, BT=5, প্রথম CPU পেল 2-তে, শেষ হলো 9-এ → TAT = 9 − 0 = 9, WT = 9 − 5 = 4, RT = 2 − 0 = 2।

1Preemptive বনাম Non-preemptive

সব algorithm-কে প্রথমে এই এক প্রশ্নে ভাগ করা যায়: একবার CPU পেলে process-কে কি মাঝপথে সরিয়ে দেওয়া যায়?

Non-preemptive (cooperative)

একবার CPU পেলে process নিজে না ছাড়া পর্যন্ত চলবে — হয় burst শেষ করবে (terminate), নয়তো I/O-র জন্য block হবে। OS জোর করে কেড়ে নেয় না।

Analogy: ডাক্তারের চেম্বার — একজন রোগী ভেতরে ঢুকলে তার দেখা শেষ না হওয়া পর্যন্ত পরের জন ঢুকতে পারে না, বাইরে যত জরুরি রোগীই আসুক।

Preemptive

চলমান process-কে OS মাঝপথে থামিয়ে ready queue-তে ফেরত পাঠাতে পারে, তারপর অন্যকে CPU দেয়। পরে সে যেখানে থেমেছিল সেখান থেকে চলবে।

Analogy: হাসপাতালের emergency — সাধারণ রোগী দেখা চলাকালীন গুরুতর রোগী এলে ডাক্তার তাকে আগে দেখেন; অথবা দাবা খেলার clock — নির্দিষ্ট সময় শেষ হলেই চাল দিতে হবে।

তুলনা যেন ন্যায্য হয়, তাই FCFS, SJF, SRTF, Priority আর RR — সবগুলো নিচের একই ৪টা process-এ চালানো হয়েছে। Time-এর একক "unit" (বাস্তবে ms ভাবতে পারো)। Priority: ছোট সংখ্যা = বেশি priority।

2FCFS — First Come First Served

Non-preemptiveReady queue = সাধারণ FIFO

যে আগে আসে, সে আগে পায় — দোকানের লাইনের মতো। Process এলে queue-এর শেষে দাঁড়ায়; CPU ফাঁকা হলে queue-এর সামনের জন চলে, আর burst শেষ (বা block) না হওয়া পর্যন্ত চলতেই থাকে।

হিসাব কীভাবে: P1 আগে এসেছে, 0–7 চলে। তারপর arrival order-এ P2 (7–11), P3 (11–12), P4 (12–16)। P3-এর burst মাত্র 1, তবু সে 7 unit বসে ছিল — কারণ তার সামনে লম্বা P1 আর P2। Average WT = (0 + 5 + 7 + 7) / 4 = 4.75।

সুবিধা

  • বোঝা আর implement করা সবচেয়ে সহজ (একটা linked-list queue)।
  • কোনো starvation নেই — আগে বা পরে সবাই CPU পাবে।
  • Context switch সর্বনিম্ন।

অসুবিধা

  • Average WT প্রায়ই অনেক বেশি, আর arrival order-এর উপর পুরো নির্ভর।
  • Convoy effect (নিচে)।
  • Non-preemptive, তাই interactive / time-sharing system-এ অচল।

Convoy effect — একটা লম্বা job, পেছনে সবাই আটকে

হাইওয়েতে একটা ধীর ট্রাকের পেছনে যেমন গাড়ির সারি (convoy) জমে যায়। FCFS-এ একটা লম্বা CPU-bound process আগে CPU পেলে পেছনের সব ছোট process (প্রায়ই I/O-bound — যাদের CPU লাগে অল্প, তারপর আবার I/O-তে চলে যায়) লম্বা সময় বসে থাকে। ফল: average WT আকাশছোঁয়া, আর সেই সময় I/O device গুলোও অলস — কারণ I/O-bound process গুলো CPU না পেয়ে নতুন I/O request-ই দিতে পারছে না। তারপর লম্বা job I/O-তে গেলে CPU-ই অলস পড়ে থাকে।

একই তিনটা job (একটা 24 unit, দুইটা 3 unit), সবাই time 0-তে এসেছে — শুধু queue-তে দাঁড়ানোর order আলাদা:

একই কাজ, average WT 17 বনাম 3 — প্রায় ৬ গুণ পার্থক্য, শুধু order বদলে। মোট কাজ (30 unit) আর throughput দুই ক্ষেত্রেই সমান, কিন্তু লম্বা job আগে থাকলে ছোট দুইটা job-কে 24 আর 27 unit বসে থাকতে হয়। "ছোট job আগে" — এই ধারণা থেকেই SJF।

3SJF ও SRTF — Shortest Job First

SJF: Non-preemptiveSRTF: Preemptive

CPU ফাঁকা হলে ready queue-তে যার burst সবচেয়ে ছোট, তাকে দাও। Preemptive version-এর নাম SRTF (Shortest Remaining Time First) — নতুন process এলে তার burst যদি চলমান process-এর বাকি সময়ের চেয়ে ছোট হয়, চলমানটাকে সরিয়ে নতুনটা চলে।

Non-preemptive SJF

ধাপ: time 0-তে শুধু P1 আছে, তাই সে চলে — non-preemptive বলে 7 পর্যন্ত কেউ থামাতে পারে না (মাঝে P2, P3, P4 এসে গেলেও)। 7-এ queue-তে P2(4), P3(1), P4(4) → সবচেয়ে ছোট P3। তারপর P2 আর P4 দুজনেরই burst 4 — tie, তাই আগে আসা P2। Average WT = (0 + 6 + 3 + 7) / 4 = 4 (FCFS-এ ছিল 4.75)।

Preemptive — SRTF

ধাপ: 2-তে P2 (burst 4) এল, P1-এর বাকি 5 → 4 < 5, P1 preempted। 4-এ P3 (1) এল, P2-এর বাকি 2 → P2 preempted। 5-এ P3 শেষ; বাকি P2(2), P4(4), P1(5) → P2। তারপর P4, শেষে P1। Average WT = (9 + 1 + 0 + 2) / 4 = 3 — সবার মধ্যে সর্বনিম্ন, কিন্তু context switch বেশি, আর লম্বা P1 একাই 9 unit বসে ছিল।

কেন optimal?

যেকোনো order-এ একটা লম্বা job যদি একটা ছোট job-এর আগে থাকে, দুটোর জায়গা বদলালে ছোটটার waiting যতটা কমে, লম্বাটার ততটা বাড়ে না (ছোট job আগে গেলে বেশি সংখ্যক process কম অপেক্ষা করে)। তাই সবাই একসাথে ready থাকলে SJF provably minimum average waiting time দেয়; arrival আলাদা হলে preemptive SRTF সেটা দেয়।

সমস্যা ১ — burst time আগে জানা যায় না

OS জানে না পরের CPU burst কত লম্বা হবে। তাই আগের burst গুলো থেকে অনুমান করা হয় — exponential averaging:

τ(n+1) = α · t(n) + (1 − α) · τ(n)

t(n) = সর্বশেষ আসল burst, τ(n) = আগের অনুমান, 0 ≤ α ≤ 1 (সাধারণত 0.5)। α বড় হলে সাম্প্রতিক burst-এ বেশি গুরুত্ব।

α = 0.5, শুরুর অনুমান τ₀ = 10n = 01234
আসল burst t(n)6464—
অনুমান τ(n)100.5·6 + 0.5·10 = 80.5·4 + 0.5·8 = 60.5·6 + 0.5·6 = 60.5·4 + 0.5·6 = 5
সমস্যা ২ — starvation: ছোট job একটার পর একটা আসতে থাকলে লম্বা job কখনো CPU পায় না। উপরের SRTF-এ P1 প্রথম এসেও সবার শেষে শেষ হয়েছে। বাস্তবে pure SJF তাই প্রায় ব্যবহার হয় না; তবে ধারণাটা (ছোট/interactive কাজ আগে) অনেক scheduler-এ ঢুকে আছে।

4Priority Scheduling

Preemptive অথবা Non-preemptive — দুটোই হয়

প্রতিটা process-এর একটা priority সংখ্যা। CPU যায় সবচেয়ে বেশি priority-র process-এ। এই পেজে (আর বেশিরভাগ textbook-এ) ছোট সংখ্যা = বেশি priority — priority 1, priority 4-এর আগে চলবে। (কিছু system উল্টো convention ব্যবহার করে, তাই interview-এ আগে জিজ্ঞেস করে নাও।) SJF আসলে priority scheduling-এরই একটা বিশেষ রূপ, যেখানে priority = burst time।

Non-preemptive priority

নতুন বেশি-priority process এলে শুধু queue-এর সামনে বসে; চলমান process শেষ (বা block) হলে তবেই সে পাবে।

Preemptive priority

নতুন process-এর priority চলমানটার চেয়ে বেশি হলে সাথে সাথে চলমানটাকে সরিয়ে দেয়। Real-time system-এ এটাই নিয়ম।

Preemptive

পার্থক্য: Non-preemptive-এ P2 (priority 1, সবচেয়ে জরুরি) 2-তে এসেও 7 পর্যন্ত বসে থাকে। Preemptive-এ সে এসেই P1-কে (priority 3) সরিয়ে দেয় — P2-এর WT 5 থেকে 0। দুই ক্ষেত্রেই P3 (priority 4, সবচেয়ে কম) সবার শেষে, WT = 11।

Starvation — কম priority-র process অনন্তকাল অপেক্ষা

বেশি priority-র process একটানা আসতে থাকলে কম priority-র process কখনো CPU পায় না — indefinite blocking / starvation। (গল্প আছে, 1973-এ MIT-র IBM 7094 বন্ধ করার সময় একটা কম priority-র job পাওয়া গিয়েছিল যেটা 1967 থেকে অপেক্ষা করছিল।) নিচে P2 (priority 4) এসেছে 1-এ, কিন্তু priority 1-এর job একটার পর একটা আসছে:

Aging — অপেক্ষা যত লম্বা, priority তত বেশি

5Round Robin (RR)

PreemptiveFIFO queue + timer

FCFS-এর মতোই FIFO queue, কিন্তু প্রত্যেকে একবারে সর্বোচ্চ একটা time quantum (time slice, q) পায়। Quantum শেষ হলে timer interrupt → process queue-এর শেষে চলে যায়, সামনের জন CPU পায়। Burst quantum-এর আগেই শেষ হলে সে নিজেই CPU ছেড়ে দেয়। Time-sharing system-এর জন্যই এটা বানানো।

খেয়াল করো: 2-তে P2 এল আর একই মুহূর্তে P1-এর quantum শেষ — নিয়ম অনুযায়ী নতুন P2 আগে queue-তে, তারপর P1। প্রতি process সর্বোচ্চ (n − 1) × q সময়ের মধ্যে আবার CPU পায়, তাই starvation নেই আর response time ভালো (average RT = 1.5, FCFS-এ 4.75)। দাম: 8টা context switch, আর average WT (5) SJF-এর চেয়ে বেশি।

Time quantum কত বড় হবে?

q খুব বড় (→ ∞)

কেউই quantum শেষ করতে পারে না, সবাই নিজের burst একবারে শেষ করে — RR হুবহু FCFS হয়ে যায়। Response time খারাপ, convoy effect ফিরে আসে।

q খুব ছোট (→ 0)

মনে হয় প্রত্যেকের নিজের ধীর CPU আছে (processor sharing), কিন্তু প্রতি quantum-এ context switch — CPU-র বড় অংশ কাজের বদলে switch-এই খরচ হয়। 10 unit-এর একটা process: q = 12 → 0টা switch, q = 6 → 1টা, q = 1 → 9টা।

নিচে একই ৫টা process (P1–P5, burst 5, 3, 8, 6, 2; arrival 0–4) আলাদা আলাদা quantum-এ। প্রতিটা সারি ওই engine দিয়ে হিসাব করা। ধরো প্রতিটা context switch-এ 0.1 unit নষ্ট হয় — শেষ কলাম সেই overhead:

Pattern: q বাড়লে context switch আর overhead কমে, কিন্তু response time বাড়ে; q = 100 (≈ ∞)-এ ফল FCFS-এর সাথে হুবহু এক। Average WT সবসময় একদিকে যায় না — এটা input-এর উপর নির্ভর করে। Rule of thumb: quantum context-switch সময়ের চেয়ে অনেক বড়, আর সাধারণ CPU burst-এর চেয়ে একটু বড় রাখো — মোটামুটি 80% CPU burst যেন quantum-এর চেয়ে ছোট হয়, যাতে বেশিরভাগ process এক quantum-এই শেষ (বা I/O-তে) চলে যায়। বাস্তব OS-এ quantum সাধারণত 10–100 ms, আর context switch লাগে ১০ µs-এরও কম।

QInterview-এ যা আসে

Average waiting time-এর জন্য optimal algorithm কোনটা?

সব process একসাথে ready থাকলে SJF provably minimum average WT দেয় (ছোট job আগে গেলে বেশি সংখ্যক process কম অপেক্ষা করে)। Arrival আলাদা হলে preemptive version SRTF optimal। সমস্যা হলো burst time আগে জানা যায় না — exponential averaging দিয়ে অনুমান করতে হয় — আর লম্বা job starve করতে পারে।

Convoy effect কী? কোন algorithm-এ হয়?

FCFS-এ একটা লম্বা CPU-bound process আগে CPU পেলে পেছনের সব ছোট (প্রায়ই I/O-bound) process তার পেছনে আটকে থাকে — average WT অনেক বেড়ে যায়, আর CPU ও I/O device পালা করে অলস পড়ে থাকে। উদাহরণ: 24, 3, 3 burst — লম্বাটা আগে থাকলে avg WT 17, পরে থাকলে 3।

Starvation কী, আর aging কীভাবে সমাধান করে?

কম priority-র (বা SJF/SRTF-এ লম্বা) process অনির্দিষ্টকাল CPU না পাওয়া, কারণ বেশি priority-র কাজ আসতেই থাকে। Aging: ready queue-তে যত বেশি অপেক্ষা, তত priority বাড়ানো (যেমন প্রতি 2 unit-এ priority সংখ্যা 1 কমানো)। একসময় তার priority সবার চেয়ে বেশি হয়ে যায়, তাই অপেক্ষার একটা ঊর্ধ্বসীমা থাকে।

Round Robin-এ quantum → ∞ বা → 0 হলে কী হয়?

→ ∞: কোনো process quantum শেষ করতে পারে না, সবাই একবারে শেষ করে — RR = FCFS। → 0: তাত্ত্বিকভাবে processor sharing (সবাই সমান গতিতে এগোয়), কিন্তু বাস্তবে প্রায় পুরো CPU time context switch-এ খরচ হয়, কাজ প্রায় হয় না। তাই quantum switch-cost-এর চেয়ে অনেক বড়, আর ~80% CPU burst-এর চেয়ে বড় রাখা হয় (বাস্তবে 10–100 ms)।

Preemptive আর non-preemptive-এর উদাহরণ দাও।

Non-preemptive: FCFS, SJF, non-preemptive Priority — process শেষ বা block না হলে CPU ছাড়ে না। Preemptive: SRTF, preemptive Priority, Round Robin, Linux-এর CFS/EEVDF — timer interrupt বা বেশি জরুরি process এলে OS কেড়ে নিতে পারে। Priority scheduling দুই রকমই হয়।

Non-preemptive algorithm-এ response time আর waiting time সমান কেন?

Non-preemptive-এ process একবার CPU পেলে শেষ পর্যন্ত চলে, তাই তার সব অপেক্ষা প্রথমবার CPU পাওয়ার আগেই। WT = প্রথম CPU পাওয়া − AT = RT। Preemptive-এ preempt হলে আবার অপেক্ষা করে, তাই সেখানে WT ≥ RT।

Linux আসলে কোন scheduler ব্যবহার করে?

সাধারণ process-এর জন্য Linux 2.6.23 (2007) থেকে CFS (Completely Fair Scheduler) — প্রতিটা task-এর vruntime (nice value দিয়ে weight করা চলার সময়) রাখে, red-black tree-তে সবচেয়ে কম vruntime-ওয়ালা task পরের বার চলে; কোনো fixed quantum নেই। Linux 6.6 (2023) থেকে CFS-এর জায়গায় EEVDF (Earliest Eligible Virtual Deadline First) — যে task তার ন্যায্য ভাগের চেয়ে কম পেয়েছে (eligible), তাদের মধ্যে যার virtual deadline সবচেয়ে আগে, সে চলে; latency-sensitive task ভালো সাড়া পায়। এর পাশাপাশি real-time class SCHED_FIFO আর SCHED_RR (fixed priority, preemptive) আছে, যারা সাধারণ task-এর আগে চলে।

Throughput আর turnaround time কি একই জিনিস মাপে?

না। Throughput = প্রতি একক সময়ে কয়টা process শেষ হলো (system-এর দৃষ্টিতে)। Turnaround = একটা নির্দিষ্ট process আসা থেকে শেষ হতে কত সময় নিল (user-এর দৃষ্টিতে)। Convoy উদাহরণে দুই order-এ throughput সমান (30 unit-এ 3টা), কিন্তু average TAT 27 বনাম 13।
