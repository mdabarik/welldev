Return to Iman (React + ASP.NET Core)

মানুষের ঈমানে ফেরার গল্প শেয়ার করার community platform - React + TypeScript frontend, ASP.NET Core 8 Web API, EF Core ও PostgreSQL।

GitHub

Project Overview

এই project-টা কী আর কেন বানিয়েছ?
Return to Iman একটা কমিউনিটি platform, যেখানে মানুষ নিজের ঈমানে ফেরার গল্প (story) শেয়ার করতে পারে - লেখা, audio বা video দিয়ে। অন্যরা পড়ে/শুনে reaction ও comment দিতে পারে, আর moderator গল্প যাচাই করে publish করে। Pitch (৩০ সেকেন্ড): "যারা একা অনুভব করে, তারা যেন অন্যের সত্যিকারের গল্প থেকে অনুপ্রেরণা পায় - এই লক্ষ্যে বানানো। Frontend React + TypeScript, backend ASP.NET Core 8 Web API, database PostgreSQL।"
Tech stack কী কী আর কেন এগুলো বেছেছ?
  • Frontend: React 18 + TypeScript + Vite + Tailwind CSS (দ্রুত dev server, type safety, utility-first styling)
  • Backend: ASP.NET Core 8 Web API + EF Core 8 (Code First)
  • Database: PostgreSQL (Npgsql provider), Supabase-এ host করার পরিকল্পনা
  • Auth: BCrypt.Net-Next দিয়ে password hash
  • Docs: Swagger (Swashbuckle)
Project-এর বর্তমান অবস্থা কী? কী কী শেষ, কী বাকি?
সৎভাবে বলো: শেষ - ৫টা entity-র schema (EF Core model + AppDbContext configuration), API-র skeleton (CORS, Swagger, Npgsql, health-check endpoint), আর পুরো React UI (Home, Story Detail, Submit Story, Categories, Moderator Dashboard)। বাকি - UI এখনো mock data (useState-এ hard-coded) দিয়ে চলছে; real controller (stories, auth, comments), migration চালানো আর frontend ↔ API সংযোগ বাকি। এই পরিষ্কার উত্তর interviewer-এর কাছে সবচেয়ে বিশ্বাসযোগ্য, আর "এরপর কী করতাম" বলতে পারলে আরও ভালো।
কে কে এই system ব্যবহার করবে? (Actor ও Role)
  • Visitor - গল্প পড়া/শোনা
  • story_submitter (default role) - গল্প জমা দেয়, comment/reaction দেয়
  • Moderator/Admin - জমা পড়া গল্প approve/reject করে, category বানায়
Role User.Role string column-এ থাকে, default "story_submitter"।

Database Design (EF Core + PostgreSQL)

Database-এ কী কী table আছে আর তাদের সম্পর্ক কী?
৫টা table: Users, Categories, Stories, Comments, MediaItems।
  • Category 1 → N Story
  • User 1 → N Story (SubmittedBy)
  • Story 1 → N Comment, User 1 → N Comment
  • Story 1 → N Media (audio/video)
প্রতিটা সম্পর্ক foreign key + navigation property (ICollection<T>) দিয়ে।
Primary key হিসেবে Guid কেন নিয়েছ, int identity নয় কেন?
সুবিধা: client বা অন্য service-এও ID বানানো যায়, DB-র ওপর নির্ভর করে না; ID অনুমান করে (enumeration) অন্যের data দেখা কঠিন; পরে database merge/shard করা সহজ। অসুবিধা: বেশি জায়গা (16 byte), random হওয়ায় clustered index-এ page split বেশি। PostgreSQL-এ সাধারণত তেমন সমস্যা হয় না, চাইলে sequential UUID (UUIDv7) নেওয়া যায়।
OnDelete behavior কীভাবে ঠিক করেছ - Cascade বনাম Restrict?
  • Category → Story: Restrict - category মুছলে গল্প যেন নীরবে হারিয়ে না যায়; আগে গল্পগুলো সরাতে/বদলাতে হবে।
  • User → Story/Comment: Cascade - user মুছলে তার data-ও যায় (privacy/GDPR-এর "delete my data"-র সাথে মেলে)।
  • Story → Comment/Media: Cascade - গল্প মুছলে তার comment ও media এতিম (orphan) হয় না।
Trade-off: Cascade সুবিধাজনক কিন্তু ভুল করে user মুছলে অনেক data যায়, তাই production-এ soft delete (IsDeleted) ভালো বিকল্প।
Fluent API আর Data Annotation-এর পার্থক্য কী? তুমি কোনটা ব্যবহার করেছ, কেন?
Annotation ([Required]) model class-এ বসে; Fluent API OnModelCreating-এ। আমি Fluent API নিয়েছি: model class পরিষ্কার (persistence-মুক্ত) থাকে, আর unique index, default value (HasDefaultValueSql("now()")), composite key, delete behavior - যা annotation দিয়ে হয় না - সব এক জায়গায় থাকে।
Email-এর unique constraint কীভাবে নিশ্চিত করেছ? শুধু code-এ check করলে কী সমস্যা?
entity.HasIndex(u => u.Email).IsUnique() - DB-স্তরে unique index। শুধু code-এ "আগে আছে কি না দেখো, তারপর insert" করলে দুই request একসাথে এলে race condition-এ দুটোই পাস করে duplicate হয়। DB constraint-ই শেষ প্রহরী; violation এলে DbUpdateException ধরে 409 Conflict ফেরাতে হবে।
CreatedAt-এ HasDefaultValueSql("now()") কেন, C# property-র default DateTime.UtcNow থাকতেও?
দুটোর কাজ আলাদা। C# default শুধু EF দিয়ে insert করলে কাজ করে; DB default সরাসরি SQL, অন্য tool বা script দিয়ে insert করলেও সময় বসায়, আর সময় আসে এক জায়গা (DB server) থেকে - client-এর ভুল ঘড়ি সমস্যা করে না। Timestamp সবসময় UTC-তে রাখা ভালো, দেখানোর সময় user-এর timezone-এ বদলাও।
Migration কী? কীভাবে চালাবে?
Model বদলালে schema-র versioned পরিবর্তন-ইতিহাস। dotnet ef migrations add InitialCreate → dotnet ef database update। Supabase-এর PostgreSQL-এ connection string বসিয়ে চালালেই table তৈরি হবে। Production-এ migration-কে CI/CD-তে বা SQL script বানিয়ে (migrations script) চালানো নিরাপদ।

Backend (ASP.NET Core Web API)

Program.cs-এ কী কী configure করেছ?
  • AddControllers() - controller-based API
  • AddCors - শুধু http://localhost:5173 (React dev server) অনুমোদিত
  • AddDbContext<AppDbContext>(UseNpgsql) - DI-তে scoped lifetime-এ
  • Swagger - শুধু Development-এ চালু
  • Pipeline: HttpsRedirection → CORS → Authorization → MapControllers
Middleware-র ক্রম গুরুত্বপূর্ণ - CORS অবশ্যই authorization-এর আগে।
CORS কী? তুমি কেন লাগিয়েছ আর AllowAnyOrigin দাওনি কেন?
Browser-এর Same-Origin Policy অন্য origin (localhost:5173 → localhost:5000) থেকে response পড়তে দেয় না; server Access-Control-Allow-Origin header দিয়ে অনুমতি দেয়। AllowAnyOrigin দিলে যেকোনো সাইট API ডাকতে পারত, তাই WithOrigins দিয়ে শুধু নিজের frontend। Production-এ সেই origin বদলে আসল domain বসাতে হবে (config থেকে)।
Connection string-এ password আছে - এটা repo-তে রাখা কি নিরাপদ?
না। appsettings.json-এ placeholder (YOUR_PASSWORD) রেখেছি; আসল secret User Secrets (dotnet user-secrets) বা environment variable (ConnectionStrings__DefaultConnection) দিয়ে দিই, production-এ Key Vault/Supabase secret। Commit হয়ে গেলে password ঘোরাতে (rotate) হয়, শুধু মুছলে git history-তে থেকে যায়।
Password কীভাবে সংরক্ষণ করবে? BCrypt কেন, SHA-256 নয় কেন?
User.PasswordHash-এ BCrypt hash, plain password কখনোই না। SHA-256 দ্রুত - attacker সেকেন্ডে কোটি guess করতে পারে; BCrypt ইচ্ছে করে ধীর (work factor) আর প্রতিবার আলাদা salt নেয়, তাই rainbow table ও brute force কঠিন। BCrypt.HashPassword(pw) / BCrypt.Verify(pw, hash)।
আরও API বানালে endpoint-গুলো কেমন হবে? (REST design)
  • GET /api/stories?category=&page= - published গল্প, pagination সহ
  • GET /api/stories/{id}
  • POST /api/stories - গল্প জমা (IsPublished=false)
  • PATCH /api/stories/{id}/publish - moderator
  • POST /api/stories/{id}/comments
  • POST /api/auth/register, /login
Entity সরাসরি না ফেরিয়ে DTO ফেরাব, যাতে PasswordHash-এর মতো field না ফাঁস হয় আর JSON-এ circular reference না আসে।
Authentication/Authorization কীভাবে যোগ করবে?
Login-এ JWT access token (ছোট মেয়াদ) + refresh token; User.Role-কে claim হিসেবে token-এ রাখব। Moderator endpoint-এ [Authorize(Roles = "moderator")]। গুরুত্বপূর্ণ: UI-তে বাটন লুকানো নিরাপত্তা নয় - প্রতিটা check server-এ হতে হবে। এখন Dashboard শুধু frontend-এ আছে, এটা auth ছাড়া production-এ যাবে না।
Moderation workflow কীভাবে কাজ করে?
গল্প জমা হলে IsPublished = false। Moderator Dashboard-এ pending তালিকা দেখে preview করে approve (IsPublished = true) বা reject করে। শুধু IsPublished == true গল্প public query-তে আসে (Where(s => s.IsPublished)) - এই filter ভুলে গেলে অপ্রকাশিত গল্প ফাঁস হবে, তাই EF Core global query filter একটা ভালো সুরক্ষা। Reject-এর কারণ জানাতে একটা status/reason field যোগ করা যায়।
Audio/Video upload কীভাবে সামলাবে?
Media table-এ শুধু URL আর duration থাকে (MediaUrl, max 2048), ফাইল নিজে DB-তে নয় - বড় binary DB-তে রাখলে ধীর ও ব্যয়বহুল। ফাইল যাবে object storage (Supabase Storage/S3)-এ, client pre-signed URL দিয়ে সরাসরি upload করবে। Server-এ file type/size যাচাই, আর antivirus/content scan দরকার। Streaming-এ CDN ও HTTP range request কাজে লাগে।

Frontend (React + TypeScript)

Frontend-এর structure কেমন? Routing কীভাবে হয়?
src/pages/ (Home, StoryDetail, SubmitStory, Categories, Dashboard) আর src/components/ (Navbar, Footer)। এখন routing state-based - page state আর setPage(...) prop দিয়ে। এর সীমা: URL বদলায় না, back button ও link share কাজ করে না, deep link নেই। উন্নতি: React Router (/stories/:id) বসানো।
useEffect কোথায় ব্যবহার করেছ? Cleanup কেন জরুরি?
Story Detail-এর audio player-এ: isPlaying true হলে setInterval প্রতি সেকেন্ডে currentTime বাড়ায়। Return করা cleanup function (clearInterval) না থাকলে component unmount বা pause-এর পরও timer চলত - memory leak ও একাধিক interval জমে গতি দ্বিগুণ হতো। Dependency [isPlaying], তাই শুধু সেটা বদলালেই effect চলে। উন্নতি: আসল <audio> element-এর timeupdate event ব্যবহার, কারণ setInterval drift করে।
Reaction toggle (like/inspired) কীভাবে বানিয়েছ? Immutable update কেন?
setReactionCounts(prev => ({...prev, [type]: {count: active ? count-1 : count+1, active: !active}}))। State সরাসরি বদলালে (mutate) React পরিবর্তন ধরতে পারে না, তাই spread দিয়ে নতুন object; আর আগের মানের ওপর নির্ভর করায় functional update (prev =>) ব্যবহার, যাতে stale state না আসে। আসল সংস্করণে optimistic update + server-এ POST, ব্যর্থ হলে rollback।
Form (Submit Story) কীভাবে handle করেছ? File drag-and-drop?
Controlled component - প্রতিটা input formData state-এর সাথে বাঁধা। onDragOver-এ preventDefault() না দিলে drop কাজ করে না; onDrop-এ e.dataTransfer.files[0]। বাকি: client-side validation (খালি, ফাইলের size/type), আর server-এও আবার validate (client-এর validation এড়ানো যায়)। জমা দিলে FormData/multipart বা pre-signed upload।
Frontend-কে real API-র সাথে কীভাবে জুড়বে? Loading/error কীভাবে সামলাবে?
এখন hard-coded array। বদলে fetch/axios + TanStack Query - caching, loading/error state, refetch, mutation। Base URL import.meta.env.VITE_API_URL-এ (Vite-এর env)। Token httpOnly cookie-তে রাখাই নিরাপদ (localStorage-এ XSS-এ চুরি যায়)। Loading skeleton আর error message ছাড়া UI অসম্পূর্ণ।
XSS থেকে কীভাবে বাঁচবে? বিশেষ করে user-এর লেখা গল্প দেখানোয়?
গল্প user-generated, তাই ঝুঁকি বেশি। React JSX-এ {text} স্বয়ংক্রিয়ভাবে escape করে, তাই নিরাপদ। বিপদ হলো dangerouslySetInnerHTML - rich text লাগলে তার আগে DOMPurify দিয়ে sanitize। Server-এও input যাচাই, আর Content-Security-Policy header।
Tailwind-এ custom design (dark theme, colour token) কীভাবে করেছ?
tailwind.config.js-এর theme.extend.colors-এ semantic token (background, primary, surface-container) আর darkMode: "class"। Hex সরাসরি না লিখে নাম ব্যবহার করায় theme বদলানো এক জায়গা থেকে হয়। Google Fonts (Noto Serif + Hanken Grotesk) আর Material Symbols icon।

Design, Quality ও Scale

কী কী security ঝুঁকি আছে আর কী ব্যবস্থা নেবে?
  • SQL injection - EF Core parameterized query
  • XSS - JSX escape + sanitize
  • Broken access control - server-এ role check, IDOR ঠেকাতে "এই গল্প কি এই user-এর?" যাচাই
  • Brute force - login-এ rate limiting
  • Secrets - repo-তে নয়
  • HTTPS আর CORS সীমিত
কেন একই repo-তে দুটো project (API ও Web) আলাদা রেখেছ?
Frontend ও backend আলাদা deploy, আলাদা scale, আলাদা technology হতে পারে (Web → Vercel/Netlify static, API → container/App Service)। সীমারেখা হলো HTTP API contract। Trade-off: CORS ও দুটো pipeline সামলাতে হয়; একই repo (monorepo) হওয়ায় একসাথে বদলানো সহজ।
Testing কীভাবে করবে?
Backend: xUnit দিয়ে service logic, WebApplicationFactory দিয়ে integration test (in-memory বা Testcontainers PostgreSQL)। Frontend: Vitest + React Testing Library (reaction toggle, form validation)। শুরুতেই /api/healthcheck আছে, যেটা deploy-পরবর্তী smoke test আর load balancer-এর health probe-এ কাজে লাগে।
Project-টা scale করতে হলে কী করতে?
Pagination ও index (Stories(IsPublished, CategoryId, CreatedAt)), গল্পের তালিকা cache (Redis), media CDN, search (PostgreSQL full-text/Elasticsearch), moderation queue background job-এ, Docker + CI/CD, rate limiting, আর structured logging/monitoring। Comment count-এর মতো aggregate আলাদা counter column-এ।
এই project-এ সবচেয়ে কঠিন বা শেখার মতো কী ছিল? আবার বানালে কী বদলাতে?
নিজের কথায় বলো, তবে মূল সুর: schema-র সম্পর্ক ও delete behavior ভাবা, আর UI আগে বানিয়ে পরে API জোড়ার ঝুঁকি। আবার বানালে: API-first (OpenAPI contract আগে), React Router + TanStack Query শুরু থেকেই, JWT auth ও role আগে, IsPublished-এর বদলে status enum (Pending/Approved/Rejected), আর soft delete।
