1আগে Same-Origin Policy (SOP)

CORS বুঝতে হলে আগে বুঝতে হবে browser কী আটকায়। Origin = scheme + host + port। তিনটার যেকোনো একটা আলাদা হলেই সেটা আলাদা origin। Path, query, hash — এগুলো origin-এর অংশ না।

URLhttps://shop.com-এর সাথেকেন
https://shop.com/cart?id=7Same-originশুধু path আর query আলাদা
https://shop.com:443/apiSame-originhttps-এর default port 443 — একই কথা
http://shop.comCross-originScheme আলাদা (http vs https)
https://api.shop.comCross-originHost আলাদা — subdomain-ও আলাদা origin
https://www.shop.comCross-originwww-ও একটা আলাদা host
https://shop.com:8443Cross-originPort আলাদা
http://localhost:5173 → http://localhost:5000Cross-originDev-এ frontend আর API আলাদা port — এখান থেকেই বেশিরভাগ CORS error

Same-site ≠ same-origin: app.shop.com আর api.shop.com একই site (registrable domain shop.com) — cookie-র SameSite নিয়ম এদের same-site ধরে। কিন্তু origin আলাদা, তাই CORS লাগবে। Interview-এ এই পার্থক্যটা প্রায়ই ধরা হয়।

SOP কী আটকায়, কী আটকায় না

আটকায় — অন্য origin-এর data পড়া

  • JS দিয়ে fetch() / XMLHttpRequest-এর cross-origin response পড়া
  • অন্য origin-এর iframe বা popup window-এর DOM পড়া
  • Cross-origin image আঁকা canvas-এর pixel পড়া (canvas "tainted" হয়ে যায়)
  • অন্য origin-এর localStorage / IndexedDB

আটকায় না — request পাঠানো আর embed করা

  • <form action="https://bank.com/transfer" method="POST"> submit
  • <img src>, <script src>, <link rel="stylesheet">, <video>
  • <iframe>-এ অন্য site দেখানো (ভেতরটা পড়া যায় না)
  • Link-এ click করে navigation
মূল কথা: বেশিরভাগ ক্ষেত্রে browser cross-origin request পাঠিয়েই দেয়, server সেটা process-ও করে, response-ও ফেরত আসে। তারপর browser দেখে response-এ অনুমতি (Access-Control-Allow-Origin) আছে কি না — না থাকলে JS-এর হাতে response দেয় না। CORS তাই মূলত ঠিক করে "JS কি response পড়তে পারবে?"। ব্যতিক্রম: যে request-এ preflight লাগে, সেখানে preflight fail করলে আসল request যায়ই না।
JS: fetch()→Browser request পাঠায়→Server process করে→Response ফেরত→Browser CORS check→JS পড়তে পারে/TypeError: Failed to fetch

2CORS কী — server opt-in করে

CORS (Cross-Origin Resource Sharing) হলো SOP-কে নিয়ন্ত্রিতভাবে শিথিল করার নিয়ম। Server response header দিয়ে বলে দেয় "এই origin আমার response পড়তে পারবে"। নিয়মটা browser enforce করে — server শুধু অনুমতি ঘোষণা করে। curl, Postman বা অন্য server-এর code browser না, তাই তারা CORS নিয়ে মাথাই ঘামায় না।

Headerকে পাঠায়মানে
OriginBrowser (request)কোন origin থেকে request আসছে। Browser নিজে বসায় — JS এটা বদলাতে পারে না (forbidden header)। curl দিয়ে অবশ্য যা খুশি লেখা যায়।
Access-Control-Request-MethodBrowser (preflight)আসল request কোন method-এ যাবে, যেমন PUT
Access-Control-Request-HeadersBrowser (preflight)আসল request-এ কোন non-safelisted header থাকবে, যেমন authorization,content-type
Access-Control-Allow-OriginServerকোন origin পড়তে পারবে — একটাই exact origin অথবা *। কমা দিয়ে একাধিক origin দেওয়া যায় না; একাধিক লাগলে server allowlist থেকে মিলিয়ে request-এর origin-টাই ফেরত দেয়।
Access-Control-Allow-MethodsServer (preflight)কোন method অনুমোদিত, যেমন GET, POST, PUT, DELETE
Access-Control-Allow-HeadersServer (preflight)কোন request header অনুমোদিত, যেমন Content-Type, Authorization
Access-Control-Allow-CredentialsServertrue হলে cookie / HTTP auth সহ (credentials: 'include') request-এর response JS পড়তে পারবে। তখন Allow-Origin-এ * চলবে না।
Access-Control-Expose-HeadersServerDefault-এ JS শুধু safelisted response header পড়তে পারে (Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified, Pragma)। X-Total-Count-এর মতো custom header পড়াতে চাইলে এখানে লিখতে হয়।
Access-Control-Max-AgeServer (preflight)Preflight-এর উত্তর কত সেকেন্ড cache থাকবে। Browser নিজের সীমা বসায় (Chrome সর্বোচ্চ 7200 = ২ ঘণ্টা)।
Vary: OriginServerResponse origin অনুযায়ী বদলায় — CDN / proxy cache-কে জানানো, যাতে এক origin-এর response আরেক origin-কে না দেয়।

3Simple request vs Preflighted request

কিছু request "নিরীহ" — HTML form দিয়েও এগুলো সবসময় পাঠানো যেত, তাই browser সরাসরি পাঠায় (spec-এর পুরনো নাম simple request)। বাকিগুলোর আগে browser নিজে একটা OPTIONS request পাঠিয়ে server-কে জিজ্ঞেস করে "এটা পাঠাতে পারি?" — এটাই preflight।

Preflight লাগে না — যদি সবগুলো শর্ত মেলে

  • Method: GET, HEAD বা POST
  • হাতে বসানো header শুধু CORS-safelisted: Accept, Accept-Language, Content-Language, Content-Type (নিচের শর্তে), Range (simple)
  • Content-Type শুধু text/plain, multipart/form-data বা application/x-www-form-urlencoded
  • Body-তে ReadableStream নেই, XHR upload-এ event listener নেই

Preflight লাগে — যেকোনো একটা হলেই

  • PUT, PATCH, DELETE ইত্যাদি method
  • Content-Type: application/json — হ্যাঁ, সাধারণ JSON POST-ও preflight করে
  • Authorization বা যেকোনো custom header (X-Request-Id…)

Preflight-এ কখনো cookie বা Authorization যায় না। তাই server-এর auth middleware যদি OPTIONS-কে 401 দেয়, preflight fail করবে।

    4Common CORS error ও সমাধান
    
    
    সব error-এর শুরু একই: Access to fetch at '…' from origin '…' has been blocked by CORS policy: — তারপরের অংশটাই আসল কারণ বলে। মনে রেখো: fix সবসময় server-এ, frontend code থেকে CORS ঠিক করা যায় না।
    
    
    
      
    
        
    Error-এর বাকি অংশকারণFix
    
        
          
    No 'Access-Control-Allow-Origin' header is present on the requested resource.Server CORS header দেয়নি — config নেই, origin allowlist-এ নেই, অথবা 500 error-এর response-এ CORS middleware চলেনি / proxy header ফেলে দিয়েছেOrigin allowlist-এ যোগ করো; CORS middleware সবার আগে বসাও; Nginx-এ always
    
          
    Response to preflight request doesn't pass access control check: It does not have HTTP ok status.OPTIONS-এ 401 / 404 / 405 / 500 এসেছে — প্রায়ই auth middleware token ছাড়া preflight-কে আটকায়CORS middleware auth-এর আগে বসাও; OPTIONS-কে 204 দাও
    
          
    The value of the 'Access-Control-Allow-Origin' header in the response must not be the wildcard '*' when the request's credentials mode is 'include'.* + cookieAllowlist থেকে exact origin ফেরত দাও + Allow-Credentials: true + Vary: Origin
    
          
    The value of the 'Access-Control-Allow-Credentials' header in the response is '' which must be 'true' when the request's credentials mode is 'include'.Cookie পাঠানো হয়েছে কিন্তু server Allow-Credentials দেয়নিAccess-Control-Allow-Credentials: true
    
          
    Request header field authorization is not allowed by Access-Control-Allow-Headers in preflight response.Preflight-এর Allow-Headers-এ Authorization নেইAllow-Headers-এ যোগ করো
    
          
    Method PUT is not allowed by Access-Control-Allow-Methods in preflight response.Method allow করা হয়নিAllow-Methods-এ যোগ করো
    
          
    The 'Access-Control-Allow-Origin' header contains multiple values '…, …', but only one is allowed.App আর Nginx দুজনেই header বসিয়েছে, অথবা কমা দিয়ে একাধিক origin লেখাCORS একটা জায়গাতেই (app অথবা proxy); একটাই origin ফেরত দাও
    
          
    The 'Access-Control-Allow-Origin' header has a value '…' that is not equal to the supplied origin.Hardcoded ভুল origin, অথবা Vary: Origin ছাড়া CDN অন্য origin-এর cached response দিয়েছেDynamic allowlist + Vary: Origin
    
          
    Redirect is not allowed for a preflight request.OPTIONS 301/302 পেয়েছে (http→https, trailing slash)Frontend-এ final URL-টাই call করো
    
          
    (error নেই) res.headers.get('X-Total-Count') → nullCustom response header expose করা হয়নিAccess-Control-Expose-Headers: X-Total-Count
    
            
      
    
    
    

    
    সঠিক server config
    
    
    Express · npm i cors
    

    import express from 'express';
import cors from 'cors';

const app = express();
const allowlist = new Set(['https://app.shop.com', 'https://admin.shop.com']);

// সব route আর auth middleware-এর আগে
app.use(cors({
  origin(origin, cb) {
    // Origin header নেই = same-origin GET বা curl / server-to-server — CORS প্রযোজ্য না
    if (!origin || allowlist.has(origin)) return cb(null, true);  // exact origin echo করবে
    return cb(null, false);                                       // কোনো CORS header দেবে না
  },
  credentials: true,                      // Access-Control-Allow-Credentials: true
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  exposedHeaders: ['X-Request-Id'],
  maxAge: 600,                            // preflight 10 মিনিট cache
}));
// cors package নিজেই Vary: Origin বসায় আর OPTIONS-কে 204 দিয়ে শেষ করে

app.get('/orders', requireAuth, listOrders);

    var builder = WebApplication.CreateBuilder(args);

    Nginx · reverse proxy-তে CORS (তখন app-এ CORS বন্ধ রাখো)
    

    # allowlist: মিললে origin-টাই, না মিললে খালি string (খালি হলে add_header বসেই না)
map $http_origin $cors_origin {
    default                  "";
    "https://app.shop.com"   $http_origin;
    "https://admin.shop.com" $http_origin;
}

server {
    listen 443 ssl;
    server_name api.shop.com;

    location /api/ {
        if ($request_method = OPTIONS) {
            add_header Access-Control-Allow-Origin      $cors_origin always;
            add_header Access-Control-Allow-Methods     "GET, POST, PUT, DELETE" always;
            add_header Access-Control-Allow-Headers     "Content-Type, Authorization" always;
            add_header Access-Control-Allow-Credentials "true" always;
            add_header Access-Control-Max-Age           600 always;
            add_header Vary                             Origin always;
            return 204;               # preflight backend পর্যন্ত যায়ই না
        }

        # always = 4xx/5xx response-এও header বসবে (নাহলে error-এর বদলে CORS error দেখবে)
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;
        add_header Access-Control-Expose-Headers    "X-Request-Id" always;
        add_header Vary                             Origin always;

        proxy_pass http://127.0.0.1:5000;
    }
}
    
    
    Nginx-এ ভেতরের block-এ (if) কোনো add_header থাকলে বাইরের সব add_header আর inherit হয় না — তাই দুই জায়গায় আলাদা করে লেখা।

    কেন কাজ করে
    
        
    Browser call করছে নিজের origin-এই (localhost:5173/api/…), তাই কোনো CORS নেই। Vite dev server request-টা server-to-server localhost:5000-এ পাঠায় — server-to-server-এ CORS প্রযোজ্যই না।
    
        
    Production-এ একই কৌশল: Nginx একই domain থেকে frontend আর /api দুটোই serve করলে CORS লাগেই না। আলাদা domain হলে সঠিক CORS config লাগবে।
    
        
    কখনো না: "Allow CORS" browser extension, chrome --disable-web-security — এগুলো শুধু তোমার browser বদলায়, user-দের browser-এ error থেকেই যায়, আর নিজের browser-এর নিরাপত্তা বন্ধ হয়ে যায়। mode: 'no-cors'-ও fix না — response "opaque" হয়ে যায় (status 0, body পড়া যায় না)।

    এতে যেকোনো site logged-in user-এর cookie দিয়ে API call করে response পড়তে পারে (cookie SameSite=None হলে)। এটা *-এর চেয়েও খারাপ — * অন্তত cookie-র সাথে চলে না।
    
      
    
      
    
        
    ২. null origin allow করা
    
        
    Sandboxed iframe, file:// page, কিছু redirect Origin: null পাঠায়। যেকোনো site চাইলে sandboxed iframe বানিয়ে null origin পেতে পারে — তাই allowlist-এ "null" রাখা মানে সবাইকে অনুমতি।

    চারটাকে প্রায়ই গুলিয়ে ফেলা হয়। CORS নিজে কোনো attack না — এটা একটা browser mechanism; সমস্যা হয় যখন সেটা ভুলভাবে config করা হয়। বিস্তারিত XSS / CSRF ছবিসহ: XSS, CSRF ও JWT গাইড।

    CORS কোনো CSRF defence না
    
        
    evil.com-এর একটা সাধারণ HTML form POST হলো "simple request" — browser cookie সহ পাঠিয়ে দেয়, server transfer করে ফেলে। CORS শুধু evil.com-কে response পড়তে দেয় না, কিন্তু ক্ষতি ততক্ষণে হয়ে গেছে।
    
        
    একটা সূক্ষ্ম ব্যাপার: API যদি শুধু application/json নেয়, cross-site JS-কে preflight করতে হয় — সেটা fail করলে request যায় না। কিন্তু এর উপর ভরসা করা ঠিক না (অনেক server text/plain-কেও JSON হিসেবে parse করে)। আসল defence: SameSite, CSRF token, Origin check।
    
      
    
      
    
        
    ভুল CORS = evil.com data পড়ে
    
        
    User shop-এ logged in→evil.com খোলে→evil-এর JS: cookie সহ fetch→Server Origin echo + Allow-Credentials→Browser পড়তে দেয়
    
        
    Server reflect করছে বলে browser ভাবে অনুমতি আছে। ফল: user-এর order, address, profile সব attacker-এর JS-এ। Defence: exact allowlist। Chrome-এর default SameSite=Lax এই ক্ষেত্রে বাড়তি সুরক্ষা দেয়।
    
      
    
      
    
        
    XSS CORS-কে পুরো bypass করে
    
        
    XSS-এর script app.shop.com-এর page-এর ভেতরেই চলে — তার জন্য api call মানে নিজের app-এর মতোই request; allowlist-এ app.shop.com আছে, তাই CORS সানন্দে অনুমতি দেয়। Same-origin হলে CORS-এর প্রশ্নই ওঠে না।
    
        
    তাই XSS থাকলে CSRF token, CORS — কোনোটাই বাঁচায় না, কারণ script page থেকে token-ও পড়তে পারে। Defence: output encoding, CSP।
    
      
    
    
    
  
    

  
  
    
    
    6কোন attack-এ victim-এর browser লাগে?
    
    
    তিনটা প্রশ্ন, তিনটা আলাদা উত্তর। মূল চাবি: attack-টা কোথায় চলে (execute হয়) আর কার credential ব্যবহার করে।
    

    
    "XSS attack কি user-এর browser ছাড়া করা যায়?"
    
    
    
      উত্তর: plant করা যায়, কিন্তু execute হতে browser-এর মতো renderer লাগে
      
    
        ① Plant — browser লাগে না→② Store — DB / log / ticket→③ Execute — কেউ page render করলে
      
    
      
    Plant: Stored XSS-এ attacker browser ছাড়াই, সরাসরি API-তে (curl বা script দিয়ে) এমন একটা comment / নাম / ticket পাঠাতে পারে যার ভেতরে HTML-script আছে। এই ধাপে কোনো victim লাগে না — data শুধু database-এ বসে থাকে।
    
      
    Execute: সেই text যখন কোনো page-এ escape ছাড়া HTML হিসেবে বসে আর কোনো JS engine সেটা render করে, তখনই script চলে — আর চলে যে render করছে তার origin ও session নিয়ে। JSON হিসেবে data রাখা বা curl দিয়ে পড়া কাউকে ক্ষতি করে না, কারণ কেউ সেটা execute করে না।
    
    
    
    
    
      
    
        
    কে render করছেXSS চলে?ক্ষতি কার
    
        
          
    Victim-এর browser (stored / reflected / DOM-based)হ্যাঁVictim-এর session, data, তার নামে action
    
          
    Admin panel — support ticket, log viewer (blind XSS)হ্যাঁAdmin — সবচেয়ে বেশি privilege, attacker নিজে কখনো page-টা দেখেই না
    
          
    Mobile app-এর WebViewহ্যাঁApp user; WebView যদি native function (JS bridge) expose করে, সেগুলোও
    
          
    Server-side headless browser / HTML→PDF renderer (Puppeteer, wkhtmltopdf)হ্যাঁServer নিজে — internal network-এ request (SSRF) বা local file পড়ার রাস্তা খুলতে পারে
    
          
    curl, Postman, backend code যা শুধু text হিসেবে store / return করেনাকারো না — HTML কখনো execute হয় না
    
            
      
    
    
    
    
    সারকথা: XSS হলো "inject হয় server-এ, চলে browser-এ"। ক্ষতি হতে browser বা browser-এর মতো কোনো renderer লাগবেই, আর ক্ষতি হয় যার renderer-এ চলল তার। Defence তাই output-এর জায়গায়: context অনুযায়ী encoding, textContent, CSP, আর server-side renderer-কে sandbox / network-isolate করা।
    

    
    "CSRF attack কি user-এর browser ছাড়া করা যায়?"
    
    
    
      উত্তর: না
      
    CSRF কাজ করে শুধু একটা কারণে: victim-এর browser অন্য site থেকে trigger হওয়া request-এ নিজে থেকেই victim-এর cookie জুড়ে দেয়। Attacker-এর নিজের মেশিন থেকে (curl / Postman) request পাঠালে তাতে victim-এর cookie থাকে না — server 401 দেয়। আর attacker-এর হাতে যদি আগে থেকেই cookie থাকে, সেটা session hijacking — CSRF না, আলাদা attack (cookie চুরি হলো কীভাবে — প্রায়ই XSS বা network)।
    
      
    
        Victim bank-এ logged in→evil.com খোলে→Hidden form auto-submit→Victim-এর browser cookie জুড়ে দেয়→Server ভাবে victim নিজেই চেয়েছে
      
    
    
    
    
    
      
    
        
    কে request পাঠাচ্ছেVictim-এর credential আছে?CSRF?
    
        
          
    Victim-এর browser, evil.com-এর form থেকে trigger, cookie authহ্যাঁ — browser নিজে জুড়ে দিল (SameSite অনুমতি দিলে)হ্যাঁ, এটাই CSRF
    
          
    Attacker-এর curl / Postmanনানা — শুধু 401
    
          
    Attacker-এর curl, চুরি করা cookie সহহ্যাঁ, কিন্তু চুরি করানা — এটা session hijacking
    
          
    Victim-এর browser, API-তে Authorization: Bearer header authনা — browser এই header নিজে থেকে বসায় না, আর evil.com SOP-এর কারণে app-এর token পড়তে পারে নানা
    
            
      
    
    
    
    
    সূক্ষ্মতা: browser যা নিজে থেকে পাঠায় তার সবকিছুই CSRF-এর ঝুঁকিতে — শুধু cookie না, HTTP Basic auth আর client certificate-ও। Bearer token CSRF-proof, কিন্তু localStorage-এ রাখলে XSS সেটা চুরি করতে পারে — তাই trade-off।
    
    
    Defence: SameSite=Lax বা Strict cookie (Chrome-এ না দিলে default Lax — তবে Lax top-level GET navigation-এ cookie পাঠায়, তাই GET দিয়ে কখনো state বদলাবে না); CSRF token (synchronizer বা double-submit); server-এ Origin / Sec-Fetch-Site header check; sensitive action-এ re-authentication। খেয়াল রাখো: SameSite শুধু cross-site আটকায় — তোমার নিজের কোনো subdomain দখল হলে সেটা same-site, তখন token / Origin check লাগবে।
    

    
    "SQL injection-এ কি browser লাগে?"

    QInterview-এ যা আসে
    
    
    
      
    Postman-এ কাজ করে, browser-এ CORS error — কেন?
    CORS browser enforce করে। Postman / curl browser না — তাদের কোনো Same-Origin Policy নেই, তাই header দেখেই না। Server আসলে দুই ক্ষেত্রেই response পাঠিয়েছে; browser শুধু JS-কে সেটা দিতে রাজি হয়নি। Fix তাই server-এ — ঠিক origin-কে Access-Control-Allow-Origin দাও।
    
      
    CORS কি server-এর security feature, না browser-এর?
    Browser-এর। Server শুধু policy ঘোষণা করে, browser মানে। এটা server-কে রক্ষা করে না — রক্ষা করে user-কে, যাতে কোনো site তার logged-in session দিয়ে অন্য site-এর data পড়তে না পারে। Server-কে তাই authentication / authorization আলাদাভাবে করতেই হবে, কারণ non-browser client CORS উপেক্ষা করে।
    
      
    Preflight কি আমার API handler / controller পর্যন্ত যায়?
    যাওয়া উচিত না — CORS middleware (ASP.NET-এর UseCors, Express-এর cors(), বা Nginx) OPTIONS-এর উত্তর 204 দিয়ে সেখানেই শেষ করে। Middleware না থাকলে বা ভুল ক্রমে থাকলে OPTIONS routing-এ গিয়ে 404/405 পায়, বা auth middleware 401 দেয় — preflight fail। Preflight-এ cookie / Authorization থাকে না, তাই OPTIONS-এ auth চাওয়া যাবে না। Max-Age দিয়ে preflight cache করা যায়, তাতে বারবার OPTIONS যায় না।
    
      
    Cookie-র সাথে Access-Control-Allow-Origin: * কেন চলে না?
    Spec ইচ্ছা করে নিষেধ করেছে। * + credentials চললে একটা ভুল config-এই internet-এর যেকোনো site যেকোনো logged-in user-এর data পড়তে পারত। তাই credentialed response-এ server-কে exact origin লিখতে হয় — যাতে সে সচেতনভাবে নির্দিষ্ট origin-কে বিশ্বাস করে। সমাধান: allowlist থেকে origin echo + Allow-Credentials: true + Vary: Origin।
    
      
    CORS কি CSRF আটকায়?
    না। CORS response পড়া আটকায়, request পাঠানো না। Cross-site form POST simple request — cookie সহ চলে যায়, server কাজ করে ফেলে। CSRF-এর জন্য SameSite cookie, CSRF token আর Origin check লাগে। উল্টো দিকে ভুল CORS (origin reflect + credentials) বরং নতুন দুর্বলতা তৈরি করে।
    
      
    একাধিক frontend domain হলে Allow-Origin-এ কী দেব?
    Header-এ একটাই মান থাকতে পারে — কমা দিয়ে list দিলে browser reject করে। Server request-এর Origin দেখে allowlist-এ exact match খোঁজে, মিললে সেই origin-টাই ফেরত দেয়, না মিললে কোনো CORS header দেয় না। সাথে Vary: Origin, যাতে cache গুলিয়ে না যায়।
    
      
    Response-এ header আছে, কিন্তু JS-এ res.headers.get() null দেয় — কেন?
    Cross-origin response-এ JS default-এ শুধু safelisted header পড়তে পারে। X-Total-Count, X-Request-Id-এর মতো custom header পড়াতে server-কে Access-Control-Expose-Headers-এ নাম দিতে হয়।
    
      
    Origin header কি fake করা যায়? তাহলে CORS-এর মানে কী?
    Browser-এর JS থেকে না — Origin forbidden header, browser নিজে বসায়। curl থেকে হ্যাঁ, যা খুশি। কিন্তু curl-এ কোনো victim-এর cookie নেই, তাই fake Origin দিয়ে attacker শুধু নিজের access-ই পায়। CORS-এর লক্ষ্য browser-এর ভেতরের user-কে রক্ষা করা — এই কারণেই এটা authentication-এর বিকল্প না।
